另一半如何规划

统计信息是输入。规划是数据库对它们所做的事：它接收一个声明式查询——描述你想要什么，而完全不涉及怎么做——并将其转化为一个可执行计划，这个计划里全都是怎么做。这其中有两项工作。第一，将查询重写为逻辑等价但更易处理的形式，这就是子查询展平、谓词下推和视图合并所在的地方。第二，在物理计划空间（join 顺序、join 算法、访问路径）中搜索 cost model 能找到的最便宜的方案。第二项工作是困难的部分，因为一个查询可能的 join 顺序数量增长得比任何人愿意想象的速度都快，而本文中的每个数据库在本质上都是一种避免枚举全部顺序的策略。

两个问题将这里的六个系统区分开来。每个系统如何驯服那个搜索空间？以及一旦有了答案，它允许你在多大程度上与结果争辩？这两个问题听起来像同一个问题。它们不是，而本文最有价值的地方正是将它们拆开来看。一个数据库可以搜索得极其出色却完全拒绝给你任何覆盖手段（Snowflake），也可以搜索得粗糙却塞给你一大把 hints（直到最近的 MySQL），或者既努力搜索又暴露所有可用的杠杆（Oracle）。搜索的复杂程度和控制面的慷慨程度是两个独立的轴。知道一个系统在这两根轴上各自位于何处，就基本上告诉了你与它的 planner 相处是什么感觉。

共同的祖先

这里几乎每一个系统都起源于、或定义了自身相对于一篇 1979 年论文的立场：IBM 的 Selinger 及其同事提出的 System R optimizer 设计。配方你已经知道了：从统计信息中估算操作的成本，自底向上用动态规划枚举 join 顺序，剪枝掉被覆盖相同关系集合的更便宜子计划所支配的任何子计划，并将搜索限制在左深树以控制组合爆炸。基于成本、自底向上、动态规划。四十多年后它仍然是大多数生产级优化器的骨架。

PostgreSQL 是最接近它的现存后代，并且它作为一个干净的参照点，因为它几乎没有偏差地实现了教科书的方案。planner 在 standard_join_search 中用自底向上的动态规划枚举 join 顺序，在此过程中为 Path 节点计成本，为每个关系集合保留最便宜的路径，并从胜出者组装出 Plan 树。当 FROM 子句中的表数量超过 geqo_threshold（默认 12）时，穷举搜索变得不可行，PostgreSQL 切换到 GEQO，一种遗传算法，通过繁殖和变异候选 join 顺序来搜索，而不是枚举它们。超过阈值后，你就用"一定能找到一个计划"的保证换掉了"一定能找到最便宜的计划"的保证。预备语句的计划会被缓存，运行时根据 plan_cache_mode 和持续的成本比较在重新规划的自定义计划和可复用的通用计划之间选择。

而控制面几乎是有意地一片空白。PostgreSQL 不提供任何查询 hints。一个都没有。这是一项政策，不是疏忽，并且是整个项目历史上争论最多的决定。先记住这个想法；这是个适合收尾而非开篇的注脚。

Oracle：转换引擎

Oracle Database 分两个阶段进行规划，而第一阶段是人们低估的那个阶段。在它为任何 join 顺序计算成本之前，查询转换层会将你的 SQL 重写为它可能更偏好的其他 SQL：子查询解嵌套、视图合并、谓词下推、OR 展开、join 因式分解、针对数据仓库模式的星型转换、group-by 放置、针对物化视图的查询重写。这些转换中有些是启发式的（总是被应用，因为它们总是至少一样好），但有趣的是基于成本的转换：Oracle 生成转换后和未转换的版本，对两者都进行成本计算，并保留胜出者。optimizer 在进入 join 枚举之前，就已经在重写你的查询并对各个重写版本互相定价。

接着计划生成器完成 System R 的工作：枚举 join 顺序、join 方法和访问路径，计算成本，选择最便宜的。完整的经典 join 菜单都可使用，而 Oracle 规划的运行时自适应部分（自适应计划、SQL plan directives）我已经在统计信息那篇文章中涵盖了，因为那套机制是用来纠正基数估算的，那既是统计信息的故事，也是规划的故事。

控制面是 Oracle 赢得"极致主义"标签的地方。有一套丰富的内联 hint 系统（LEADING、USE_HASH、INDEX、FULL、PARALLEL 以及几十个其他的），嵌入在 /*+ ... */ 注释中。在 hints 之上是 SQL Plan Management：SQL plan baseline 捕获一条语句已知良好的计划，并禁止 optimizer 使用不同的计划，直到新的候选计划已在后台被验证确实更快为止。那是将计划稳定性作为一种有管理的生命周期，而不是简单的冻结一个计划。SQL profile（由 SQL Tuning Advisor 生成）将基数修正绑定到一条语句上而不触及语句文本。计划驻留在共享游标缓存中，按 SQL 文本键控并在多次执行间共享，而自适应游标共享允许一条语句为不同的绑定变量选择性分布保留多个计划，因此 status = 'rare' 的计划和 status = 'common' 的计划可以共存。这每一层都是一个你可以干预的地方。Oracle 的理论是，一个认真的 DBA 最终会需要所有这些。

Db2：重写图，然后计成本

IBM Db2（同样是 LUW 产品线）源自 Starburst，即 IBM Almaden 研究院的 optimizer，这体现在其架构中。一条查询被解析成一个查询图模型（Query Graph Model），一个内部的图表示，然后两个不同的阶段在其上操作。查询重写阶段激进地、启发式地转换 QGM：相关子查询变成 join，谓词迁移到它们能最早剪枝的地方，冗余 join 消失，视图合并。接着基于成本的优化阶段在重写后的图上进行 join 枚举和物理计划选择，所有三种经典 join 方法都在桌面上。

其独特的规划旋钮是优化类（optimization class），通过 CURRENT QUERY OPTIMIZATION 设置，从 0 到 9，默认 5。这是一个调节 optimizer 工作强度的单一旋钮，同时控制尝试哪些重写以及如何搜索 join 空间；较低的类使用贪婪 join 枚举以快速规划，而类 9 则释放一个近乎穷举的动态规划搜索，留给你用于确实复杂的查询——这些查询的规划时间本身是值得付出的。PostgreSQL 将类似的权衡隐藏在 geqo_threshold 中；Db2 将整个频谱做成一个会话设置并期望你去使用它。

计划复用有一个本文中其他系统都不具备的特殊之处：静态 SQL。经典的 Db2 模式在编译时将 SQL 绑定到一个包中，在那时计算成本并冻结访问计划，然后按那个冻结的计划执行直到你显式重新绑定。计划被提前选定一次并存储下来。动态 SQL 得到的是更熟悉的处理方式，计划保存在包缓存中。而 hint 机制也特有结构：不是内联注释，Db2 使用优化指南（optimization guidelines），即注册在数据库上的 XML 文档（优化配置文件），为匹配的语句指导 join 顺序、访问方法和重写选择。这是一种有 schema 的 hinting。

MySQL：一个在飞行中被替换的 planner

MySQL 是这里唯一一个你可以实时看到它的 planner 被重新构建的系统，这使它成为最有趣也最难用现在时来描述的系统。

传统 optimizer 是朴素的那一个。Join 枚举是一种贪婪、深度优先、基于成本的搜索，限制在左深树，由 optimizer_search_depth（默认 62）界定，并由 optimizer_prune_level 进行启发式剪枝。cost model 是可用的，并且多年来一直相当粗糙。MySQL 8.0 叠加了真正的转换（派生表合并、子查询到半连接的转换及一组策略、物化、索引条件下推、索引合并），所有这些都通过 optimizer_switch 标志来切换，这拽着 optimizer 向前走，而没有改变其左深、贪婪的核心。

替代者是 hypergraph optimizer，在 8.0.23 中实验性引入并从此稳步开发。它将查询建模为一个超图（顶点是表，超边是可以同时触及多个表的 join 谓词），并在其上运行 DPhyp，一种恰当的动态规划 join 枚举算法。后果正是 System R 留下的东西：它考虑丛生树（bushy tree），而不仅仅是左深树，并将 hash join 视为一等公民。直到最近它只能在 stock MySQL Server 的调试构建中使用；从 MySQL 9.7 Community Edition（2026 年 4 月）起，它随每个版本一起发布，作为可选择的替代方案，默认关闭，通过 optimizer_switch='hypergraph_optimizer=on' 按会话或按语句开启。它已经是 MySQL HeatWave 中的默认 optimizer，而在今天的普通安装中你仍在运行贪婪的左深 optimizer，除非你将新的打开。MySQL 正在所有人面前从一个 1990 年代的 join optimizer 迁移到一个现代版本，一个版本接一个版本。

在控制方面，MySQL 是慷慨的。有传统的索引 hints（USE INDEX、FORCE INDEX、STRAIGHT_JOIN）和一个在 8.0 中新增的较新的 optimizer hints 族，放在 /*+ ... */ 注释中（JOIN_ORDER、HASH_JOIN、BKA、SET_VAR 用于为单条语句覆盖 optimizer 标志，等等）。它所缺失的是持久的计划管理；旧的查询缓存在 5.7 中被弃用并在 8.0 中被移除，没有 Oracle 风格的共享计划存储。计划被创建、使用，然后遗忘。

SQLite：小搜索，冻结行为

SQLite 运行着下一代查询规划器（Next-Generation Query Planner），自 2013 年起就在使用，对于一个可以装进手机的数据库来说，它是一个比你想像中更有原则的基于成本的 planner。搜索是针对 join 循环顺序的，因为每个 join 都是嵌套循环，唯一的决策是哪个表驱动外循环以及哪个索引服务每个内循环。NGQP 在每一步保持多个候选的部分计划存活并向前计算它们的成本，这听起来平淡无奇，直到你了解到它所取代的旧 planner 是一个纯粹的最近邻启发式算法，每一步只保留单一最便宜的选择，因此经常错过一个开头稍差但结尾好得多的排序。这次升级是从"贪婪选一"到真正的有限搜索。

转换列表长且有完善的文档：子查询展平、将 WHERE 条件推入子查询和视图、OR-by-union 优化、MIN/MAX 和 COUNT(*) 快捷方式、省略其列从未被使用的 LEFT JOIN、常量传播，以及 skip-scan。最迷人的条目是自动索引：如果 SQLite 判断一个查询会从某个不存在的索引中受益，它会在当场构建一个临时索引，仅为那一条查询使用它，然后将其丢弃。一个没有 DBA 的数据库会在一条语句的持续时间内为自己建索引。

一切最终编译成 VDBE 字节码，而 planner 优先考虑稳定性甚于聪明；项目发布了一份明确的检查清单，用于避免跨升级的计划退化，因为 SQLite 内置在那些无法容忍一个昨天很快的查询在库版本升级后变慢的应用程序中。控制面匹配了那种你应该很少需要它的哲学：INDEXED BY 和 NOT INDEXED 子句，一元 + 用于取消一个条件对索引使用的资格，CROSS JOIN 用于固定循环顺序（SQLite 从不重排它），以及 likelihood() 系列用于修正选择性猜测。文档对所有这一切的姿态是相同的：最后的手段，如果你需要一个，请报告查询以便 planner 能被修复。

DuckDB：现代教科书，装在一个嵌入式盒子中

DuckDB 就是当读过近期文献的人从头构建一个 optimizer 且没有向后兼容性需要遵循时得到的结果。管道是干净的：解析器，然后是绑定器（根据目录解析表和列），然后是逻辑规划器，然后是一叠 optimizer 规则，然后是一个选择算子实现的物理规划器。当前构建运行着超过两打不同的 optimizer 规则，而这些名字是现代经典的一次巡礼：表达式重写和常量折叠，过滤器下推（它还会在等价集合间复制谓词并剪枝可证明为空的子树），公共子表达式消除，统计信息传播，join 过滤器下推。

Join 顺序 optimizer 是真家伙：DPccp，来自 Moerkotte 和 Neumann 的"Dynamic Programming Strikes Back"中的动态规划枚举，当 join 图太大而无法穷举搜索时回退到贪婪。这比 PostgreSQL 的默认更强，后者在十二张表时就倒向遗传算法；DuckDB 在动态规划中停留更久，并且回退到贪婪而非随机。另一个突出之处是子查询解嵌套：DuckDB 实现了对任意相关子查询的展平（来自 Neumann–Kemper 工作线的依赖 join 消除技术，内部称为"delim join"），这意味着其他系统需要为每个外行重新执行的相关子查询被重写为单次基于集合的 join。对于分析型查询，这经常是秒和小时之间的差别。

控制是最小化的且毫无歉意。没有真正的 hint 系统；你可以禁用特定的 optimizer 规则以用于调试，你可以通过禁用 join 顺序 optimizer 并按顺序书写 join 来固定 join 顺序，但这些是逃生舱口，而不是受支持的调优面。DuckDB 自己在这个问题上写得很直接，甚至有点冒失：如果你认为你找到了一个可以手动击败 optimizer 的查询，请确保你也为数据所有可能的未来状态做了手动优化，因为 optimizer 已经做了。其立场是搜索足够好，以至于覆盖它通常是一个你还没注意到的错误。

Snowflake：最大搜索，零旋钮

Snowflake 在云服务层进行规划，在架构上与执行查询的计算仓库分离，而这种分离很重要：规划是一项集中化的托管服务，而不是在计算层内部发生的事情。optimizer 是基于成本的，由始终保持最新的微分区元数据提供数据，它生成一个形状为由链接连接的算子组成的 DAG，其中这些链接是跨仓库节点移动和重新分发行的数据交换边。基于成本的 join 排序选择顺序；真正的分布式决策是每个 join 的分发策略，将小的一侧广播到每个节点或对两侧进行哈希分区并 shuffle。正如我在统计信息中提到的，"broadcast vs. shuffle" 是云数据仓库版本的 "nested loop vs. hash"，而 Snowflake 现在通过自适应 Join 决策做出这个选择，使用来自运行时执行的反馈在广播 join 和哈希分区 join 之间切换，而不是仅凭估算做出承诺。

而控制面是有意地一片空白。Snowflake 不暴露任何内联查询 hints。在博客文章中流传的 /*+ BROADCAST */ 风格语法是从 Spark 借来的，不是 Snowflake 的一个特性；broadcast 还是 shuffle 的决策属于 optimizer，并且越来越属于运行时。最接近 hint 的东西是声明性的并存在于 schema 中：你可以使用 RELY 属性定义主键、外键和唯一约束，Snowflake 不强制执行这些约束，但让 optimizer 能够执行 join 消除和其他否则无法证明的重写。其他看起来像调优的东西（聚簇键、搜索优化服务）是物理设计，而非计划引导。在其之上，结果缓存在 24 小时内返回相同查询的已存储结果，完全不涉及规划和执行，这是所有查询优化中最有效的：不运行查询。

来自统计信息文章的发展轨迹在这里重复出现，但沿着不同的轴。在那里，Snowflake 消除了统计信息的决策。在这里，它消除了规划的决策。你写 SQL 并定义 schema；optimizer 拥有从那里开始的每一个选择，而它对你在 join 顺序上的意见不感兴趣。

这让 PostgreSQL 落在何处

将六个系统画在两根轴上，形状是清晰的。在搜索复杂程度上，现代基于成本的 planner 簇拥在顶部：Oracle 有基于成本的转换，Db2 有 Starburst 的先重写后计成本的拆分，DuckDB 有 DPccp 和任意子查询解嵌套，Snowflake 有分布式 cost model，而 MySQL 随着 hypergraph optimizer 的推出正在快速攀升。SQLite 按设计位于更低的位置，在单 join 算子上进行真实但小的搜索，它对此心满意足。在控制上，分布极其宽广且与第一根轴不相关：Oracle 和 Db2 递给你 hints、baselines、profiles 和 guidelines；MySQL 递给你 hints；SQLite 和 DuckDB 递给你几个最后手段的覆盖开关外加一段关于不要使用它们的布道；Snowflake 什么都不给你。

PostgreSQL 在搜索上高居而在控制上接近零，而后半段是那个深思熟虑且有争议的选择。planner 是一个忠实的 System R 实现，具有真正的动态规划，而项目在其整个历史中拒绝向核心添加查询 hints。其理由是一贯的，值得公正地陈述：hints 会将一个对去年的数据和去年的 optimizer 来说正确的计划固化下来，它们会成为一种拐杖，隐藏起项目更愿意修复的基数估算缺陷，而一个今天有帮助的 hint 在数据变化的那一天就是一个潜在的退化。反方立场同样真实并且由有能力的人持有：有时你确实比 optimizer 知道得更多，在生产环境中错误计划的代价不是理论性的，并且扩展 pg_hint_plan 确实存在，在那些等不及 planner 改进的场合被大量依赖。两件事都是真的。PostgreSQL 核心的立场是，官方认可的 hints 的正确数量仍然是零，并且搜索应该做得足够好以至于你不需要去使用它们；实践者的立场是"足够好"这句话里有太多文章。

这次比较所明确的是，PostgreSQL 的 planner 并非不够复杂——这是缺失的 hint 系统所引来的指责。它的搜索与这里除了基于成本转换的极致主义者之外的任何系统一样认真，然后它按原则拒绝让你覆盖结果。这种组合是罕见的。大多数搜索得这么好的系统（Oracle、Db2）也给你所有的杠杆；这里唯一另一个努力搜索并拒绝给你控制的系统是 Snowflake，而 Snowflake 之所以能这样做是因为它拥有整个技术栈直到存储层。PostgreSQL 拒绝给你控制权的同时却运行在你自管理的存储和统计信息之上，这取决于下午的心情要么是有原则的，要么是固执的，而这正是其中最 PostgreSQL 的特质。
