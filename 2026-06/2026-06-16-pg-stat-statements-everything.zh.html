即使不是第一，pg_stat_statements 也是 PostgreSQL 生态中使用最广泛的扩展之一。它随 contrib 一起发布，使用成本几乎为零。我们大多数人都用它来回答一个问题：数据库到底在干什么？ 它确实很有用。你可以用它获取某个时间段内发生的事情快照，然后更快地决定要修复什么。

从其他数据库引擎过来的人，可能会期待它更像一个 query store——那种内置的功能，能够保存归一化后的查询及其计划历史。但 pg_stat_statements 不是这样的东西。本文将深入探讨这个扩展到底能提供什么。

因为一旦你开始依赖它，就会逐渐注意到那些粗糙的边缘。这种差距来自"一个 query store 应该能做什么"和"它实际告诉你什么"之间的落差。

同一个查询可能会出现在很多行里。监控工具显示的数字和 mean_exec_time 对不上。查询消失了。数字一夜之间变了。

这些都不是 bug。所有这一切都源于 pg_stat_statements 的真正本质：它是一个固定大小的 hash table，存储运行中的计数器，驻留在 shared memory 中，以你的 parse tree 的 hash 值为 key。它只计数，不记录。把这一想法刻在脑子里，上面列表中的每件令人惊讶的事情就不再令人惊讶了。

下面的一切都可以复现。把这些粘贴到 scratch database 里：

CREATE TABLE customers (
    id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL
);

CREATE TABLE orders (
    id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id integer NOT NULL REFERENCES customers(id),
    amount numeric(10,2) NOT NULL,
    status text NOT NULL DEFAULT 'pending',
    created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO customers (name)
SELECT 'Customer ' || i FROM generate_series(1, 2000) AS i;

INSERT INTO orders (customer_id, amount, status, created_at)
SELECT (random() * 1999 + 1)::int,
       (random() * 500 + 5)::numeric(10,2),
       (ARRAY['pending','shipped','delivered','cancelled'])[floor(random()*4+1)::int],
       '2024-01-01'::date + (random() * 700)::int
FROM generate_series(1, 100000);

ANALYZE;

然后开启扩展：

-- 在 postgresql.conf 中设置
-- shared_preload_libraries = 'pg_stat_statements'  (需要重启)
CREATE EXTENSION pg_stat_statements;

它实际存储了什么

刚开启扩展，我们先从它呈现给你的东西开始看。

SELECT * FROM pg_stat_statements;

你会看到每个 distinct query shape 一行，以及后面跟着的一系列计数器：calls、total_exec_time、rows、shared_blks_hit、shared_blks_read 等等。

虽然存在一个 query 列，你可能会以为它保存了你的 SQL。但它并没有。如果你仔细看，query text 是被归一化（normalize）过的，常量被剥离了出去（WHERE id = 42 被存成 WHERE id = $1），而且不管运行多少次，每个 shape 只有一行。计数器只会往上加。一条语句运行，它对应 shape 的计数器增加，而那次单独的执行——它的值、它的时间、它的执行计划——都消失了。每行是一个 entry：按 shape 累积的 running total，而不是执行记录。本文中大部分的限制都源于这一点。

首先是数据存在哪里。计数器驻留在启动时分配的 shared memory 中，如我们所说，是一个固定的 hash map。被跟踪的语句数量有上限（pg_stat_statements.max，默认 5000）。query text 存储在磁盘上的一个文件中：$PGDATA/pg_stat_tmp/pgss_query_texts.stat，视图在你读取时将其与内存计数器做 join。

这个 map 中的每个 entry 以 queryid 为 key，而麻烦就从这里开始。

queryid

query jumble 在 PostgreSQL 14 中移入了 core；在此之前它只存在于 pg_stat_statements 内部。它的开关由 compute_query_id 设置控制，默认值 auto 表示只要有需要它的模块（比如这个扩展）被加载就开启。

queryid 由 Postgres core 计算，而不是扩展。当 Postgres 解析和分析一条语句时，它会遍历生成的树，并把定义查询结构的那些部分哈希成一个单一的 64 位数字，将常量值排除在外。Postgres 源码称这一步为 query jumble；pg_stat_statements 只是读取结果，并将其作为每行的 key。

排除常量是整个技巧的关键。WHERE id = 42 和 WHERE id = 99 会被 jumble 成同一个数字，常量显示为 $n 占位符，这样一个 entry 就可以代表数百万次只在参数值上有差别的执行。

SELECT * FROM orders WHERE id = 42;
SELECT * FROM orders WHERE id = 99;
SELECT * FROM orders WHERE id = 12345;

SELECT queryid, query, calls
FROM pg_stat_statements
WHERE query LIKE 'SELECT * FROM orders WHERE id%';

       queryid        |               query                | calls
----------------------+------------------------------------+-------
 -8198406948996196422 | SELECT * FROM orders WHERE id = $1 |     3

三次执行，一行。现在看看 queryid：它是负数。它是一个有符号 64 位整数，如果你的 dashboard 把它存成了无符号列，或把它当作友好标识符打印，就很容易出问题。它是一个 hash，不是序列号。把它当作一个不透明令牌、可能为负数，然后继续。

这也是各种意外开始的地方，因为 jumble 比"它会忽略常量"这句话听起来要敏感得多。

queryid 在不同版本之间不稳定

手册对此毫不含糊：

假定 queryid 在 PostgreSQL 主要版本之间保持稳定是不安全的。

哈希过程也对机器架构和平台其他方面的差异敏感。

如果你仔细阅读了前一节，就会发现：hash 来自 parse tree 的形状，而不是 query text。从 Postgres 16 升级到 17，或者迁移到不同的 CPU 架构，同样的 SQL 可能会 hash 成不同的 queryid。

任何通过 join queryid 来聚合整个集群中查询成本的工具，在集群不是同构的那一刻就会悄悄崩溃。文档特别提到了 replica：

逻辑复制方案不保证按位保持 replica 一致，因此在逻辑 replica 集合中，queryid 不能用作累计成本的标识符。

不要把 queryid 当作持久化的 key。
在一台服务器内，它在 minor version 之间是稳定的，这是唯一的保证。跨主要版本升级、不同 CPU 架构、或逻辑复制集合中的 replica 时，相同的 SQL 可能 hash 成不同的值。任何跨机器 join queryid 的 dashboard 或 rollup，都离安静地重复计数或丢掉行只有一次升级的距离。

queryid 跟踪的是 OID，而不是名字

jumble 使用的是查询引用的对象的 OID，而不是它们的名字。这衍生出两种行为，都直接来自手册，都让人猝不及防：

pg_stat_statements 会认为两个看起来完全相同的查询是不同的，如果它们引用了一个在两次执行之间被删除并重建的函数。

反过来说，如果一个表在两次查询执行之间被删除并重建，两个看似相同的查询可能被认为是相同的。

删除并重建一个表——这在迁移、dump-restore 或 blue-green cutover 中经常发生——所有针对它的查询都会获得一个新的 queryid，因为表现在有了一个新的 OID。你旧有的那些关于这个表的统计信息被困在旧的 id 下，看上去就像这些查询停止了运行。你的 dashboard 上显示的"挂掉"的查询并没有挂掉；是它的 OID 变了。

search_path 隐藏着同样的陷阱。SELECT * FROM orders 在一个连接中解析为 tenant_a.orders，在另一个连接中解析为 tenant_b.orders，因此一个 schema-per-tenant 的应用会将一个逻辑查询分散到每个 tenant 的 OID 上。行为是正确的，但要汇总"所有针对 orders 的读取"，就得你自己去解析 OID。

别名和结构也会泄露进去

如果两个看起来相似的查询使用了不同的表别名，这些查询会被认为是不同的。

这最后一条——别名敏感性——是对 ORM 用户伤害最大的。

ORM 行爆炸

jumble 归一化了常量。但它不归一化结构。两个你读起来是"同一个查询"但在 parse tree 中不同的语句——比如不同的列列表、不同的表别名、多了一个 LIMIT、或 AND 条件顺序不同——它们是不同的 shape，有不同的 queryid，在不同的行里。

ORM 不断产生这些变体。以下是 ActiveRecord、Hibernate 或 Ecto 应用为一个本质上相同的操作——"按 ID 加载一个 customer"——可能发出的四种查询：

SELECT id, name FROM customers WHERE id = $1;             -- queryid A
SELECT id, name, created_at FROM customers WHERE id = $1; -- queryid B  (.select 添加了列)
SELECT c.id, c.name FROM customers c WHERE c.id = $1;     -- queryid C  (使用了别名)
SELECT id, name FROM customers WHERE id = $1 LIMIT $2;    -- queryid D  (.first)

四行。calls 被分成了四份，每份看起来都微不足道，尽管这背后可能是你整个系统中最热的路径。mean_exec_time 是 per-row 的，因此一个命中所有四种变体的性能下降会被稀释到四行中。

ORM 不止产生四种。每个条件 .where、每个可选 .select、每次 eager-load 都是一个新 shape；一个逻辑查询会散落成几十甚至几百个 entry。你可以在实际的生产环境快照中看到，一个逻辑查询可能落在 几百 个不同的 queryid 下，其中每一个单独看都显得无足轻重。

这正是 qshape（boringSQL 技术栈的一部分）这类工具要解决的事情。

这个扩展无法修复这一点，而且它也不应该修复。jumble 运行的时候，还无法理解"这几条从同一张表读不同列，原因相同"。把变体重新聚类意味着要重新解析每个 entry 的 text，规范化 tree（去除别名、排序 AND 谓词、识别列集超集），然后重新做 fingerprint。pg_stat_statements 交给你的是原始的、碎片化的 shape；将它们重组回逻辑查询是一个它不具备的层。

下游重新解析之所以可行，是因为归一化只是看起来把信息扔掉了。jumble 只去掉一种东西——常量值（= 42 变成 = $1），而把所有结构留在了 query text 中：别名、列列表、AND/OR 树、LIMIT、join 顺序。这些结构正是一个 canonicalizer 所需要的全部信息，让它能判断 WHERE a = $1 AND b = $2 和 WHERE b = $1 AND a = $2 是同一个谓词，或者 c.id 和 id 是同一列。这个扩展对常量过度归一化，对结构却又归一化不足。

但有一件事确实丢失了：任何被 evict（驱逐） 掉的东西。canonicalizer 只能看到当前视图中存在的行，因此如果你的 ORM 已经淹没了 hash table，dealloc 丢掉了尾部，那就没什么东西可以去做 fingerprint 了。先把基数控制住：提高 pg_stat_statements.max、升级到 PG 18、或者切换到 array binding（详见下一节），否则你就只是在给碰巧存活下来的那几行做 fingerprint，而不是给真正的负载。

IN-list 特殊情况及其 PG 18 修复

有一个 Postgres 历来处理不好的结构性变体：常量列表。

SELECT * FROM orders WHERE id IN (1, 2, 3);
SELECT * FROM orders WHERE id IN (1, 2, 3, 4);
SELECT * FROM orders WHERE id IN (1, 2, 3, 4, 5);

在 PostgreSQL 18 之前，上述每一个都是自己的 entry，因为列表长度改变了 parse tree。任何动态构建 IN 子句的应用——绝大多数应用都这么做——可以用一个 query shape 耗尽数千个 entry，并在此期间驱逐掉所有其他内容（关于驱逐详见下文）。

PostgreSQL 18 最终将它们合并了。上面三条语句，仅在列表长度上不同，现在落在同一个 entry 中：

query | SELECT * FROM orders WHERE id IN ($1 /*, ... */)
calls | 3

PostgreSQL 18：IN-list 被压缩。
仅在长度上不同的常量列表现在合并为一个 entry，显示为 IN ($1 /*, ... */)。它是无条件的，没有 GUC 来关闭。限制：它只对内联常量有效，因此那些将 IN ($1, $2, $3) 作为参数绑定的驱动，仍然会在每个不同长度下产生新 entry。

这是一项真正的改进，也是升级到 18 的一个好理由。但有两件事让它不是完整的答案。大多数生产集群仍然在 17 或更早版本上，IN-list 爆炸依然活得很好。而它所跳过的那些参数绑定驱动——JDBC 之流——往往是最严重的罪魁祸首：它们把 IN ($1, $2, $3) 作为 bind 参数发送，因此这些值在 parse tree 里从来就不是常量，没什么可供压缩。IN ($1,$2,$3) 和 IN ($1,$2,$3,$4) 仍然是不同的 entry，每个列表长度一个新 shape。

压缩功能在 PG 18 开发期间曾经短暂地受一个 GUC query_id_squash_values 控制。它在发布前被移除，因此现在该行为始终开启。

如果你用的是那些参数绑定的驱动，不管你跑什么 Postgres 版本都逃不掉，但有一个真正的修复方法，而且比 PG 18 的压缩更好，因为它在任何地方都能用。停止发送 IN-list，改为发送 array。把这样：

SELECT * FROM orders WHERE id IN ($1, $2, $3, ... $n); -- n 个参数，n 个不同的 shape

改写成这样：

SELECT * FROM orders WHERE id = ANY($1); -- 一个参数，一个 shape，永远如此

= ANY(array) 接收单个参数，一个 array 值，因此 parse tree 无论是 3 个元素还是 3000 个元素都完全一样。那就只有一个 queryid，在任何 Postgres 版本、任何驱动下都是如此——不管是否使用 prepared statement，因为 array 长度从来不是 jumble 所见结构的一部分。大多数驱动和 ORM 直接支持 array binding（setArray、ARRAY[...]、pgx 的 slice binding、ActiveRecord 的 where(id: array)），planner 用它做索引选择的方式也与 IN-list 很像。对于重度使用 ORM 的团队，这是保持 pg_stat_statements 可读性的最高杠杆手段。

首次看到的 text 被冻结

每个 entry 显示一个 query text，并且是第一个创建该 entry 的那个。不是最近的，不是最常见的，是第一个。在那之后，计数器随着每次匹配的执行不断增长，但磁盘上的 text 永远不会改变——至少在该 entry 被驱逐并重建之前不会。

大多数情况下这没什么问题，因为常量都被归一化为 $1。但一旦你的查询携带了注释，而且现代应用携带了大量注释，这就很不好了。sqlcommenter 和 marginalia 约定在每条查询上附加结构化的 key-value 上下文：

SELECT id, name FROM customers WHERE id = $1
/*application='checkout',controller='orders',action='show'*/

注释不是 parse tree 的一部分，所以它们不会改变 queryid。每次执行仍然映射到同一个 entry。但该 entry 上的 text 是第一次出现时的那个。这把注释标签分成了两类，而这种划分就是全部的故事：

标签类别 示例 pg_stat_statements 如何对待它
静态 （每次调用同一位置的值相同） application、controller、action、job、framework 存活。 首次看到的值具有代表性，因为该位置发出的每次调用都携带相同的值。你可以从 query text 中抓取并信赖它。
动态（每次请求一个不同值） traceparent、request_id、trace_id、tenant_id、user_id 丢失。 第一个请求的值被永久冻结在 text 中，此后每个请求的值都被悄悄丢弃。

第二行就是 pg_stat_statements 永远不能作为 APM 或 tracing 工具的 join target 的原因。你无法问它"显示给我 14:32 超时的 trace 中的查询"，因为它只保留了一个 traceparent，它见到的第一个，而扔掉了剩下的。计数器是总和，总和没有地方记录哪个请求贡献了什么。如果你需要动态标签，你需要一个与扩展并行运行的 per-execution capture 路径（auto_explain，或基于 hook 的 harvester），而不是扩展本身。

在 pg_stat_statements 的 text 中出现一个 traceparent 是一个警告信号，而不是一种功能：一个 per-request 值率先到达了 entry，现在被冻结在那里，仿佛它是静态上下文。如果你从这些 text 中抓取标签来构建目录，请丢弃那些形状看起来像 hex ID 的。

均值会在你面前撒谎

这是让最多人掉坑的限制，因为那些数字看起来太可信了。

每个计数器都是自上次 reset 以来的累积值。扩展内部根本没有时间维度。视图是 accumulated running total 的一个快照，这带来了两个相互助长的问题。

没有内置历史。 假设你想知道这周哪些查询变慢了。最直观的做法是读 mean_exec_time，而这恰恰是出错的地方。这个数字是自上次 reset 以来所有时间的平均值，因此在一个已经运行了几个月的集群上，它把一个冷缓存的周一早晨、夜间批处理作业、以及一个安静的周日融合成一个数字，而这个数字无法描述任何真实的时间点。要得到一个"本周"的数字，你必须自己做簿记工作：按时间表给视图拍快照，把每次快照保存在一个表里，然后用其中两次做减法。过去一小时的均值就是 (total_exec_time_now - total_exec_time_then) / (calls_now - calls_then)。视图给你的是一个 running total；把它转化为 rate 是你的事。

这个减法操作比看起来更不可靠。它隐含着一个假设："now"的计数器是从"then"的计数器接续的，它们只增不减。大多数情况下这是对的，但不是总是。驱逐和 reset（这两者在第二部分中都有涉及）会打破这个假设；一个真正值得信赖的快照 diff 必须处理三种情况：

  • 该 entry 被驱逐并重建了。 如果一个查询从表中消失，后来又再次运行，它会带着归零的计数器回来。此时 total_exec_time_now 小于 total_exec_time_then，减法给出了一个负的增量。不要把它解读为"查询变快了"。把它解读为"这个窗口对这个 queryid 无效"，因为该 entry 的历史被截断了。
  • 在两个快照之间发生了全局 reset。 有人运行了 pg_stat_statements_reset()，或部署脚本执行了它。每一行的"now"都小于"then"。这种情况很好抓：将 pg_stat_statements_info.stats_reset 与你较早快照的时间比较，如果 reset 时间更新，那么整个窗口跨过了 reset，整个 diff 都作废。
  • queryid 只出现在一侧。 一个在"then"中存在但在"now"中缺失的查询，要么被驱逐了，要么它的表被删掉并重建了（新 OID，新 id）。一个在"now"中存在但"then"中没有的查询，要么是新的，要么是重建的。用 full outer join 连接两次快照，把两侧不匹配的行当作事件，而不是当做可以被减去的零。

PostgreSQL 17 增加了一个更干净的 per-entry 守卫：每行携带 stats_since，即 entry 被创建或重创建的时间。如果一行的 stats_since 比你较早快照的时间还要新，说明它的计数器在你背后被复位了，不管减法算出来是什么值，都要丢弃这个窗口。

PG 17 之前，全局 stats_reset 是你唯一内置的信号，而 per-entry 驱逐只有通过"计数器倒退"这个技巧才能察觉。裸公式是正确的；监控层围绕着它的，大部分就是这个记账工作；跳过这一步，就是 homemade dashboard 最终报告不可能的负延迟的原因。

均值掩盖了分布。 即使在一个窗口内，扩展也只对每个 shape 保留四个数字：执行时间的 min、max、mean 和 stddev。它是在运行中构建这些值的：每次执行折叠进入 running aggregate，然后丢弃时间数据，因此没有直方图，没有百分位数，没有 per-call 记录可以回溯。一个在 99% 时间运行 1ms、在另外 1% 时间运行 2 秒的查询，其 mean_exec_time 大约在 21ms 左右——这个数字不符合任何一次实际执行，并且隐藏了那个正在疯狂 paging 你的 on-call 的 p99。双峰延迟——一种真实的性能问题的常见形态——就这样消失在均值和标准差之中。这个扩展可以告诉你一个查询在平均意义上是慢的，但不能告诉你它有时是灾难性的慢，而后者通常是更危险的情况。

均值就是 total_exec_time / calls，但扩展（以及 stddev 背后的方差）是通过 Welford 在线算法维护的：每次执行折叠进入 running mean 和 sum-of-squares，然后丢弃其时间数据。最后只留下一个均值和一个标准差，永远不会有百分位数，因为没有保留任何 sample 可以做排序。

如果你想要百分位数或延迟时间线，这是错误的工具，对它查询再多次也没用。它在写入那一行的时候就已经把分布丢弃了。

结语

这就是故事的前半部分：pg_stat_statements 告诉你的一切，以及它悄悄扭曲自己报告内容的方式。一个逻辑查询被碎片化成数百个 shape，text 在初见时被冻结，整个分布被压平成一个单一的均值。

另一半是它从不记录的东西：它悄悄驱逐的 entry、可以一笔勾销的 query text、它看不到的执行计划，以及它不知道其存在的 replica。那是第二部分的内容，也会回到我们开头的问题：这究竟是 Postgres 缺失的 query store，还是你用来搭建一个 query store 的地基？
