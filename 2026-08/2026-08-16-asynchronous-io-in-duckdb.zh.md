# DuckDB 中的异步 I/O：工作、线程、再工作

如果无法快速读入数据，那么数据库系统中的查询算子再快也无济于事。然而，在 DuckDB 历史的大部分时期，我们通过尽早剪枝数据，在很大程度上避开了这个问题。通过下推过滤条件和投影，我们可以确保只读取实际需要的数据。

这种方式尤其有效，因为 DuckDB 过去主要在本地运行，其主要用例是作为一个快速响应的数据库引擎，直接查询机器 SSD 上的数据。我们可以将数据拆分为多个分区，例如 Parquet 文件的行组或 CSV 文件的固定大小缓冲区，并以低延迟和高带宽加载它们。因此，主要瓶颈出现在其他地方：子查询、连接、聚合等。实际的数据访问路径获得的关注较少，因为同步访问完全适合这种用例。

一如往常，情况发生了变化。我们意识到，DuckDB 的架构非常适合查询远程存储的大规模数据集，例如数据湖（如 [DuckLake](https://ducklake.select/)）。从[今年 5 月](https://duckdb.org/2026/05/12/quack-remote-protocol)起，我们甚至可以使用 [Quack 协议](https://duckdb.org/quack)将 DuckDB 作为服务器运行。因此，最初关于数据文件位于本地 SSD 上的预期如今并非总能成立。

这些变化带来的实际影响是，当前许多 DuckDB 部署都需要将文件从远程存储传输到真正处理它们的机器上。例如，对于数据湖，一种典型的部署方式是把数据存储在 S3 等 blob 存储中，并在同一区域内的一台 EC2 机器上处理。在这种部署中，延迟和带宽发挥着重要得多的作用。如果我们无法发出足够多的并发请求来利用可用的网络带宽，性能就可能急剧下降，线程会把大量时间花在等待远程读取上，而不是处理数据。

举个例子，让我们考虑对一个远程 Parquet 文件执行的简单查询。为简单起见，假设只有一个线程在执行。

```sql
FROM read_parquet('s3://bucket/file.parquet');
```

一次 Parquet 扫描会被划分为基于行组的作业，每个作业包含一个或多个发出字节范围请求的获取任务。使用同步 I/O 时，工作线程会被阻塞，等待数据到达机器，然后才能执行解码、聚合等实际工作。下图直观展示了这一过程：线程在等待读取完成期间被阻塞，无法执行任何工作。

![同步读取](../../assets/duckdb-asynchronous-io/sync-light.svg)
![同步读取](../../assets/duckdb-asynchronous-io/sync-dark.svg)
*同步读取*

为了解决这个问题，我们一直在 DuckDB 中实现异步 I/O 流水线。目前，它们已针对 Parquet 和未压缩、可定位的 UTF-8 CSV 文件实现；对 DuckDB 原生格式和 JSON 等其他格式的支持仍有待加入。在本文余下部分，我们将简单说明 DuckDB 中异步 I/O 的实现方式，并提供 Parquet 和 CSV 文件的基准测试结果。

> 如果你想现在试用异步 I/O，可以使用 [DuckDB 的 v2.0.0-dev 预览构建](https://duckdb.org/install/preview)。
> 从[秋季](https://duckdb.org/release_calendar)发布的下一个 DuckDB 主要版本 v2.0 起，将默认使用异步 I/O。

## 异步 I/O

异步 I/O 的概念相当简单：我们应该能够启动一项 I/O 操作，而不阻塞发起请求的工作线程。将这一概念应用于前面的 Parquet 示例，同一幅图会变成下面这样：

![异步读取](../../assets/duckdb-asynchronous-io/async-light.svg)
![异步读取](../../assets/duckdb-asynchronous-io/async-dark.svg)
*异步读取*

在这个示例中，我们有两个 `ASYNC` 线程和一个常规工作线程。`ASYNC` 线程在工作线程解码数据的同时，让_获取任务_保持在途状态。在最初的预热阶段，扫描任务会停放，从而让工作线程可以自由运行流水线中的其他任务。第一个作业就绪后，获取和解码便可以重叠进行。

在 DuckDB 中，我们实现了类似的机制。我们有[两个独立的线程池](https://github.com/duckdb/duckdb/blob/34f2a32f08e9c454205f1ce45a4e9fa38adf4f53/src/include/duckdb/common/enums/task_scheduler_type.hpp#L15-L17)：

* `REGULAR` —— 这个池包含我们的工作线程（默认情况下，每个可用的 CPU 线程对应一个）。它们负责执行真正的工作，如解码、连接和聚合。它们优先处理常规工作，但空闲时也可以执行 I/O 任务。
* `ASYNC` —— 用于异步任务的线程池，主要处理阻塞式 I/O。

之所以设置这两个不同的池，主要是因为在执行远程 I/O 时，这些线程几乎可能一直处于阻塞状态，例如等待 HTTP 响应，因此 CPU 利用率很低。正因如此，`ASYNC` 工作线程的数量远多于系统线程，默认设置为 `4 * system threads`，总数上限为 256。

让尽可能多的 `ASYNC` 线程保持忙碌至关重要。为确保这一点，我们采用预读策略，而不是按需发起读取。这意味着要提前调度获取任务，超前于常规工作线程当前所需的工作。

需要注意的一点是，预读通过占用内存来换取吞吐量。如果解码速度慢而网络速度快，预取的数据可能会积累并导致内存不足问题。为缓解这一问题，我们还实现了异步内存治理。后续各节将更详细地解释预读和内存治理。

### 预读队列

预读的思路也很直接。我们不是在常规工作线程恰好需要数据的那一刻才启动读取，而是为更靠后的工作提前调度获取任务。当一个常规工作线程解码当前作业时，ASYNC 线程已经在拉取后续作业的数据。目标是让足够多的获取任务保持在途状态，以掩盖远程存储的延迟。

作业是可以独立调度和处理的工作单元，并且会因底层文件格式而异。对于 Parquet 文件，一个作业就是一个文件中的一个行组。对于 CSV 文件，一个作业则是一个通常覆盖文件内固定字节范围的扫描边界。

根据查询投影、过滤条件下推、物理列位置，以及哪些相邻字节范围可以合并，一个 Parquet 作业可能会拆分为多个获取任务。下图中的两个获取任务仅用于说明，因为其确切的分组和大小取决于文件和查询。

对于 CSV 文件，我们无法获得像 Parquet 文件那样细粒度的信息。如果作业的起始缓冲区尚未位于内存中，它的获取任务会加载该缓冲区；当扫描边界到达该缓冲区末尾时，还会加载后续缓冲区（例如，用于处理跨两个缓冲区拆分的行）。

![作业](../../assets/duckdb-asynchronous-io/jobs-light.svg)
![作业](../../assets/duckdb-asynchronous-io/jobs-dark.svg)
*作业*

填充队列不需要专用的生产者线程。任何前来寻找扫描工作的常规工作线程，都会先在允许的范围内尽可能补满队列。限制由用户指定的槽位数或内存预算决定。如果存在空间，就会创建一个作业及其获取任务。获取任务会立即在 `ASYNC` 池上调度，而作业则按照批次顺序进入预读队列。

`ASYNC` 线程执行各个获取任务时，不受作业队列认领顺序的约束。同一作业的获取任务可以并发运行，但不保证会以任何特定方式分配给 `ASYNC` 线程。一个作业的所有获取任务共享一个倒计数器，使其归零的那个获取任务会完成该作业的 I/O。

工作线程会认领队列中最早的作业并检查该倒计数器。如果 I/O 已完成，工作线程就开始解码该作业。否则，它会停放扫描任务，并可以自由运行流水线中的其他任务。最后一个获取任务随后会解除扫描任务的阻塞，而该扫描任务可能在任意常规工作线程上恢复执行。

认领作业还会立即释放一个队列槽位，使任何正在寻找扫描工作的常规工作线程都可以在队尾生成一个替代作业。下图描绘了这一循环：

![预读循环](../../assets/duckdb-asynchronous-io/cycle-light.svg)
![预读循环](../../assets/duckdb-asynchronous-io/cycle-dark.svg)
*预读循环*

### 内存管理

让更多获取任务保持在途状态会消耗更多内存。为了确定预算并避免内存不足问题，我们引入了 `read_ahead_depth` 配置选项。它可以取三类值：

* `-1`（默认值）：深度不受限，但受内存约束。
* `N > 0`：最多提前 `N` 个作业，不设内存预算。
* `0`：关闭预读，每个扫描任务只为自己的作业调度 I/O。

要进行配置，请使用 `SET` 子句，例如：

```sql
SET read_ahead_depth = 5;
```

在默认模式下，预算由临时内存管理器协商；这个管理器也负责在并发连接、排序和窗口算子之间分配内存。当内存压力很大时，例如某个算子正在使用大量内存，队列预留量可能会立即超出预算。实际上，这意味着队列一次只允许一个作业，扫描的行为将接近同步扫描。

当内存密集型算子完成后，内存管理器就有更多预算可供分配，队列也会再次填满。

## 基准测试

当同步请求的延迟使我们无法利用可用的远程带宽时，异步 I/O 应该会产生最大的效果。为了衡量这种效果，我们运行了 [SF100 规模的 TPC-H 查询 6](https://duckdb.org/docs/current/core_extensions/tpch)，数据存放在 S3 上，并将结果与最新稳定版本 [DuckDB v1.5.5](https://duckdb.org/2026/07/22/announcing-duckdb-155)进行了比较。在 Parquet 和 CSV 基准测试中，SF100 数据集的每张表都写入单个文件，其中 `lineitem` 表包含 600,037,902 行。

计算环境使用的是一台 EC2 [r7i.16xlarge](http://instances.vantage.sh/aws/ec2/r7i.16xlarge) 机器（64 个 vCPU 和 512 GB 内存），机器和存放数据的 S3 存储桶位于同一区域。我们将查询执行五次，并报告平均执行时间。文件从不缓存（即 `SET enable_external_file_cache = false;`），这意味着每次执行都直接从 S3 读取数据。

### Parquet

Parquet 文件约为 22 GB，包含约 4,880 个行组，每个行组约有 122,880 行。使用异步 I/O 后，平均运行时间从 8.230 秒降至 2.844 秒，使查询速度提升近 3 倍。

| 版本                          | Q6 运行时间 |
| ----------------------------- | ----------: |
| v1.5.5（同步）                |     8.230 s |
| v2.0.0-dev（异步 I/O）        |     2.844 s |

下面还展示了查询执行过程中的网络吞吐量：

![网络吞吐量](../../assets/duckdb-asynchronous-io/q6_network_throughput_3way-light.svg)
![网络吞吐量](../../assets/duckdb-asynchronous-io/q6_network_throughput_3way-dark.svg)
*网络吞吐量*

在图中，我们运行了 DuckDB v1.5.5 和 DuckDB v2.0.0-dev 的两个变体。其中一个的预读深度由内存治理器决定；另一个则针对这台机器进行调优，将预读上限设为 64 个在途作业，并调整 I/O 设置（`SET async_threads = 48; SET http_retries = 8; SET http_retry_wait_ms = 50; SET http_retry_backoff = 2`）。可以看到，v2.0.0-dev 对可用带宽的利用效率高得多，它接近网络上限，并在若干时刻达到该上限。调优版本则更进一步。凭借数量更少、活跃度更高的连接和低成本重试，吞吐量方差降至最低，25 Gbit/s 的网络几乎始终处于满载状态。其查询时间为 2.227 秒，比未经调优的 v2.0.0-dev 运行时间缩短了 21.7%，并且比 DuckDB v1.5.5 快约 3.7 倍。相比之下，v1.5.5 一直在 5 Gbit/s 左右，因为它的同步读取没有让足够多的请求保持在途状态，无法跑满网络。

另一个值得注意的细节是，在所有实验中，首次出现网络流量上升之前都会经过几百毫秒，而主要数据传输开始之前又会经过几百毫秒。第一个空档是打开 DuckDB 连接、执行首次 TLS 握手以及打开文件所需的时间。流量上升对应于下载文件页脚，而第二个空档则来自执行查询之前对页脚信息的处理。我们认为，在 v2.0 发布之前，这一领域还可以进一步研究和优化。

> 我们每隔 50 ms 对 NIC 的接收字节计数器采样一次，并根据相邻样本之间的字节变化计算吞吐量。我们分别使用 DuckDB 全文件读取和 [`s5cmd` 工具](https://github.com/peak/s5cmd)，独立确认了该机器能够以 25 Gbit/s 的速率访问网络。

#### 本地磁盘

远程存储是异步 I/O 的主要目标，但本地冷读取提供了有用的对照。为了测量它们，我们对 SF100 Parquet 文件运行了 TPC-H 查询 6，这一次文件存放在一台 MacBook Pro（Apple M4 Max、14 核和 36 GB 内存）的本地磁盘上。由于异步 I/O 在本地磁盘上的收益来自冷读取，我们在每次运行之间清除了操作系统缓存（使用 macOS 的 `purge` 命令），以确保每次执行确实都从磁盘读取文件。

| 版本                          | Q6 运行时间 |
| ----------------------------- | ----------: |
| v1.5.5（同步）                |     1.321 s |
| v2.0.0-dev（异步 I/O）        |     0.883 s |

可以看到，对于冷运行，异步 I/O 约快 1.5 倍，运行时间缩短约 33%。性能差异远小于上文所示的情形，因为 SSD 的延迟远低于 EC2/S3 网络，带宽也远高于后者。对于热运行，这种差异可以忽略不计，因为如果数据得到正确缓存，就不会发生磁盘访问。

#### 小文件

分区数据集是这里尤其相关的用例，因为分区很容易使数据分散到大量小文件中。为了观察异步 I/O 在这种部署下的表现，我们还使用相同的 TPC-H SF100 数据集进行了一次 Parquet 测试。我们没有使用单个文件，而是生成了 976 个文件，每个文件包含五个行组。每个文件约有 615,000 行，大小约为 22 MB。

| 版本                          | Q6 运行时间 |
| ----------------------------- | ----------: |
| v1.5.5（同步）                |     9.344 s |
| v2.0.0-dev（异步 I/O）        |     2.945 s |

可以看到，v2.0.0-dev 在这里带来的性能提升与单文件基准测试相近，运行速度约快 3 倍。这表明，预读也可以跨多个文件实现并行化，而不会因打开文件或获取其页脚而遭遇瓶颈。

#### 大行组

我们还想观察另一个极端：当一个 Parquet 文件仅包含少数几个非常大的行组时会发生什么。在这项实验中，我们将同一张 TPC-H SF100 `lineitem` 表生成为六个单文件版本，仅改变请求的行组（RG）大小，并使用 DuckDB v2.0.0-dev 运行 Q6。下表报告了每个版本的运行时间。

| 每个 RG 的行数 | RG 数量 | RG 近似大小（MB） | 文件总大小（MB） |    时间 |
| --------------: | ------: | ----------------: | ----------------: | ------: |
|         122,880 |   4,886 |             ~4 MB |        ~21,600 MB |  2.74 s |
|       1,966,080 |     306 |            ~70 MB |        ~21,400 MB |  2.11 s |
|       9,375,593 |      64 |           ~320 MB |        ~20,500 MB |  2.27 s |
|      62,914,560 |      10 |         ~1,500 MB |        ~14,700 MB |  3.69 s |
|     150,009,476 |       4 |         ~3,200 MB |        ~12,800 MB |  8.01 s |
|     600,037,902 |       1 |        ~12,300 MB |        ~12,300 MB | 25.26 s |

起初，较大的行组会缩短查询时间。随着行组大小增加，请求延迟被摊销到大得多的数据传输上。然而，超过某个临界点后，可用的并行度开始下降。行组是 DuckDB 进行 Parquet 扫描并行化的单位，因此理想情况下，一次扫描应该为每个系统线程提供至少一个行组。在这台 64 vCPU 的机器上，包含 64 个行组的版本恰好做到了这一点，并在 2.27 秒内完成；而包含 306 个行组的版本最快，用时 2.11 秒。

然而，当行组数少于线程数时，我们就会损失并行度，也无法再跑满网络。对于 Q6，投影和列的物理位置会使每个行组产生两个获取请求。因此，四个行组只能提供大约八个并发 S3 流，使运行时间增至 8.01 秒。在最大的配置中，文件只包含一个行组，其 I/O 实际上被缩减为两个巨大的数据流，将运行时间推高至 25.26 秒。尽管更好的压缩使该文件的大小仅略高于包含 4,886 个行组版本的一半，仍然会出现这种情况。在这个例子中，较小行组所需的额外带宽，其代价低于使用超大行组所损失的并行度。

#### 并发查询

当多个查询同时运行时，这种效果会更加明显。在这项实验中，我们使用单个 DuckDB 实例，针对 S3 上的同一个 SF100 Parquet 数据集并发运行 TPC-H 查询 1、6、9 和 18。我们之所以选择这些查询，是因为它们涵盖了扫描、聚合和连接的组合，并具有不同的 CPU 和内存需求。我们分别使用默认内存配置以及 16 GB 和 8 GB 的内存限制重复了实验。总运行时间是指全部四个查询完成前的墙钟时间。我们报告平均和峰值 CPU 利用率（使用的核心数）、峰值带宽（bw.）以及峰值常驻集大小（RSS）。

| 版本       | 内存限制 | 运行时间 | 平均 CPU | 峰值 CPU |    峰值带宽 | 峰值 RSS |
| ---------- | -------: | -------: | -------: | -------: | ----------: | -------: |
| v1.5.5     |     默认 |   35.8 s |      5.9 |     35.7 | 10.7 Gbit/s |  14.5 GB |
| v2.0.0-dev |     默认 |   15.6 s |     48.1 |     64.0 | 24.9 Gbit/s |  20.1 GB |
| v1.5.5     |    16 GB |   35.6 s |      6.1 |     25.7 | 17.4 Gbit/s |  14.1 GB |
| v2.0.0-dev |    16 GB |   22.7 s |     35.2 |     63.4 | 24.8 Gbit/s |  15.7 GB |
| v1.5.5     |     8 GB |   35.9 s |      6.9 |     38.8 | 16.8 Gbit/s |  10.4 GB |
| v2.0.0-dev |     8 GB |   24.2 s |     30.3 |     63.7 | 25.0 Gbit/s |  11.5 GB |

使用默认内存配置时，DuckDB v1.5.5 平均只能让 64 个核心中的约 6 个保持忙碌。换句话说，机器约 90% 的资源处于空闲状态，等待同步 S3 读取。另一方面，DuckDB v2.0.0-dev 平均有 48 个核心保持忙碌，峰值时全部 64 个核心都被使用，并且跑满了 25 Gbit/s 的网络。因此，全部四个查询的完成时间不到原来的一半。

内存结果也很有意思。随着我们降低限制，内存治理器会减少预读积压，而 Q18 中的内存密集型算子则可以溢写到磁盘。这使 DuckDB v2.0.0-dev 的 DuckDB 进程峰值物理内存用量（即 RSS）从默认配置下的 20.1 GB，降至 16 GB 限制下的 15.7 GB 和 8 GB 限制下的 11.5 GB。额外的溢写和减少的预读也会降低平均 CPU 利用率并增加运行时间，但在这两种情况下，v2.0.0-dev 仍然能够跑满网络，并且依旧显著快于 v1.5.5。

> 有人可能会注意到，8 GB 配置的 RSS 峰值仍然达到了 11.5 GB。这是因为 [jemalloc](https://duckdb.org/docs/current/internals/jemalloc) 会让最近释放的页面在大约一秒内保持常驻，以便重复使用。这部分内存不再计入 DuckDB 内存管理器的统计，而 v1.5.5 也表现出相同的分配器行为。

### CSV

对 CSV 文件的效果更大。CSV 文件大小为 80.89 GB，异步 I/O 将平均运行时间从 878 秒缩短至仅 45 秒，使查询速度提升近 20 倍。CSV 面向行，因此扫描会传输多得多的数据，并执行固定大小的缓冲区读取，这使并发远程读取尤为有价值。

| 版本                          | Q6 运行时间 |
| ----------------------------- | ----------: |
| v1.5.5（同步）                |   877.563 s |
| v2.0.0-dev（异步 I/O）        |    45.264 s |

与其他实验一样，我们使用了默认的、由内存治理的预读深度，因此这次运行并未经过调优，无法让 25 Gbit/s 的网络平均保持满载。

## 结论

在本文中，我们介绍了近期针对 Parquet 和 CSV 文件开展的异步 I/O 工作。其大部分收益来自访问远程数据，但本地冷读取也能受益，只是程度较小。接下来，我们计划为 JSON 和 DuckDB 原生文件添加异步读取，因为它们是另外两种与 DuckDB 核心最相关的格式。位于树外扩展中的格式目前尚未列入路线图。我们还将研究 Linux 的异步 I/O 接口 [`io_uring`](https://man7.org/linux/man-pages/man7/io_uring.7.html)，它可以减少系统调用开销以及因 I/O 而阻塞的线程数量。如果实践证明它确实有益，我们会将其集成到 DuckDB 中。需要注意的一点是，只要底层数据格式是 Parquet（或者，如果你足够大胆，也可以是 CSV），DuckDB 支持的任何数据湖解决方案现在都已经可以自动受益于异步 I/O。
