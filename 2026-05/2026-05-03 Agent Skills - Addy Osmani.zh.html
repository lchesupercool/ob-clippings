特工技能

来源：译文

人工智能编码代理采用最短路径完成任务，这通常意味着跳过使软件大规模可靠的规范、测试和审查。代理技能...

摘要

这篇文章的核心是：AI编码代理默认会走“最快完成任务”的路线，容易跳过规范、测试、审查、验证证据和范围控制；代理技能试图把高级工程师的工程学科编码变成代理必须执行的工作流程。关键设计包括：流程胜于散文、反合理化表格、验证作为退出标准、渐进披露，以及严格的范围纪律。

正文

高级工程师的工作主要是差异中没有出现的部分。规格。测试。评论。范围纪律。无法核实的拒绝发货。 AI 编码代理默认跳过这些部分。特工技能是我尝试让它们不再是可选的。

任何人工智能编码代理的默认行为都是采取最短路径“完成”。询问一个功能，它就会写出该功能。它不会询问您是否有规范，在实施之前编写测试，考虑更改是否跨越信任边界，或者检查 PR 对于审阅者来说是什么样子。它生成代码，宣布胜利，然后继续前进。

这是每个高级工程师在其职业生涯中都在学习避免的相同故障模式。任何任务的高级版本都包括没有出现在 diff 中的工作：提出假设、编写规范、将工作分解为可审查的块、选择无聊的设计、留下结果正确的证据、确定更改的大小以便人们可以实际审查它。这些步骤是大规模交付可靠软件的工程师与推送损坏代码的工程师的主要区别。

特工们跳过这些步骤的原因与任何初级人员都会做的一样。他们是看不见的。奖励信号指向“任务完成”而不是“任务完成且设计文档存在”。所以我们必须重新用螺栓固定高级工程师的脚手架。

代理技能 是我对该脚手架的尝试。它刚刚突破了 26K 星，所以显然我并不是唯一一个想要它的人。 这篇文章是自述文件没有完全涵盖的部分：为什么每个设计选择存在，它如何映射到标准 SDLC 和 Google 发布的工程实践，以及即使您从未安装任何技能，您也应该从项目中窃取什么。

什么是“技能”

“技能”这个词在克劳德密码/人类词汇中做了很多工作，它有助于精确。技能是一个带有 frontmatter 的 markdown 文件，当情况需要时，它会被注入到代理的上下文中。介于系统提示片段和操作手册之间。

技能不是参考文档。它不是“你应该了解的有关测试的一切”。这是一个工作流程：代理遵循的一系列步骤，带有产生证据的检查点，以定义的退出标准结束。

这种区别就是整个游戏。如果您将一篇关于测试最佳实践的 2,000 字文章放入代理的上下文中，代理会阅读它，生成看起来合理的文本，并跳过实际测试。如果您在那里放置一个“工作流程”（首先编写失败的测试，运行它，观察它失败，编写要通过的最少代码，观察它通过，重构），那么代理有事情要做，并且您有一些事情需要验证。

**过程胜于散文。工作流程超过参考。具有退出标准的步骤优于没有退出标准的文章。 ** 这一单一区别将有用的技能与漂亮的 Markdown 文件区分开来。它还解释了为什么如此多的“人工智能规则”存储库最终在实践中无所作为。规则就是论文。

SDLC 技能编码

存储库中的 20 种技能围绕六个生命周期阶段进行组织，其中七个斜线命令位于顶部。定义 (/spec) 是您决定实际构建的内容的地方。计划（/plan）将工作分解。 Build (/build) 在垂直切片中实现它。验证（/test）证明它有效。回顾（/review）发现漏掉的东西。船舶（/ship）将其安全地送到用户手中。 /code-simplify 位于整个事物的底部。

这并非巧合。每个正常运行的工程组织都运行相同的 SDLC，只是词汇不同。谷歌称之为设计文档→审查→实施→可读性审查→启动清单。亚马逊将其称为“倒推备忘录”和“提高标准”。每个健康的团队都有这个循环的某个版本。

人工智能编码代理的新功能是大多数代理默认跳过这些阶段中的大部分。你要求一个功能，你得到一个实现，但规范、计划、测试、审查和启动清单都没有发生。 技能推动代理经历高级工程师强迫自己经历的相同阶段，因为在没有技能的情况下交付代码就是产生事件的方式。

一个复杂的功能可能会依次激活十一项技能。一个小错误修复可能会使用三个。路由器（using-agent-skills）决定哪一个适用。关键是工作流程会扩展到实际范围，而不是假定范围。

开展工作的五个原则

该项目中的五个设计决策是承重决策。系统的其余部分都遵循它们。

1. 过程重于散文

已经覆盖了。工作流程可由代理执行；论文则不然。对于人类团队来说也是如此。如果你的团队手册有 200 页，那么没有人会在时间压力下阅读它。如果它是一小组带有检查点的工作流程，那么人们实际上会运行它们。

2.反合理化表

这是该项目中最独特的设计决策，也是我最希望其他团队借鉴的设计决策。

每项技能都包含一个代理（或疲惫的工程师）可能用来跳过工作流程的常见借口表，并附有书面反驳。一些接近原文的例子：

  • “这个任务太简单了，不需要规范。” → 验收标准仍然适用。五行就好了。零线不是。
  • “我稍后再写测试。” → 后来是承重词。没有以后了。首先编写失败的测试。
  • “测试通过，发货。” → 通过测试是证据，而不是证据。你检查过运行时间吗？您是否验证了用户可见的行为？人类读过差异吗？

这样做的原因是法学硕士非常擅长合理化。他们将生成一个听起来合理的段落，解释为什么“这个特定的”任务不需要规范，或者为什么“这个特定的”更改可以在不进行审查的情况下合并。 反合理化表是对代理人尚未说出的谎言的预先写好的反驳。

这种模式对于人类团队来说同样有效。大多数工程的衰退并不是任何人选择做不好的工作。人们接受了看似合理的理由，跳过他们不想做的部分。一个写下其反合理化的团队是一个拥有较少反合理化的团队。

3. 验证是不可协商的

每项技能都以具体的证据为终结。测试通过。构建输出是干净的。运行时跟踪显示了预期的行为。审稿人签字。 “看起来正确”永远是不够的。

这与 Anthropic 的harness从故障中恢复的原理相同，这使得 Cursor 的 planner/worker/judge 分割实际上捕获了错误，这使得任何长时间运行的代理都可以恢复。代理是一个生成器。您需要一个单独的信号来表明工作已完成。技能将这一信号融入到每个工作流程中。

4. 渐进式披露

不要在课程开始时将所有二十个技能加载到上下文中。根据阶段激活它们。一个小的元技能 (using-agent-skills) 充当路由器，决定哪个技能适用于当前任务。

这是在技能粒度上应用的利用工程课程。加载到上下文中的每个令牌都会降低某处的性能，因此您加载相关内容并将其余内容保留在磁盘上。 渐进式披露是如何在不毒害井的情况下将 20 种技能库放入 5K 代币槽中的方法。

5. 范围规则

元技能编码了一个不可协商的内容，如果可以的话，我会把它钉在每个代理身上：“只触摸你被要求触摸的东西。”不要重构相邻的系统。不要删除您不完全理解的代码。不要忽略 TODO 并决定重写文件。

这听起来很明显，直到您看到代理决定修复一个错误需要现代化三个不相关的文件。 范围纪律是决定代理的 PR 是否可合并或必须解除的最大决定因素。 这也是最清晰地映射到 Google 代码审查规范的原则，其中审查者将阻止 PR 做不止一件事。

谷歌 DNA

这些技能充满了谷歌软件工程和谷歌公共工程文化的实践。这是故意的。谷歌规模的软件工作的大部分内容都是记录在案且公开的，而这“正是”代理最有可能跳过的部分。

哪种技能编码哪种实践的部分地图：

  • api-and-interface-design 中的 海鲁姆定律。 API 的每个可观察行为最终都会被某人依赖，因此在设计时要考虑到这一点。
  • test-driven-development 中的测试金字塔 (~80/15/5) 和碧昂丝规则。 “如果你喜欢它，你应该对它进行测试。”基础设施的变化不会发现错误；测试确实如此。
  • 测试中 DAMP 优于 DRY。 Google 的测试理念很明确，即测试代码应该像规范一样读起来，即使以一些重复为代价。过度抽象的测试是一种已知的反模式。
  • ~100 行 PR 大小，在 code-review-and-quality 中带有关键/Nit/可选/FYI 严重性标签。直接来自 Google 的代码审查规范。大公关不会得到审查；他们会被盖上橡皮图章。
  • code-simplification 中的 切斯特顿栅栏。在您了解某物为何放在那里之前，请勿将其移除。
  • git-workflow-and-versioning 中的 基于主干的开发和原子提交。
  • ci-cd-and-automation 中的左移和功能标志。尽早发现问题，将部署与发布分离。
  • deprecation-and-migration 中的 代码即责任。你保留的每一条线都必须永远保持，所以更喜欢较小的表面。

这些都不是新想法。 重点是，默认情况下，它们都不在代理中。 前沿模型在其训练数据中读取了短语“海鲁姆定律”，但在凌晨 3 点设计 API 时，它并不适用海鲁姆定律。技能是你确保它发挥作用的方式。

如何实际使用它

三种模式，大致增加承诺。

模式 1：通过市场安装。 如果您使用的是 Claude Code：

/plugin marketplace add addyosmani/agent-skills
/plugin install agent-skills@addy-agent-skills

您会收到斜杠命令（/spec、/plan、/build、/test、/review、/ship、/code-simplify），代理会根据上下文自动激活相关技能。这是我建议大多数人开始的道路。

模式 2：将 Markdown 放入您选择的工具中。 技能是带有 frontmatter 的普通 Markdown。游标用户将它们放在.cursor/rules/中。 Gemini CLI 有自己的安装路径。 Codex、Aider、Windsurf、OpenCode，任何接受系统提示的东西都可以读取它们。工具比下面的工作流程更重要。

模式 3：将它们作为规范来阅读。 即使您从未安装过任何东西，这些技能也是对人工智能代理的良好工程的书面描述。阅读 code-review-and-quality.md 并将五轴框架应用到您团队的审核流程中。阅读 test-driven-development.md 并用它来解决与初级学生的下一个“我们是否需要先编写测试”的争论。阅读元技能并为您自己的 AGENTS.md 窃取五个不可协商的内容。

第三种模式是我真正开始的地方。选择最接近您当前痛苦的四到五种技能。决定您想要实施哪些工作流程。然后安装运行时，或者推出您自己的运行时来执行强制操作。

即使你从未安装也可以窃取什么

无论你是否使用人工智能编码代理，我都会从该项目中窃取一些模式。

将反合理化作为团队实践。 写下你的团队告诉自己的谎言。 “我们将在发布后修复测试。” “对于设计文档来说，这个变化太小了。” “没关系，我们有监控。” 将每条内容与反驳配对。将其放入您的 AGENTS.md 或工程 wiki 中。它会节省你的争论，并且会赶上下一个疲倦的周五下午的捷径。

对于你在内部写的任何东西，流程重于散文。 如果你发现自己正在写一篇 2,000 字的文档，标题为“我们如何处理 X”，那么你已经写了参考材料。将其转换为带有检查点的工作流程。该文档缩减至 400 字，人们实际运行它。这既适用于入职指南和操作手册，也适用于座席技能。

将验证作为硬退出标准。 将“提供证据”作为每项任务的退出步骤。对于代理商，对于工程师，对于您自己。证据是证明工作已完成的一切：绿色测试运行、屏幕截图、日志、审核批准。没有它，任务就无法完成。 “看起来是对的”永远不会结束循环。

逐步披露任何规则手册。 不要编写 50 页的手册。写一个小路由器，根据情况指向正确的小章节。对于 AGENTS.md、运行手册、事件手册以及任何人在时间压力下会阅读的任何内容都是如此。

从元技能中提取的五个不可协商的内容，我明天将其放入任何 AGENTS.md 中：

  1. 构建前的表面假设。错误的假设是最常见的失败模式。
  2. 当需求发生冲突时停下来询问。别猜。
  3. 必要时进行反击。代理人（或工程师）不是一个唯唯诺诺的机器。
  4. 喜欢无聊、显而易见的解决方案。聪明是昂贵的。
  5. 只触摸要求您触摸的部分。

这是一种有价值的五行工程文化，您无需安装任何东西即可采用它。

这适合安全带的位置

从更广泛的角度来看，技能是代理利用工程的一层。线束是模型加上你围绕它构建的所有东西；技能是可重用的工作流程块，逐渐显示在系统提示中。它们与 AGENTS.md（滚动规则手册）、钩子（确定性执行层）、工具（代理可以采取的操作）和会话日志（持久内存）并存。每一层都有特定的工作。技能完成高级工程师的流程工作。

技能对于长时间运行的代理比对于聊天式的代理更重要，因为长时间的运行会放大每条捷径。在 10 分钟会话中跳过测试的代理会产生一个错误。在 30 小时的会话中跳过测试的代理会在运行结束时生成一个调试考古项目，当时没有人记得最初的意图是什么。 运行的时间越长，高级工程师的脚手架就越需要强制执行，而不是建议。

技能格式的可移植性也很重要。相同的 SKILL.md 文件适用于 Claude Code、Cursor（带规则）、Gemini CLI、Codex 以及接受系统提示内容的任何其他工具。工作流程编写一次，运行时就会强制执行。这就是 markdown-with-frontmatter 格式给你带来的东西，而定制的提示工程却没有。

结束

我最希望人们从这个项目中学到的东西，不仅仅是技能本身，是框架。

人工智能编码代理是非常有能力的初级工程师，对差异中没有出现的工作部分没有直觉。高级工程工作（提出假设、调整规模、编写规范、留下证据、拒绝合并无法审查的内容）正是代理会跳过的工作，除非你让其无法跳过。越来越多的工作是将这种纪律编码为代理无法说服自己放弃的东西。

技能是其中的一种形式。反合理化表。渐进式披露。过程胜于散文。验证作为承载退出标准。谷歌的做法已经行之有效，并且变得可移植。

您可以安装我的版本。你可以自己动手。 无论哪种方式，教训都是如此：工作中的高级工程师部分不再是可选的，即使工程师是模特。
