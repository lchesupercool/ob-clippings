# 数据湖到底是什么（以及为什么你可能并不需要它）

来源：[原文](https://thebuild.com/blog/2026/05/06/what-a-data-lake-actually-is-and-why-you-probably-dont-need-one/)

![](../../assets/data-lake-actually-is/data-lake-actually-is-01.png)

如果你的工程师告诉你需要一个数据湖，你应该稍微警惕一点。大多数构建数据湖的组织其实并不需要它们，而在真正构建了数据湖的组织中，也有相当一部分最终得到的是业内——毫无讽刺意味地——称为“数据沼泽”的东西。所以，在讨论数据湖是什么之前，让我先直白地说：正确答案通常是“还不到时候，也许永远都不需要”。有意思的问题是，“还不到时候”什么时候会变成“就是现在”。

要理解这一点，你必须明白，你实际上有三类彼此不同的数据系统，它们承担不同的工作。

**事务型数据库**是运行你的应用程序的东西。PostgreSQL、MySQL、SQL Server。它针对大量小规模读写进行了优化——订单被创建、库存被扣减、用户完成认证。Schema 很严格：每一列都有类型，每一行都符合表定义，每一个约束都会被强制执行。当正确性很重要且工作负载可预测时，这正是你想要的。

**数据仓库**是你做分析的地方。Redshift、Snowflake、BigQuery。它的工作负载正好相反：数量更少但规模大得多的查询，它们会扫描数十亿行并进行聚合。数据仓库是列式的、分布式的，并针对“上个季度销售情况如何，按地区和产品线拆分”这类问题进行了调优；这类问题会让事务型数据库苦不堪言。Schema 仍然严格——你把数据加载到具有已定义列的已定义表中。

**数据湖**是第三种东西。它是廉价对象存储——S3、GCS、Azure Blob——中的一堆文件，数据以它到达时的任意形态存在。来自供应商的 CSV。来自你应用程序的 JSON 事件流。从你的数据仓库导出的 Parquet 文件。日志文件。图片。也许还有一个两年没人看过的 PDF 目录。它的定义性属性是：存储层并不关心 schema。你是在*读取时*应用 schema，而不是在写入时。

最后这句话就是全部要点，所以值得多停留一下。数据仓库要求你在数据到达之前就承诺一个 schema。数据湖不要求。这比听起来要重要得多。它意味着你可以摄取那些你还不了解其形态的数据，来自你无法控制的来源，规模大到会让数据仓库变得昂贵——然后你可以稍后决定要问它什么问题，甚至可能是几年之后。

（不论好坏，这正是 Palantir 用来构建其整个业务的概念。）


### 为什么不直接用一个更大的 PostgreSQL？

PostgreSQL 是一个事务型数据库。它非常擅长扮演这个角色。它并没有针对扫描一整年的点击流事件来计算漏斗进行优化。你完全可以把几 TB 数据放进 PostgreSQL 并在上面跑分析，而且对许多公司来说，这在很长一段时间里都是正确答案。但一旦你超过了，比如说，十 TB 的分析型数据，或者每个查询要扫描数亿行，使 PostgreSQL 擅长 OLTP 的面向行的堆布局就开始与你作对。

有一些扩展和衍生项目可以改变这一点：用于分布式的 `citus`，用于列式存储的 `hydra`，面向分析形态的 PostgreSQL 方案 ParadeDB。它们都是很棒的选择。但到那时，你已经不再是在“把 PostgreSQL 当 PostgreSQL 使用”，而是开始把 PostgreSQL 当作其他东西的底座；于是，与专门构建的数据仓库相比，PostgreSQL 的优势就不再是一边倒了。


### 为什么不直接用 Redshift（或任何其他数据仓库）？

这个问题更有意思，因为 Redshift 确实是一个数据仓库，也确实能够处理分析工作负载。它不是完整答案的原因在于，数据仓库迫使你在数据进入时就对数据建模。如果你有一百个来源，产生高度异构的数据，那么在数据可查询*之前*，你就要花费巨大的工程精力编写 ETL 作业，把每个来源转换成数据仓库的 schema。

有两个后果。第一，任何你决定不加载的东西都会消失——或者至少会消失，除非你回到源头重新获取，而源头可能已经不存在，或者可能会向你收费。第二，schema 的每一次变化都要求重做 ETL。数据湖把这件事反过来：你永远保留原始的、未转换的数据，并按需转换。如果下个季度有人想问一个你现有数据仓库模型无法回答的问题，原始数据仍然在那里。


### 什么时候你真的需要一个数据湖

当以下一项或多项为真时，你需要一个数据湖：

- 你有**真正异构的来源**——日志、第三方 feed、抓取的数据、半结构化事件——它们并不能自然地适配数据仓库 schema。
- 你有**机器学习或数据科学工作负载**，它们需要原始的、未转换的数据，而不是你的 BI 团队构建出来的已建模子集。
- 你有**足够大的数据量**，以至于数据仓库存储成本变成一项真实的账目，而不是四舍五入误差。
- 你预计**问题演化得比 schema 能跟上的速度更快**，并且你想保留选择权。

如果这些都不成立，你大概率不需要数据湖。你需要一个数据仓库，也许由 PostgreSQL 逻辑复制或 CDC 管道供数，然后你就不必再为此担心了。


### 简要谈谈湖仓一体

2026 年的诚实答案是，数据湖/数据仓库的区别正在坍缩。开放表格式——Apache Iceberg、Delta Lake、Apache Hudi——让你可以把数据保存在对象存储中，*同时*在其上拥有事务型表、schema 演进和时间旅行查询。这就是业内称为“lakehouse”的东西。Snowflake、Databricks、BigQuery 和 Redshift 现在都能读取 Iceberg，只是热情程度各不相同。如果你今天正在构建一个新的分析栈，问题与其说是“数据湖还是数据仓库”，不如说是“哪个引擎来查询我的 Iceberg 表”。

这对你的决策很重要，因为它移除了历史权衡中最糟糕的部分。你不再必须在“数据湖，所有东西都能进去但没有任何结构”和“数据仓库，所有东西都有结构但你必须提前知道”之间二选一。你可以拥有一个存储层，让数据湖阵营和数据仓库阵营都能查询。

从实践上讲，这对你意味着：让你的工程师给你带来一页纸，回答三个问题。这个数据湖具体解锁了哪些你今天无法做出的决策？它的成本是多少——对象存储成本、计算成本，以及持续运营所需的工程时间成本？谁会长期拥有它，包括那些不光鲜的部分，比如编目、访问控制，以及决定删除什么？

如果他们无法回答全部三个问题，他们还不需要数据湖。他们需要的是一次会议。
