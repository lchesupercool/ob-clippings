Code Agent Orchestra - 多代理编码的工作原理

2026 年 3 月 26 日

我今天在 O'Reilly AI CodeCon 上谈到了编排编码代理。演讲涵盖了在现实世界软件工作流程中协调人工智能编码代理的模式——从生成第一个子代理到运行具有质量门的并行代理团队，以确保一切都值得信赖。这是我为那些希望将这些模式付诸实践的人提供的材料的文章。

如果您想跟随交互式平台或获取所有资源，它们就在这里：

  • 完整的交互式幻灯片
  • 概述和资源页面

我们所处的时刻

您曾经与一个人工智能配对。现在您管理一个代理团队。

六个月前，大多数开发人员在紧密的同步循环中使用单个人工智能助手。您输入提示，等待，查看输出，提供反馈，然后重复。您的上限是适合该单一上下文窗口的任何内容。对话线程是您的工作空间。

该模型已被替换。如今，最高效的开发人员正在协调多个异步运行的代理 - 每个代理都有自己的上下文窗口、自己的文件范围、自己的职责范围 - 而开发人员则从上面进行编排。代码库成为您的画布，而不是对话线程。这是从指挥（一名音乐家，实时指导）到协调者（整个乐团，异步协调）的转变。我在 代理编码的未来 中写到了这种转变的早期迹象。

本次演讲涵盖了如何实际实现这一转变：模式、工具、质量关卡以及做好转变所需的纪律。

AI 辅助编码的 8 个级别

大多数开发人员都停留在 3-4 级。编排层从第 6 级开始，它需要一套与您达到第 5 级完全不同的技能。

Steve Yegge 最近概述了开发人员如何使用 AI 工具发展的八个级别，它是一个有用的框架，可以帮助您了解您的现状和前进方向。

本次演讲涵盖了第 5 级到第 8 级。您处于这个阶梯的哪个位置？

转变：指挥家到编曲家

指挥模型为您提供一个同步代理，将您的上下文窗口作为硬天花板。协调器模型为您提供了多个具有自己的上下文窗口的代理，在您计划和签入时异步工作。

核心思维模式的转变是结对编程和管理团队之间的区别。在指挥模型中，您可以实时引导单个 AI 代理。它是同步的、连续的，并且你的上下文窗口是一个硬天花板。该模型的工具包括 Claude Code CLI 和 Cursor 编辑器内代理模式。

在协调器模型中，您正在协调整个整体。多个代理，每个代理都有自己的上下文窗口，异步工作。您计划工作、分配工作并定期检查。该模型的工具包括 Agent Teams、Conductor、Codex 和 Copilot Coding Agent。

就像管理一个真正的团队一样，你现在需要不同的技能：明确的规范、工作分解和输出验证，而不是自己编写代码。

单代理上限

每个开发人员最终都会用一个代理碰上三堵墙：上下文过载、没有专业化、没有协调。子代理解决了前两个问题。特工团队解决了所有三个问题。

为什么一个代理人不能包办这一切？三个约束。

上下文过载。 一个代理只能保存这么多信息。大型代码库会淹没单个上下文窗口。随着谈话时间的延长，你会失去重要的细节。

没有专业化。 一个代理做所有事情 - 数据层、API、UI、测试 - 是万事通，但一无是处。与处理整个代码库的通才相比，仅处理数据层的专注代理可以编写更好的数据库代码。

没有协调。 即使您生成助手，它们也无法通信、共享任务列表或解决依赖关系。在没有协调原语的情况下添加的代理越多，它就会变得越困难。

为什么要使用多代理？

并行性、专业化、隔离性和复合学习不仅会相加，而且会成倍增加。三名专注的客服人员的表现始终优于一名多面手客服人员，其工作时间是其三倍。

采用多代理的四个复合原因：

  • 并行性（3 倍吞吐量） - 三个代理同时构建前端、后端和测试。
  • 专业化（重点上下文） - 每个代理只能看到其拥有的文件。一个只知道 db.js 的代理会比一个处理整个代码库的代理编写更好的数据库代码。
  • 隔离（安全执行） - Git 工作树为每个代理提供了自己的工作目录。它们工作时没有合并冲突。
  • 复合学习 - AGENTS.md 文件会累积跨会话的模式和陷阱，因此每个会话都会使下一个会话变得更好。

模式 1：子代理 - 集中委派

子代理是最简单的多代理模式，也是您应该首先尝试的模式。

子代理使用任务工具从父协调器中生成专门的子代理。父级将任务分解为多个部分，为每个部分生成子代理，并手动管理依赖关系图。

这是一个具体的例子。您给 Claude Code 一个提示：“使用 Express 和 SQLite 构建一个名为 Link Shelf 的书签管理器。”父协调器将其分解为三个子代理摘要：

  • 数据层子代理 - 使用架构和 CRUD 操作构建 db.js，完成后写入 DATA.md 报告
  • 业务逻辑子代理 - 使用输入规则构建 validation.js，完成后写入 LOGIC.md 报告
  • API 路由子代理 - 读取 DATA.md 和 LOGIC.md，使用 Express 路由构建 server.js 前两个子代理是独立的 - 它们并行运行。第三个依赖于两者，因此它在开始之前等待它们的报告文件。父级手动管理此依赖关系图。

演示 1：子代理构建链接架

观察父级分解提示，并行生成数据和验证子代理，然后在两个报告准备就绪后启动 API 路由。测试最终通过。

子代理解决的问题： 每个代理的上下文隔离、专业化、独立任务的并行执行，并且总共大约 220k 令牌，成本中性。

还缺少什么：父级必须手动管理依赖关系图。代理之间没有对等消息传递。没有共享任务列表。如果您对文件范围界定不重视，两个代理可能会写入同一个文件。

底线：子代理为您提供手动协调的并行执行。这对于简单分解来说非常有用。但当协调成为瓶颈时，您就需要代理团队。

专业提示：分层子代理 - 团队的团队

不要停留在某一级别的授权上。产生特色线索，产生自己的专家。这可以让您进行 3 倍更深的分解，而不会破坏任何人的上下文窗口。

您的协调器不会产生六个子代理（这会分散其上下文），而是会产生两个功能线索。每个功能领导者都会产生自己的两到三名专家。

父协调器仅与两个代理通信，保持其上下文干净。功能主管 A 收到类似“构建搜索功能”的简介，并将其分解为数据、逻辑和 API 子代理。家长永远看不到这些细节。

这模仿了真实工程组织的工作方式。您没有工程副总裁将任务分配给各个工程师。您会经历层层技术主管。

模式 2：代理团队 - 真正的并行执行

代理团队添加了子代理所缺乏的协调原语：具有依赖性跟踪的共享任务列表、团队成员之间的点对点消息传递以及文件锁定以防止冲突。

代理团队是 Claude Code 的实验性功能，可实现真正的并行执行。启用它：

export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1

该架构分为三层：

  • 团队领导位于顶部 - 分解工作、创建任务列表、综合结果
  • 中间的 共享任务列表 - 具有状态（待处理、进行中、已完成、已阻止）、依赖项跟踪和文件锁定的任务
  • 队友位于底部 - 每个独立的 Claude Code 实例都有自己的上下文窗口，在 tmux 拆分窗格中运行 队友从共享列表中自行领取任务。他们直接互相发送消息——点对点，而不是通过领导。当队友完成并将任务标记为完成时，依赖于该任务的任何被阻止的任务都会自动取消阻止。随时按 Ctrl+T 即可切换任务列表的视觉覆盖。

演示 2：代理团队并行构建搜索

这是英雄演示。我们从一个可用的 Link Shelf 应用程序开始，并给 Claude Code 一个提示：“创建一个三人代理团队来添加搜索功能。”领导者会产生后端、前端和测试队友。后端队友启动搜索 API 端点。前端队友启动搜索 UI。测试队友最初处于阻塞状态 - 等待 API。当后端完成并向前端发送 API 合约消息时，测试任务会自动解除阻塞。三者同时工作。

演示3：座席团队近距离沟通

这个较短的演示重点介绍了通信机制。观察 Ctrl+T 任务列表覆盖、后端将 API 端点标记为已完成时依赖项自动解除阻止，以及后端代理直接向前端代理发送 API 合约而无需通过引导的对等消息。

特工团队：机制如何运作

代理团队有两种机制发挥作用：具有自动依赖关系解析功能的共享任务列表，以及防止潜在客户成为瓶颈的点对点消息传递。

共享任务列表为每个任务提供一个状态：待处理、进行中、已完成或已阻止。被阻止的任务具有显式的依赖性。当后端团队成员将搜索 API 标记为已完成时，被阻止的测试编写任务会自动转为待处理状态，并由团队成员接手。文件锁定可防止两个队友同时编辑同一文件。

对等消息传递是另一个关键部分。后端代理直接告诉前端代理 API 合约：“GET /search?q= returns [{id,title,url}]”。这不会通过引线。当队友空闲时，领导会自动收到通知。这种点对点方法可以防止潜在客户成为协调瓶颈。

代理团队：关键要点

三到五个队友是最佳选择。代币成本呈线性增长，三个专注的团队成员始终优于五个分散的团队成员。

  • 真正的并行与协调 - 不仅仅是同时运行。具有依赖性跟踪的共享任务列表可确保工作按正确的顺序进行。
  • 对等消息传递可防止瓶颈 - 队友直接沟通。后端将 API 合约告知前端，无需 Lead 作为中介。
  • 风险任务的计划批准 - 要求队友在实施之前编写计划。主管审查并批准或拒绝，在代码存在之前发现架构问题。
  • 调整你的团队规模 - 3-5 名队友是最佳选择。代币成本与团队规模呈线性关系。

给代理团队的专业提示：可靠性

带强制反射的环形护栏可大幅减少卡住的药剂。专门的@reviewer 队友会在每次任务完成时自动触发，这意味着领导只能看到经过绿色审核的代码。

循环护栏+反射步。每个队友都会获得硬MAX_ITERATIONS=8。每次重试之前，强制显示反射提示：

“什么失败了？什么具体的改变可以解决这个问题？我是否在重复同样的方法？”

这一单一的改变大大减少了被困的代理。如果没有它，代理就会无休止地循环尝试相同的破碎方法。有了它，他们就能自我纠正。

专门的@reviewer队友。产生一个具有以下约束的永久审阅者：

  • 型号： Claude Opus 4.6（只读）
  • 工具： lint、测试、仅安全扫描
  • 触发： 每个 TaskCompleted 事件都会自动触发
  • 比例： 每 3-4 名构建者 1 名审阅者 领导只能看到经过绿色审查的代码。这就像团队本身内置了一个永久的 CI 质量门。

模式 3：大规模编排

当您需要跨多个存储库和功能管理 5、10 或 20 多个代理时，您需要专门构建的编排工具。 2026 年的每个工具都适合三个级别之一 - 选择适合工作的正确级别。

2026 年的工具格局分为三个层次：

第 1 层：流程内子代理和团队

克劳德·代码子代理和代理团队。单个终端会话，无需额外的工具。从这里开始。

第 2 层：本地协调者

您的机器在隔离的工作树中生成多个代理。您可以随时了解仪表板、差异审查和合并控制。最适合已知代码库上的 3-10 个代理。工具包括 Conductor、Vibe Kanban、Gastown、OpenClaw + Antfarm、Claude Squad、Antigravity 和 Cursor Back Agents。

第 3 层：云异步代理

分配任务，关闭笔记本电脑，返回拉取请求。代理在云虚拟机中运行。没有终端，没有本地设置。工具包括 Claude Code Web、GitHub Copilot Coding Agent、Jules by Google 和 Codex Web by OpenAI。

到 2026 年，大多数开发人员将使用所有三个层 - 第 1 层用于交互式工作，第 2 层用于并行冲刺，第 3 层用于隔夜消除积压。

工具亮点

Melty Labs 指挥

Conductor 是在 Mac 上启动多代理编排的最快方式。它并行运行多个 Claude Code 和 Codex 代理，每个代理都在自己的 git 工作树中，并具有可视化仪表板和差异优先审查 UI。它是免费的 - 您只需支付 API 费用。目前仅限 macOS（Apple Silicon 和 Intel）。最佳点是同一个存储库上有 3-8 个并行功能，并且具有视觉监督。

克劳德代码网络

claude.ai/code 网站上的 Claude Code 是 Claude Code 的第 3 层版本 - 完全基于浏览器，无需终端。连接您的 GitHub 存储库，描述任务，然后它们在 Anthropic 管理的云虚拟机中运行。您可以在运行中进行引导、自动创建 PR，并从 iOS 应用程序访问它。关键心智模型：Teams（终端）用于与代理一起工作； Web（浏览器）用于委派和离开。

GitHub Copilot 编码代理

一个重要的区别：IDE 中的 Copilot 代理模式是同步且交互式的。 GitHub 上的 Copilot Coding Agent 是完全异步的。将任何 GitHub 问题分配给 @copilot 或使用代理面板，它会创建在 GitHub Actions 环境中工作的草稿 PR。现在，它会在标记您之前运行自我审查循环。还可以通过同一代理面板访问包括 Claude Code 和 Codex 在内的第三方代理，并且您可以从 Slack、Jira、Linear 和 Azure Boards 触发它。

朱尔斯（谷歌）

Jules 是 Google 的异步云编码代理，由 Gemini 提供支持。工作流程：连接 GitHub 存储库，描述任务，Jules 在编写任何代码之前生成您批准的计划，然后在云虚拟机中运行并返回包含完整推理和终端日志的 PR。独特的功能包括音频更改日志、任务中中断以及用于直接管道 GitHub 问题的 Jules Tools CLI。它会自动读取您的存储库的 AGENTS.md 且零额外配置。

OpenAI Codex 网站

Codex Web 是该领域使用最广泛的工具之一。每个任务都在预加载了 GitHub 存储库的单独沙盒容器中运行。 Surface 生态系统涵盖 Web、CLI（开源）、macOS 应用程序、IDE 扩展和 GitHub 集成 - 所有这些都通过您的 ChatGPT 帐户连接。可验证的证据功能会返回每个任务的终端日志和测试输出的引用，以便您可以准确审核发生的情况。

光标云代理 + Glass

代理基础相同，但在隔离的云虚拟机中运行。从网络、桌面应用程序、Slack、Linear、GitHub、API 启动代理，甚至在手机上安装cursor.com/agents 作为 PWA。 Glass 是 Cursor 的新界面，它使代理管理成为主要界面，并让您在需要时可以使用传统编辑器。这反映了整个生态系统的更广泛模式：控制平面正在成为主要体验，而编辑器是其之下的工具。

氛围看板

Vibe 看板解决了“末日滚动间隙”——客服人员正在工作而您无事可做的那 2-5 分钟。创建带有详细提示的任务卡，拖动到“进行中”，每个任务卡都有自己的工作树和分支。审查内部差异，向正在运行的代理发送反馈。支持 Claude Code、Codex、Gemini CLI、Amp、Cursor Agent CLI 等。跨平台（Mac、Windows、Linux）、免费、BYOK。

扩展的专业技巧

多模型布线可在不牺牲质量的情况下降低成本。无论长度如何，人工策划的 AGENTS.md 都比机器生成的更有价值 - 研究表明人工智能编写的规则没有任何好处，并且会略微降低成功率。

多模型路由

并非每项任务都需要最昂贵的模型。将规划和架构任务路由到更便宜的 Gemini/Claude/OpenAI 模型之一。将实施路由至 Sonnet、Opus 或 Codex。将审查路由到专用安全模型。创建 MODEL_ROUTING.md 文件：

Planning       -> Gemini 
Implementation -> Claude Opus or Sonnet 
Review         -> etc.
Tests          -> etc.

Worktree 生命周期脚本

三个 shell 别名自动完成繁重的工作：

agent-spin <feature>   # create worktree + branch + start agent
agent-merge <feature>  # rebase + review + open PR
agent-clean            # remove finished worktrees

bash 大约有 12 行。 Conductor 可以直观地为您完成此操作。

仅限人工策划的 AGENTS.md

这是最大的一个。 研究表明（Gloaguen 等人，苏黎世联邦理工学院）LLM 生成的 AGENTS.md 文件没有任何好处，并且会略微降低成功率（平均约 3%），同时使推理成本增加超过 20%。相比之下，开发人员编写的上下文文件提供了约 4% 的适度改进。切勿让代理直接写入 AGENTS.md。领导必须批准每一行。保持简短并有清晰的部分：

## STYLE
- Use functional components with hooks
- Prefer named exports

## GOTCHAS
- SQLite requires WAL mode for concurrent reads
- Express middleware order matters for auth

## ARCH_DECISIONS
- All state in SQLite, no in-memory caches
- One Express router per feature module

## TEST_STRATEGY
- Integration tests over unit tests for API routes
- Use supertest for HTTP assertions

质量门：信任但验证

三个质量关卡使代理输出值得信赖：计划批准在代码存在之前捕获不良架构，挂钩对每个生命周期事件强制执行自动检查，并且 AGENTS.md 复合了跨会话的学习。

计划批准。 要求团队成员在开始编码之前编写计划。领导审查该方法并批准或拒绝。修复一个糟糕的计划比修复糟糕的代码要便宜得多。流程如下：

teammate >>> writes plan >>> lead review >>> approve/reject >>> implement

挂钩。 自动检查生命周期事件。 TeammateIdle 挂钩会在允许代理停止工作之前验证所有测试是否通过。 TaskCompleted 挂钩在将任务标记为完成之前运行 lint 和测试。如果钩子失败，代理将继续工作直到通过：

task done >>> hook runs npm test >>> pass? allow  |  fail? keep working

用于复合学习的 AGENTS.md。 该文件捕获发现的模式、陷阱和风格偏好。每个代理在会话开始时都会读取它，并且每个会话都会添加到它。会话一了解测试模式，AGENTS.md 已更新，会话二避免了同样的错误。

瓶颈已经转移

瓶颈不再是一代。这是验证。代理可以以令人难以置信的速度产生令人印象深刻的输出。确信地知道输出是否正确是困难的部分。

在更改之前通过的测试并不能保证它们会捕获更改带来的回归。代理可以编写技术上有效的测试，但会错过重要的案例。上下文窗口限制意味着在大型代码库上工作的代理可能会错过当前视图之外的重要约束。当 40 个代理同时进行相同的片状测试时，片状环境（单个开发人员遇到的恼人的边缘情况）就会成为系统障碍。

在验证基础设施赶上生成能力之前，人工审核不是可选的开销。这是安全系统。对令人印象深刻的代理输出的适当反应不是因为它看起来不错而相信它。要有架构理解和测试纪律来严格评估它。

演示 4：质量门和自我改进代理

这个演示将所有内容联系在一起。注意三件事。首先，计划审批流程 - 队友建议添加收藏夹功能，领导者发现该计划缺少数据库迁移步骤并拒绝它，然后队友进行修改。其次，钩子在任务完成时触发 - TaskCompleted 钩子捕获被遗忘的 console.log 语句，代理在任务标记为完成之前修复它。第三，AGENTS.md 最后更新了一个新条目：“向现有表添加列时始终包含 ALTER TABLE 迁移。”这种学习会延续到未来的每一堂课。

拉尔夫循环和自我改进代理

拉尔夫循环模式将开发分解为小的原子任务，并在无状态但迭代的循环中运行代理。每次迭代：选择任务、实施、验证、如果通过则提交、重置上下文并重复。这可以避免上下文溢出，同时保持通过外部存储器的连续性。

拉尔夫环路 (Ralph Loop) 由杰弗里·亨特利 (Geoffrey Huntley) 和瑞安·卡森 (Ryan Carson) 推广，是“睡觉时运输”背后的模式。 Carson 的独立 ralph 工具 (snarktank/ralph) 实现了核心循环，而他的 Antfarm 项目则使用相同的模式在 OpenClaw 之上分层多代理编排。核心思想概括了各种工具。

五步循环：

  • 选择 - 从 tasks.json 中选择下一个任务
  • 实施 - 进行更改
  • 验证 - 运行测试、类型、lint
  • 提交 - 如果检查通过，则提交并更新任务状态
  • 重置 - 清除代理上下文并重新开始下一个任务 关键的见解是无状态但迭代的。通过重置每次迭代，代理可以避免累积混乱。与一个巨大的提示相比，小的有界任务会产生更干净的代码，并且产生的幻觉更少。

使其可靠的保障措施：反馈错误以进行自动重试，但在 3 次以上卡住迭代后终止并重新分配。始终在功能分支上工作。对迭代、时间和令牌设置硬性限制。代理打开 PR - 您在合并之前进行审查。

重置后会保留四个内存通道：git 提交历史记录、进度日志、任务状态文件 (tasks.json) 和 AGENTS.md 作为长期语义内存。从一个循环开始过夜。逐渐达到十个分支上的十个循环。

随着时间的推移让代理变得更加聪明

通过 REFLECTION.md 提案进行自我反思。 在每项任务之后，强制代理编写 REFLECTION.md：令我惊讶的是，将一种模式添加到 AGENTS.md，一种快速改进。领导审查并合并批准的学习内容。这就是复合学习实际上是复合的 - 系统地，而不是临时的。

令牌预算和终止标准。 设置每个代理的硬性预算：前端 180k 令牌，后端 280k 令牌。当预算达到 85% 时，自动暂停并通知主管。如果在同一个错误上重复 3 次以上，则终止并重新分配给新代理。

珠子/持久记忆。 Gas​​town 的“珠子”模式：每个决定和结果的不可变的、由 git 支持的记录，具有完整的出处。代理通过任务图和 SQL 可寻址数据平面查询过去的珠子 - 不是传统的基于向量的 RAG，而是结构化的、可查询的机构内存，远远超出了平面 Markdown 文件。

纪律：是什么让这一切成功

人类瓶颈是一个功能，而不是一个错误。按照人类的节奏，错误会慢慢复合，而痛苦则迫使人们及早纠正。有了一支特工大军，小错误会以超出你捕捉能力的速度复合。

当人类编写代码缓慢时，你很早就感受到痛苦。测试失败，代码审查发现一些东西，你注意到重复。疼痛是立竿见影的，所以你可以边走边修复。

有了精心策划的特工大军，就不存在天然的瓶颈。无害的小错误——这里有代码味道，那里有重复，不必要的抽象——以不可持续的速度复合。你已经把自己从循环中解脱出来，所以你不会感到痛苦，直到为时已晚。然后有一天，您尝试添加一项功能，但架构不允许。你的测试同样不可信，因为这些测试也是由代理编写的。

这就是为什么每个质量门都很重要。计划批准、挂钩、代币预算、人工审核——它们的存在并不是因为它们很好，而是因为没有它们，你就会自动将自己逼入角落。

委派任务，而不是判断

让代理通过明确的通过/失败标准、样板、迁移和测试脚手架处理范围内的任务。为自己保留：架构，决定不构建什么，在完整的上下文中进行审查，以及产生良好系统的品味。

代理在具有严格评估功能的任何事情上都表现出色——代理可以衡量自己的工作。他们非常擅长样板文件、迁移、测试脚手架以及探索你永远没有时间手动尝试的方法。

为自己保留：架构和 API 设计（代理在他们的训练数据中看到了大量糟糕的架构，并且很乐意将货物崇拜企业模式引入您的初创公司），决定不构建什么（说“不”是代理没有的功能），并使用完整的系统上下文审查代理输出（代理只有本地视图）。

构建更少的功能，但构建正确的功能。代码生成的速度是令人惊叹的。放慢速度以保持理解。因为如果你失去了对自己系统的理解，你就失去了修复它、扩展它、甚至知道它何时损坏的能力。

你的规格就是杠杆

当您并行协调 50 个代理时，模糊的思维不仅会减慢您的速度，还会成倍增加。不明确的需求通过数十次并行运行传播，每次都在稍微不同的方向上出现轻微错误。优秀的工程师可以从代理商那里获得更多的影响力，而不是更少。

平庸的输出和卓越的输出之间的差异几乎完全取决于您的规格的质量。模糊的规格会使整个机队的错误成倍增加。精确的规范——具有清晰的架构、集成边界、边缘情况和不变量——可以在任何地方乘以精确的实现。

spec 不再是提示。规范是明确的产品思维。这就是为什么强大的软件工程师比弱软件工程师从这些工具中获得更多的利用。键入代码的机械工作正在自动化。理解系统的认知工作正在整个自主工作人员队伍中得到放大。

工厂模型

您不再只是编写代码。您正在构建构建软件的工厂。该工厂有一条生产线：计划、生成、监控、验证、集成、复古。

工厂有质量控制。工厂有工艺文件。工厂的输入需要精确指定，否则输出就会出错。当环境不可靠时，工厂就会停工。所有这些属性都直接映射到代理软件开发。

六步生产线：

  • 计划 - 编写带有验收标准的规格。你的规格就是杠杆。
  • Spawn - 创建您的团队并分配代理。
  • 监控 - 每 5-10 分钟观察进度并解决障碍。不要悬停。
  • 验证 - 运行测试，审查代码。验证是瓶颈，而不是生成。
  • 集成 - 合并分支，解决冲突。

  • 复古 - 使用新模式更新 AGENTS.md。复合学习。 经营工厂的实用技巧：

  • 设置 WIP 限制： 运行的代理数量不要超过您可以有意义地审查的数量。 3-5是最佳点。

  • 定义终止标准： 如果代理因同一错误而卡住 3 次以上迭代，则停止并重新分配。
  • 异步签入： 每 5-10 分钟检查一次进度。让代理自主工作。
  • 一个文件，一个所有者： 切勿让两个代理编辑同一文件。冲突会扼杀速度。 有关此框架的更多信息，请参阅工厂模型。
