## 3.6.1. 预处理

定义在 `planner.c` 中的 subquery\_planner() 函数会调用预处理流程。单表查询的预处理已在 `Section 3.3.1` 中描述过。本小节将介绍多表查询的预处理。由于内容较多，这里只介绍其中的一部分。

1. 规划并转换 CTE
	如果存在 WITH 列表，planner 会通过 SS\_process\_ctes() 函数处理每一个 WITH query。
2. 提升 Subquery
	如果 FROM 子句中包含 subquery，且该 subquery 不含 GROUP BY、HAVING、ORDER BY、LIMIT 或 DISTINCT 子句，也不使用 INTERSECT 或 EXCEPT，那么 planner 会通过 pull\_up\_subqueries() 函数将其转换为 join 形式。
	例如，下面这条在 FROM 子句中包含 subquery 的查询可以被转换为一条 natural join query。不用说，这种转换是在 query tree 上完成的。
	```sql
	testdb=# SELECT * FROM tbl_a AS a, (SELECT * FROM tbl_b) as b WHERE a.id = b.id;
	```
	⇓
	$$
	\Downarrow
	$$
	```sql
	testdb=# SELECT * FROM tbl_a AS a, tbl_b as b WHERE a.id = b.id;
	```
3. 将 outer join 转换为 inner join
	planner 会在可能的情况下将 outer join query 转换为 inner join query。

## 3.6.2. 获取 cheapest path

为了得到最优的 plan tree，planner 需要考虑所有 index 和 join method 的组合。这个过程代价非常高，当表的数量超过某个程度时，由于组合爆炸，这种做法将变得不可行。幸运的是，当表的数量小于约 12 时，planner 可以通过 dynamic programming 得到最优 plan。否则，planner 会使用 *genetic algorithm*。参考下文。

当执行一条 join 了很多表的 query 时，优化 query plan 将耗费大量时间。为了应对这种情况，PostgreSQL 实现了一个有趣的特性：

`Genetic Query Optimizer`。

这是一种近似算法，可以在合理的时间内确定一个合理的 plan。因此，在 query 优化阶段，如果要 join 的表的数量高于由参数 `geqo_threshold` 指定的阈值（默认值为 12），PostgreSQL 就会使用 genetic algorithm 生成 query plan。

通过 dynamic programming 确定最优 plan tree 可以用以下步骤说明：

- Level = 1
	获取每个表的 cheapest path。该 cheapest path 被保存在对应的 RelOptInfo 中。
- Level = 2
	获取每两个表组合的 cheapest path。
	例如，如果有两个表 A 和 B，就获取表 A 和 B 的最便宜 join path。这就是最终答案。
	下文中，两个表的 RelOptInfo 用 {A, B} 表示。
	如果有三个表，则分别获取 {A, B}、{A, C} 和 {B, C} 的 cheapest path。
- Level = 3 及以上
	继续同样的流程，直到 level 等于表的数量为止。

这样一来，每个 level 上都会得到子问题的 cheapest path，并用于上一层 level 的计算。这使得高效计算最便宜 plan tree 成为可能。

```sql
--------+---------+-----------

Indexes:
    "tbl_a_pkey" PRIMARY KEY, btree (id)

testdb=# \d tbl_b
     Table "public.tbl_b"
 Column |  Type   | Modifiers
--------+---------+-----------
 id     | integer |
 data   | integer |

testdb=# SELECT * FROM tbl_a AS a, tbl_b AS b WHERE a.id = b.id AND b.data < 400;
```

### 3.6.2.1. Level 1 的处理

在 Level 1 中，planner 会为 query 中的每个 relation 创建一个 RelOptInfo 结构并估算其 cheapest cost。这些 RelOptInfo 结构会被添加到该 query 的 PlannerInfo 的 simple\_rel\_array 中。

![](https://www.interdb.jp/pg/pgsql03/fig-3-35.png)

Figure 3.35. Level 1 处理之后的 PlannerInfo 和 RelOptInfo。

tbl\_a 的 RelOptInfo 有三条 access path，这些 path 被添加到该 RelOptInfo 的 pathlist 中。每条 access path 都会被链接到一条最便宜 cost path：*cheapest start-up (cost) path*、*cheapest total (cost) path* 和 *cheapest parameterized (cost) path*。cheapest start-up 和 total cost path 含义较为直观，下面将介绍最便宜的 parameterized index scan path 的 cost。

正如 `Section 3.5.1.3` 中所述，planner 会考虑在 indexed nested loop join（以及极少数情况下带有 outer index scan 的 indexed merge join）中使用 parameterized path。cheapest parameterized cost 是所估算的 parameterized path 中最便宜的 cost。

tbl\_b 的 RelOptInfo 只包含一条 sequential scan access path，因为 tbl\_b 没有相关的 index。

### 3.6.2.2. Level 2 的处理

在 Level 2 中，会创建一个 RelOptInfo 结构并被加入到 PlannerInfo 的 join\_rel\_list 中。接着，会估算所有可能 join path 的 cost，并选出 total cost 最便宜的 best access path。RelOptInfo 会将该 best access path 保存为其 cheapest total cost path。见 Figure 3.36。

![](https://www.interdb.jp/pg/pgsql03/fig-3-36.png)

Figure 3.36. Level 2 处理之后的 PlannerInfo 和 RelOptInfo。

Table 3.1 展示了本例中所有 join access path 的组合。本例中的 query 是 equi-join 类型，因此三种 join method 都会被估算。为了方便起见，这里引入一些 access path 的记号：

- *SeqScanPath(table)* 表示 table 的 sequential scan path。
- *Materialized->SeqScanPath(table)* 表示 table 被物化后的 sequential scan path。
- *IndexScanPath(table, attribute)* 表示按该 table 的 attribute 进行 index scan 的 path。
- *ParameterizedIndexScanPath(table, attribute1, attribute2)* 表示按 table 的 attribute1 进行 parameterized index path，该 path 由 outer table 的 attribute2 参数化。

## 3.6.3. 获取三表 query 的 cheapest path

获取涉及三张表的 query 的 cheapest path 过程如下：

```sql
testdb=# \d tbl_a
     Table "public.tbl_a"
 Column |  Type   | Modifiers
--------+---------+-----------
 id     | integer |
 data   | integer |

testdb=# \d tbl_b
     Table "public.tbl_b"
 Column |  Type   | Modifiers
--------+---------+-----------
 id     | integer |
 data   | integer |

testdb=# \d tbl_c
     Table "public.tbl_c"
 Column |  Type   | Modifiers
--------+---------+-----------
 id     | integer | not null
 data   | integer |
Indexes:
    "tbl_c_pkey" PRIMARY KEY, btree (id)

testdb=# SELECT * FROM tbl_a AS a, tbl_b AS b, tbl_c AS c
testdb-#                WHERE a.id = b.id AND b.id = c.id AND a.data < 40;
```
- Level 1：
	planner 估算所有表的 cheapest path，并将这些信息保存在对应的 RelOptInfo 对象中：{tbl\_a}、{tbl\_b} 和 {tbl\_c}。
- Level 2：
	planner 取出三张表中所有两两组合，并为每种组合估算 cheapest path。然后将信息保存到对应的 RelOptInfo 对象中：{tbl\_a, tbl\_b}、{tbl\_b, tbl\_c} 和 {tbl\_a, tbl\_c}。
- Level 3：
	planner 最终利用已获得的 RelOptInfo 对象得到 cheapest path。

	更准确地说，planner 会考虑三种 RelOptInfo 对象的组合：{tbl\_a, {tbl\_b, tbl\_c}}、{tbl\_b, {tbl\_a, tbl\_c}} 和 {tbl\_c, {tbl\_a, tbl\_b}}，因为

planner 接着会估算其中所有可能 join path 的 cost。

对于 RelOptInfo 对象 {tbl\_c, {tbl\_a, tbl\_b}}，planner 会估算 tbl\_c 与 {tbl\_a, tbl\_b} 的 cheapest path 的所有组合；在本例中，该 cheapest path 是 hash join，其 inner 和 outer 表分别为 tbl\_a 和 tbl\_b。

这些估算出的 join path 将包含三类 join path 及其变体，如前一小节所示，即 nested loop join 及其变体、merge join 及其变体，以及 hash join。

planner 以同样的方式处理 RelOptInfo 对象 {tbl\_a, {tbl\_b, tbl\_c}} 和 {tbl\_b, {tbl\_a, tbl\_c}}，并最终从所有估算出的 path 中选出最便宜的 access path。

这条 query 的 EXPLAIN 命令的结果如下所示：

![](https://www.interdb.jp/pg/pgsql03/fig-3-37.png)

最外层的 join 是 indexed nested loop join（第 5 行）。内侧的 parameterized index scan 见第 13 行，其 outer relation 则是一条 hash join 的结果，该 hash join 的 inner 和 outer 表分别为 tbl\_b 和 tbl\_a（第 7-12 行）。因此，executor 会先执行 tbl\_a 和 tbl\_b 的 hash join，然后再执行 indexed nested loop join。
