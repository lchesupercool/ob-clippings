5. Concurrency Control

Concurrency Control 是一种机制，用于在多个 transaction 在数据库中并发运行时，维护 ACID 中的两个属性 ==atomicity 与 isolation==。

==Concurrency Control 大致分为三类技术==：Multi-version Concurrency Control（MVCC）、Strict Two-Phase Locking（S2PL）和 Optimistic Concurrency Control（OCC）。每种技术又有许多变体。

在 MVCC 中，每次 ==写操作== 都会创建数据项的新版本，同时保留旧版本。当一个 transaction ==读取== 数据项时，系统会选择其中一个版本，以保证 ==单个 transaction 的 isolation==。MVCC 的主要优势在于 "读者不阻塞写者，写者也不阻塞读者"，==作为对比==，例如基于 S2PL 的系统在写者写入数据项时必须阻塞读者，因为写者需要获取该数据项的 exclusive lock。PostgreSQL 和一些 RDBMS 使用 ==一种称为 Snapshot Isolation (SI) 的 MVCC 变体。==

为了实现 SI，某些 RDBMS（如 Oracle）使用 rollback segment。==在写入新数据项时，该数据项的旧版本会被写入 rollback segment，随后新数据项会被覆盖写入数据区域。==PostgreSQL 则使用一种更简单的方法。新的数据项直接被插入到相应的 table page 中。在读取数据项时，PostgreSQL 会通过应用 visibility check rules，为每一个 transaction 选择合适的数据项版本。

SI 不允许 ANSI SQL-92 标准中定义的三种异常：==Dirty Reads、Non-Repeatable Reads 和 Phantom Reads。==然而，SI 无法实现真正的 serializability，因为它允许一些 serialization anomaly，例如 Write Skew 和 Read-only Transaction Skew。需要注意的是，基于经典 serializability 定义的 ANSI SQL-92 标准 不 等价于现代理论中的定义。

为了处理这个问题，从 9.1 版本开始新增了 Serializable Snapshot Isolation (SSI)。SSI 可以检测 serialization anomaly，并可以解决由此类异常引起的冲突。因此，PostgreSQL 9.1 或更高版本提供了真正的 SERIALIZABLE isolation level。（此外，SQL Server 同样使用 SSI；Oracle 目前仍然只使用 SI。）

Transaction Isolation Level in PostgreSQL

PostgreSQL 实现的 transaction isolation level 如下表所示：

Isolation Level Dirty Reads Non-repeatable Read Phantom Read Serialization Anomaly
READ COMMITTED Not possible Possible Possible Possible
REPEATABLE READ *1 Not possible Not possible Not possible in PG; See Section 5.7.3. (Possible in ANSI SQL) Possible
SERIALIZABLE Not possible Not possible Not possible Not possible

*1：在 9.0 及更早版本中，这一级别被用作 "SERIALIZABLE"，因为它不允许 ANSI SQL-92 标准中定义的三种异常。然而，随着 9.1 版本中 SSI 的实现，该级别被改为 "REPEATABLE READ"，并引入了真正的 SERIALIZABLE 级别。

Note

PostgreSQL 对 DML（Data Manipulation Language，例如 SELECT、UPDATE、INSERT、DELETE）使用 SSI，对 DDL（Data Definition Language，例如 CREATE TABLE 等）使用 2PL。
