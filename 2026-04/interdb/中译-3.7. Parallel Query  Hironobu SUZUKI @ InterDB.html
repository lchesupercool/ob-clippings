3.7. Parallel Query

Parallel Query 是从 9.6 版本开始支持的特性，它使用多个进程（Worker）来处理单个查询。

例如，在满足某些条件时，执行查询的 PostgreSQL 进程会成为 Leader，并启动若干 Worker 进程（最大数量由 max_parallel_workers_per_gather 决定）。然后每个 Worker 进程执行扫描处理，并将结果依次返回给 Leader 进程。Leader 进程再聚合这些由 Worker 进程返回的结果。

图 3.38 展示了由两个 Worker 进程处理顺序扫描查询的过程。

图 3.38. Parallel Query 概念图。

在 14 版本引入的配置参数 parallel_leader_participation 允许 Leader 进程在等待 Worker 响应时也参与处理查询。默认值为 on。

不过为了简化说明与图示，我们将在假定 Leader 进程不处理查询（即 parallel_leader_participation 为 off）的前提下展开解释。

Parallel Query 在逐步完善之中。表 3.2 摘录了官方文档 release notes 中关于 Parallel Query 的若干要点。

版本 描述
9.6 - Seq Scan。- Nested Loop Join 与 Hash Join。
10 - Merge Join。- B-tree Index Scan、Bitmap Heap Scan。- 允许非相关子查询。
11 - CREATE INDEX 在构建 B-tree 索引时可以使用并行处理。- 允许 hash join 通过共享 hash table 并行执行。- 允许 UNION 在各自 SELECT 无法单独并行时，将每个 SELECT 并行执行。- 允许并行化 CREATE TABLE... AS、SELECT INTO 和 CREATE MATERIALIZED VIEW 等命令。
12 - 允许在 SERIALIZABLE 隔离级别下并行化查询。
14 - 允许引用多个 foreign table 的查询并行执行 foreign table scan。- 允许 REFRESH MATERIALIZED VIEW 使用并行。
15 - 允许 SELECT DISTINCT 并行化。- 在更多场景下允许引用多个 foreign table 的查询并行执行 foreign table scan。- 允许在 postgres_fdw 服务器上并行提交。
16 - 允许 FULL 以及内部 right OUTER hash join 并行化。- 允许 postgres_fdw 并行执行 abort。

需要注意的是，Parallel Query 主要面向 READ-ONLY 场景，目前尚不支持游标操作。

3.7.1. Overview

图 3.39 简要描述了 PostgreSQL 中并行查询的执行过程。

图 3.39. Parallel Query 的执行过程。

  1. Leader 创建 Plan： 优化器创建一个可以并行执行的 plan。
  2. Leader 存储共享信息： 为了让 Leader 节点和 Worker 节点都能执行该 plan，Leader 会将必要的信息存放到自己的 Dynamic Shared Memory (DSM) 区域中。更多细节见下文说明。
  3. Leader 创建 Worker。
  4. Worker 设置状态： 每个 Worker 读取存储的共享信息来设置自己的状态，从而与 Leader 保持一致的执行环境。
  5. Worker 扫描行并返回结果。
  6. Leader 汇总结果。
  7. 查询完成后，Worker 被终止，Leader 释放 DSM 区域。

在 Parallel Query 处理过程中，Leader 和 Worker 进程通过 Dynamic Shared Memory (DSM) 区域进行通信。

Leader 进程按需分配内存空间（即可以在需要时分配，不再需要时释放）。Worker 进程随后可以像读写自己的内存一样，对这些内存区域进行读写。

本节中，为了用具体示例进行演示，我们使用如下的表 d：

testdb=# CREATE TABLE d (id double precision, data int);
CREATE TABLE
testdb=# INSERT INTO d SELECT i::double precision, (random()*1000)::int FROM generate_series(1, 1000000) AS i;
INSERT 0 1000000
testdb=# ANALYZE;

3.7.1.1. Creating Parallel Plan

Parallel Query 并不总是会被考虑。如果待扫描的表大小大于等于 min_parallel_table_scan_size （默认值为 8MB），或者待扫描的索引大小大于等于 min_parallel_index_scan_size （默认值为 512kB），优化器就会考虑使用 Parallel Query。

下面是一个最简单的并行查询 plan：

testdb=# EXPLAIN SELECT * FROM d WHERE id BETWEEN 1 AND 100;
                                     QUERY PLAN
-------------------------------------------------------------------------------------
 Gather  (cost=1000.00..16609.10 rows=1 width=12)
   Workers Planned: 2
   ->  Parallel Seq Scan on d  (cost=0.00..15609.00 rows=1 width=12)
         Filter: ((id >= '1'::double precision) AND (id <= '100'::double precision))
rows

如上所示，最简单的 plan 由一个 Gather 节点和一个 Seq Scan 节点构成。

图 3.40 展示了上述查询的 plan tree：

图 3.40. Leader 的 Plan Tree

Gather 节点是 Parallel Query 专用的节点，负责收集来自 Worker 的结果。除了 Gather 之外，Parallel Query 还有以下专用节点：

  • GatherMerge
  • Append 和 AppendMerge（见 Official Document。）
  • Finalize/Partial Aggregate（见 Section 3.7.3。）

由 Worker 执行的节点通常是 Gather 节点之下的 subplan tree，并且其 parallel_safe 值被设置为 True。在上述示例中，位于 Gather 节点之下的 Seq Scan 节点及其下方节点，都是由 Worker 执行的。

3.7.1.2. Storing Shared Information

为了与 Worker 协同执行查询，Leader 会将需要与 Worker 共享的信息存放在自己的 DSM (Dynamic Shared Memory) 区域中。

Leader 与 Worker 共享两类信息：execution state 和 query。

  • Execution State： Leader 和 Worker 一致地执行同一查询所需的环境信息。详情见 README.parallel。包括以下信息：
    • 所有配置参数（GUC）
      • 事务快照、当前子事务的 XID。（详情见 Chapter 5。）
      • 由 dfmgr.c 动态加载的库集合。 这些信息由 InitializeParallelDSM() 存储。
  • Query： 包含以下信息：
    • PlannedStmt
      • ParamListInfo
      • Worker 执行的节点的 Description 结构。例如 SeqScan 节点使用 ParallelTableScanDesc；IndexScan 节点使用 ParallelIndexScanDesc。详情见 ExecParallelInitializeDSM()。
      • 用于汇报目的的 instrumentation 和 usage 信息。 这些信息由 ExecInitParallelPlan() 存储。

此外，Leader 会在 DSM 上创建一个 TupleQueue（基于 tqueue.c ），用于读取 Worker 的结果。

3.7.1.3. Creating Workers

查询 plan 中计划的 Worker 数量，可能与实际运行的 Worker 数量不同。这是因为 Worker 的最大数量受 max_parallel_workers 限制，并且由于其他并行查询进程的存在，可用 Worker 可能不够。

EXPLAIN ANALYZE 命令会同时显示 planned 与 launched 的 Worker 数量。

3.7.2.1. Nested Loop Join

在 nested loop join 中，内表（inner table）总是需要处理所有行，并且不是并行处理的。

因此，举例来说，在 materialized nested loop join 中，每个 Worker 都必须独立地物化内表，效率较低。

testdb=# SET enable_nestloop = ON;
SET
testdb=# SET enable_mergejoin = OFF;
SET
testdb=# SET enable_hashjoin = OFF;
SET

testdb=# EXPLAIN SELECT * FROM d, f WHERE d.data = f.data AND f.id < 10000;
                                  QUERY PLAN
-------------------------------------------------------------------------------
 Gather  (cost=1000.00..97163469.29 rows=9651513 width=24)
   Workers Planned: 2
   ->  Nested Loop  (cost=0.00..96197317.99 rows=4825756 width=24)
         Join Filter: (d.data = f.data)
         ->  Parallel Seq Scan on f  (cost=0.00..121935.99 rows=4831 width=12)
               Filter: (id < '10000'::double precision)
         ->  Materialize  (cost=0.00..27992.00 rows=1000000 width=12)
               ->  Seq Scan on d  (cost=0.00..18109.00 rows=1000000 width=12)
rows

图 3.42. Parallel Query 中的 Materialize Nested Loop Join。

另一方面，在 Indexed Nested Loop Join 中，内表可以由 Worker 并行扫描，因此效率更高。

testdb=# EXPLAIN SELECT * FROM d, f WHERE d.id = f.id AND f.id < 10000;
                                  QUERY PLAN

3.7.2.2. Merge Join

与 nested loop join 类似，merge join 也总是对内表的所有行进行处理，不会并行。因此每个 Worker 都会独立执行内表的排序过程。

但是，如果内表通过 index scan 访问，则可以像 Indexed Nested Loop Join 那样高效地完成 join 操作。

testdb=# SET enable_mergejoin = ON;

testdb=# SET enable_hashjoin = OFF;

3.7.3. Parallel Aggregate

PostgreSQL 中几乎所有的聚合函数也都可以并行处理。某个聚合函数是否可以并行化，取决于其在 Official Document 中 Partial Mode 是否被设置为 YES。

当预测的目标行数较少时：

  1. 每个 Worker 扫描的行经过 parallel (seq) scan 节点处理后，在 gather 节点处被汇集。
  2. 这些被汇集起来的行随后在 aggregate 节点进行聚合。

请看以下示例：

testdb=# EXPLAIN SELECT avg(id) FROM d where id BETWEEN 1 AND 10;
                                        QUERY PLAN
------------------------------------------------------------------------------------------
 Aggregate  (cost=16609.10..16609.11 rows=1 width=8)
   ->  Gather  (cost=1000.00..16609.10 rows=1 width=8)
         Workers Planned: 2
         ->  Parallel Seq Scan on d  (cost=0.00..15609.00 rows=1 width=8)
               Filter: ((id >= '1'::double precision) AND (id <= '10'::double precision))
rows

testdb=# EXPLAIN SELECT var_pop(id) FROM d where id BETWEEN 1 AND 10;
                                        QUERY PLAN
------------------------------------------------------------------------------------------
 Aggregate  (cost=16609.10..16609.11 rows=1 width=8)
   ->  Gather  (cost=1000.00..16609.10 rows=1 width=8)
         Workers Planned: 2
         ->  Parallel Seq Scan on d  (cost=0.00..15609.00 rows=1 width=8)
               Filter: ((id >= '1'::double precision) AND (id <= '10'::double precision))
rows

当预测的目标行数较大时：

  1. 每个 Worker 扫描的行经过 parallel sequential scan 节点处理后，在 aggregate 节点进行部分聚合（partial aggregation）。
  2. 这些中间聚合结果在 gather 节点被汇集。
  3. 最后在 finalize aggregate 节点做最终聚合。

请看以下示例：
