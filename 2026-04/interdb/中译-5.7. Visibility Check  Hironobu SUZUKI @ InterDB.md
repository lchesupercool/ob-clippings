## 5.7. 可见性检查（Visibility Check）

本节描述 PostgreSQL 如何执行可见性检查，也就是在给定事务中挑出合适版本的 heap tuple 的过程。本节还会描述 PostgreSQL 如何防止 ANSI SQL-92 标准中所定义的异常现象：脏读（Dirty Reads）、不可重复读（Repeatable Reads）以及幻读（Phantom Reads）。

### 5.7.1. 可见性检查

图 5.10 展示了一个用于说明可见性检查的场景。

![](https://www.interdb.jp/pg/pgsql05/fig-5-10.png)

图 5.10. 用于说明可见性检查的场景。

在图 5.10 所示的场景中，SQL 命令按以下时间顺序执行。

- **T1：** 启动事务（txid 200）
- **T2：** 启动事务（txid 201)
- **T3：** 执行 txid 200 和 201 的 SELECT 命令
- **T4：** 执行 txid 200 的 UPDATE 命令
- **T5：** 执行 txid 200 和 201 的 SELECT 命令
- **T6：** 提交 txid 200
- **T7：** 执行 txid 201 的 SELECT 命令

为简化描述，假定这里只有两个事务，即 txid 200 和 201。txid 200 的隔离级别是 READ COMMITTED，txid 201 的隔离级别是 READ COMMITTED 或 REPEATABLE READ 之一。

我们接下来考察 SELECT 命令如何对每条 tuple 执行可见性检查。

**T3 的 SELECT 命令：**

在 T3 时刻，表 'tbl' 里只有 Tuple\_1，并且它由于 **Rule 6** 而*可见*。因此，两个事务中的 SELECT 命令都返回 'Jekyll'。

- Rule6(Tuple\_1) ⇒ $⇒$ $\Rightarrow$ Status(t\_xmin:199) = COMMITTED ∧ $∧$ $\wedge$ t\_xmax = INVALID ⇒ $⇒$ $\Rightarrow$ Visible

```sql
testdb=# -- txid 200
testdb=# SELECT * FROM tbl;
  name
--------
 Jekyll
row
```

```sql
testdb=# -- txid 201
testdb=# SELECT * FROM tbl;
  name
--------
 Jekyll
row
```

**T5 的 SELECT 命令：**

首先考察由 txid 200 执行的 SELECT 命令。Tuple\_1 由于 **Rule 7** 而不可见，Tuple\_2 由于 **Rule 2** 而可见。因此，这条 SELECT 命令返回 'Hyde'。

- Rule7(Tuple\_1)：Status(t\_xmin:199) = COMMITTED ∧ $∧$ $\wedge$ Status(t\_xmax:200) = IN\_PROGRESS ∧ $∧$ $\wedge$ t\_xmax:200 = current\_txid:200 ⇒ $⇒$ $\Rightarrow$ Invisible
- Rule2(Tuple\_2)：Status(t\_xmin:200) = IN\_PROGRESS ∧ $∧$ $\wedge$ t\_xmin:200 = current\_txid:200 ∧ $∧$ $\wedge$ t\_xmax = INVALID ⇒ $⇒$ $\Rightarrow$ Visible

```sql
testdb=# -- txid 200
testdb=# SELECT * FROM tbl;
 name
------
 Hyde
row
```

另一方面，在由 txid 201 执行的 SELECT 命令中，Tuple\_1 由于 **Rule 8** 而可见，Tuple\_2 由于 **Rule 4** 而不可见。因此，这条 SELECT 命令返回 'Jekyll'。

- Rule8(Tuple\_1)：Status(t\_xmin:199) = COMMITTED ∧ $∧$ $\wedge$ Status(t\_xmax:200) = IN\_PROGRESS ∧ $∧$ $\wedge$ t\_xmax:200 ≠ $≠$ $\ne$ current\_txid:201 ⇒ $⇒$ $\Rightarrow$ Visible
- Rule4(Tuple\_2)：Status(t\_xmin:200) = IN\_PROGRESS ∧ $∧$ $\wedge$ t\_xmin:200 ≠ $≠$ $\ne$ current\_txid:201 ⇒ $⇒$ $\Rightarrow$ Invisible

```sql
testdb=# -- txid 201
testdb=# SELECT * FROM tbl;
  name
--------
 Jekyll
row
```

如果被更新的 tuple 在提交之前就能被其他事务看到，这种现象就被称为**脏读（Dirty Reads）**，也叫作 **wr-conflicts**。不过，如上所示，在 PostgreSQL 中任何隔离级别下都不会出现脏读。

**T7 的 SELECT 命令：**

下面描述 T7 的 SELECT 命令在两种隔离级别下各自的行为。

当 txid 201 处于 READ COMMITTED 级别时，由于事务快照是 '201:201:'，txid 200 被视为 COMMITTED。因此，Tuple\_1 由于 **Rule 10** 而*不可见*，Tuple\_2 由于 **Rule 6** 而*可见*。这条 SELECT 命令返回 'Hyde'。

- Rule10(Tuple\_1)：Status(t\_xmin:199) = COMMITTED ∧ $∧$ $\wedge$ Status(t\_xmax:200) = COMMITTED ∧ $∧$ $\wedge$ Snapshot(t\_xmax:200) ≠ $≠$ $\ne$ active ⇒ $⇒$ $\Rightarrow$ Invisible
- Rule6(Tuple\_2)：Status(t\_xmin:200) = COMMITTED ∧ $∧$ $\wedge$ t\_xmax = INVALID ⇒ $⇒$ $\Rightarrow$ Visible

```sql
testdb=# -- txid 201 (READ COMMITTED)
testdb=# SELECT * FROM tbl;
 name
------
 Hyde
row
```

注意，在 txid 200 提交前后执行的这两次 SELECT 命令返回的结果是不一样的。这种现象通常被称为**不可重复读（Non-Repeatable Reads）**。

与此相反，当 txid 201 处于 REPEATABLE READ 级别时，由于事务快照是 '200:200:'，txid 200 必须被视为 IN\_PROGRESS。因此，Tuple\_1 由于 **Rule 9** 而*可见*，Tuple\_2 由于 **Rule 5** 而*不可见*。这条 SELECT 命令返回 'Jekyll'。

注意，在 REPEATABLE READ（和 SERIALIZABLE）级别下不会出现不可重复读。

- Rule9(Tuple\_1)：Status(t\_xmin:199) = COMMITTED ∧ $∧$ $\wedge$ Status(t\_xmax:200) = COMMITTED ∧ $∧$ $\wedge$ Snapshot(t\_xmax:200) = active ⇒ $⇒$ $\Rightarrow$ Visible
- Rule5(Tuple\_2)：Status(t\_xmin:200) = COMMITTED ∧ $∧$ $\wedge$ Snapshot(t\_xmin:200) = active ⇒ $⇒$ $\Rightarrow$ Invisible

```sql
testdb=# -- txid 201 (REPEATABLE READ)
testdb=# SELECT * FROM tbl;
  name
--------
 Jekyll
row
```

### 5.7.2. Hint Bits

为了获取一个事务的状态，PostgreSQL 内部提供了三个函数：==TransactionIdIsInProgress()==、==TransactionIdDidCommit()，以及 TransactionIdDidAbort()。==这些函数的实现已经做了优化，例如通过 cache 来减少对 clog 的频繁访问。然而，如果每次检查每条 tuple 时都执行它们，仍然会出现瓶颈。

为解决这一问题，PostgreSQL 使用了 *hint bits*，如下所示：

```sql
#define HEAP_XMIN_COMMITTED       0x0100   /* t_xmin committed */
#define HEAP_XMIN_INVALID         0x0200   /* t_xmin invalid/aborted */
#define HEAP_XMAX_COMMITTED       0x0400   /* t_xmax committed */
#define HEAP_XMAX_INVALID         0x0800   /* t_xmax invalid/aborted */
```

在读取或写入一条 tuple 时，PostgreSQL 会在条件允许的情况下把 hint bit 设置到该 tuple 的 t\_informask 上。

比如，假设 PostgreSQL 检查某条 tuple 的 t\_xmin 的状态并得到 COMMITTED。那么在这种情况下，PostgreSQL 就会把 hint bit HEAP\_XMIN\_COMMITTED 设置到该 tuple 的 t\_infomask 上。

如果 hint bits 已经被设置好，就不再需要 TransactionIdDidCommit() 和 TransactionIdDidAbort()。因此，PostgreSQL 可以高效地检查每条 tuple 的 t\_xmin 和 t\_xmax 的状态。

### 5.7.3. PostgreSQL REPEATABLE READ 级别下的幻读

ANSI SQL-92 标准定义的 REPEATABLE READ 是允许**幻读（Phantom Reads）**的。然而，PostgreSQL 的实现并不允许幻读。原则上，SI（快照隔离）是不允许幻读的。

假设有两个事务，即 Tx\_A 和 Tx\_B，并发运行。它们的隔离级别分别是 READ COMMITTED 和 REPEATABLE READ，txid 分别是 100 和 101。首先，Tx\_A 插入一条 tuple，然后它被提交。该插入 tuple 的 t\_xmin 是 100。

接下来，Tx\_B 执行一条 SELECT 命令；然而，由 Tx\_A 插入的那条 tuple 由于 **Rule 5** 而*不可见*。因此，幻读不会发生。

- Rule5(new tuple)：Status(t\_xmin:100) = COMMITTED ∧ $∧$ $\wedge$ Snapshot(t\_xmin:100) = active ⇒ $⇒$ $\Rightarrow$ Invisible

```sql
testdb=# -- Tx_A: txid 100
testdb=# START TRANSACTION
testdb-#  ISOLATION LEVEL READ COMMITTED;
START TRANSACTION
testdb=# SELECT txid_current();
 txid_current
--------------
          100
row

testdb=# INSERT INTO tbl(id, data)
                VALUES (1,'phantom');
INSERT 1
testdb=# COMMIT;
COMMIT
```

```sql
testdb=# -- Tx_B: txid 101
testdb=# START TRANSACTION
testdb-#  ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION
testdb=# SELECT txid_current();
 txid_current
--------------
          101
row

testdb=# SELECT * FROM tbl WHERE id=1;
 id | data
----+------
(0 rows)
```
