5.5. Transaction Snapshot

transaction snapshot 是一个数据集，用于为某个单独的事务保存在某一时间点所有事务是否处于 active 状态的信息。这里 active 事务是指仍在进行中或尚未启动的事务。

PostgreSQL 在内部将 transaction snapshot 的文本表示格式定义为 '100:100:'。例如，'100:100:' 表示 "小于等于 99 的 txid 不是 active 的，而大于等于 100 的 txid 是 active 的"。

在下文的描述中，都会使用这种便利的表示形式。如果你对它不熟悉，请参阅下文。

内置函数 pg_current_snapshot 及其文本表示格式

该函数 pg_current_snapshot 展示当前事务的 snapshot。

testdb=# SELECT pg_current_snapshot();
 pg_current_snapshot
---------------------
 100:104:100,102
row

txid_current_snapshot 的文本表示形式为 'xmin:xmax:xip_list'，各部分说明如下：

  • xmin （仍然 active 的最早的 txid）：所有更早的事务要么已经提交且可见，要么已经回滚且 dead。
  • xmax （首个尚未分配的 txid）：所有大于等于该值的 txid 在 snapshot 建立时尚未开始，因此不可见。
  • xip_list （snapshot 建立时 active 的事务 id 列表）：该列表只包含 xmin 和 xmax 之间 active 的 txid。

例如，在 snapshot '100:104:100,102' 中，xmin 为 '100'，xmax 为 '104'，xip_list 为 '100,102'。

下面给出两个具体例子：

图 5.8. transaction snapshot 表示的示例。

第一个示例是 '100:100:'。该 snapshot 含义如下（图 5.8(a)）：

  • 小于等于 99 的 txid 不是 active，因为 xmin 是 100。
  • 大于等于 100 的 txid 是 active，因为 xmax 是 100。

第二个示例是 '100:104:100,102'。该 snapshot 含义如下（图 5.8(b)）：

  • 小于等于 99 的 txid 不是 active。
  • 大于等于 104 的 txid 是 active。
  • txid 100 和 102 是 active，因为它们存在于 xip 列表中；而 txid 101 和 103 不是 active。

transaction snapshot 由 transaction manager 提供。在 READ COMMITTED isolation level 下，事务每次执行 ==SQL command 时都会获取一个 snapshot==；否则（REPEATABLE READ 或 SERIALIZABLE）事务只在执行 ==第一条 SQL command== 时获取一次 snapshot。获取到的 transaction snapshot 用于 tuple 的可见性检查，详见 Section 5.7。

当使用获取到的 snapshot 进行可见性检查时，即便 snapshot 中 active 的事务实际上已经提交或中止，也必须将它们视为 in progress。这条规则很重要，因为它导致了 READ COMMITTED 与 REPEATABLE READ（或 SERIALIZABLE）之间的行为差异。我们在下文各节中会反复引用这条规则。

本节其余部分将通过图 5.9 所示的具体场景来描述 transaction manager 和事务。

图 5.9. transaction manager 与事务。

transaction manager 始终持有当前正在运行的事务信息。假设有三个事务依次启动，Transaction_A 和 Transaction_B 的 isolation level 是 READ COMMITTED，Transaction_C 的 isolation level 是 REPEATABLE READ。

  • T1： Transaction_A 启动并执行第一条 SELECT 命令。执行第一条命令时，Transaction_A 请求此刻的 txid 和 snapshot。 在这个场景中，transaction manager 分配 txid 200，并返回 transaction snapshot '200:200:'。
  • T2： Transaction_B 启动并执行第一条 SELECT 命令。transaction manager 分配 txid 201，并返回 transaction snapshot '200:200:'，因为 Transaction_A（txid 200）仍在进行中。因此，Transaction_B 看不到 Transaction_A。
  • T3： Transaction_C 启动并执行第一条 SELECT 命令。transaction manager 分配 txid 202，并返回 transaction snapshot '200:200:'，因此 Transaction_C 看不到 Transaction_A 和 Transaction_B。
  • T4： Transaction_A 已提交。transaction manager 移除该事务的相关信息。
  • T5： Transaction_B 和 Transaction_C 各自执行它们的 SELECT 命令。 Transaction_B 需要一个 transaction snapshot，因为它处于 READ COMMITTED level。 在这个场景中，Transaction_B 获得新的 snapshot '201:201:'，因为 Transaction_A（txid 200）已提交。因此，Transaction_A 对 Transaction_B 不再不可见。 相对地，Transaction_C 不需要新的 transaction snapshot，因为它处于 REPEATABLE READ level，会沿用此前获得的 snapshot，即 '200:200:'。因此，Transaction_A 对 Transaction_C 仍然不可见。
