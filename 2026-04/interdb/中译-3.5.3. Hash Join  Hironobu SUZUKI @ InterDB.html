3.5.3. Hash Join

与 merge join 类似，hash join 也只能用于自然连接（natural join）和等值连接（equi-join）。

PostgreSQL 中的 hash join 会根据表的大小而表现出不同的行为。如果目标表足够小（更准确地说，如果 inner table 的大小不超过 work_mem 的 25%），则会采用简单的两阶段 in-memory hash join。否则，将采用配合 skew 方法的 hybrid hash join。

本小节将描述 PostgreSQL 中这两种 hash join 的执行过程。

关于代价估算的讨论被省略了，因为它相当复杂。粗略地说，如果假设在 hash table 中查找和插入时没有冲突，那么 start-up cost 和 run cost 都是 O(Nouter+Ninner) $O(N_{outer} + N_{inner})$。

3.5.3.1. In-Memory Hash Join

本小节描述 in-memory hash join。

这种 in-memory hash join 是在 work_mem 中处理的，其 hash table 所在区域在 PostgreSQL 中称为 batch。一个 batch 含有若干 hash slot，内部称为 bucket，bucket 的数量由定义于 nodeHash.c 中的 ExecChooseHashTableSize() 函数决定；bucket 的数量总是 2n $2^{n}$，其中 n $n$ 是整数。

In-memory hash join 有两个阶段：build 阶段和 probe 阶段。在 build 阶段，inner table 的所有 tuple 都被插入到一个 batch 中；在 probe 阶段，outer table 的每个 tuple 都会与 batch 中的 inner tuple 进行比较，如果满足连接条件则完成连接。

下面给出一个具体示例以便清楚地理解该操作。假设使用 hash join 执行下面所示的查询。

testdb=# SELECT * FROM tbl_outer AS outer, tbl_inner AS inner WHERE inner.attr1 = outer.attr2;

下面展示 hash join 的操作过程。参见图 3.26 和图 3.27。

图 3.26. In-memory hash join 的 build 阶段。

  • (1) 在 work_mem 上创建一个 batch。 在本示例中，该 batch 有 8 个 bucket，即 bucket 的数量为 23 $2^{3}$。
  • (2) 将 inner table 的第一个 tuple 插入到 batch 的对应 bucket 中。 详细步骤如下：
    1. 计算第一个 tuple 中参与连接条件的那个属性的 hash-key。 在本例中，因为 WHERE 子句是 'inner.attr1 = outer.attr2'，所以第一个 tuple 的属性 'attr1' 的 hash-key 是使用内置的 hash 函数计算得到的。
      1. 将第一个 tuple 插入到对应的 bucket 中。 假设第一个 tuple 的 hash-key 用二进制表示为 '0x000…001'，也就是说其最后三位是 '001'。这种情况下，该 tuple 会被插入到 key 为 '001' 的 bucket 中。

在本文档中，这种用于构建 batch 的插入操作以如下符号表示：⊕ $\oplus$

  • (3) 将 inner table 剩余的 tuple 依次插入。

图 3.27. In-memory hash join 的 probe 阶段。

  • (4) 对 outer table 的第一个 tuple 进行 probe。 详细步骤如下：

    1. 计算 outer table 第一个 tuple 中参与连接条件的那个属性的 hash key。 在本例中，假设第一个 tuple 的属性 'attr2' 的 hash-key 为 '0x000…100'；也就是说，最后三位是 '100'。

      1. 将 outer table 的第一个 tuple 与 batch 中的 inner tuple 进行比较，若满足连接条件则将 tuple 连接。 因为第一个 tuple 的 hash-key 最后三位是 '100'，所以执行器会取出 key 为 '100' 的 bucket 中的 tuple，并根据连接条件（由 WHERE 子句定义）比较两表各自指定属性的值。 如果连接条件满足，outer table 的第一个 tuple 将与 inner table 对应的 tuple 进行连接；否则，执行器什么也不做。

      在本例中，key 为 '100' 的 bucket 中有 Tuple_C。如果 Tuple_C 的 attr1 等于第一个 tuple（Tuple_W）的 attr2，那么 Tuple_C 和 Tuple_W 将被连接并保存到内存或临时文件中。

      在本文档中，这种 probe batch 的操作以如下符号表示：⊗ $\otimes$ - (5) 对 outer table 剩余的 tuple 依次进行 probe。

3.5.3.2. Hybrid Hash Join with Skew

当 inner table 的 tuple 无法在 work_mem 中用一个 batch 装下时，PostgreSQL 会使用配合 skew 算法的 hybrid hash join，这是基于 hybrid hash join 的一个变体。

首先，介绍 hybrid hash join 的基本概念。在第一轮 build 和 probe 阶段中，PostgreSQL 会准备多个 batch。batch 的数量与 bucket 的数量相同，由 ExecChooseHashTableSize() 函数决定。它总是 2m $2^{m}$，其中 m $m$ 为整数。在此阶段，只有一个 batch 分配在 work_mem 中，其他 batch 则以临时文件的形式创建。属于这些 batch 的 tuple 会被写入对应的文件并利用临时 tuple 存储功能保存下来。

图 3.28 展示了 tuple 如何被存储到四个（= 22 $2^{2}$）batch 中。在这种情况下，每个 tuple 存入哪个 batch 是由其 hash-key 最后 5 位中的前两位决定的，因为 bucket 和 batch 的规模分别是 23 $2^{3}$ 和 22 $2^{2}$。Batch_0 存储 hash-key 最后 5 位介于 ' 00 000' 到 ' 00 111' 之间的 tuple，Batch_1 存储 hash-key 最后 5 位介于 ' 01 000' 到 ' 01 111' 之间的 tuple，依此类推。

图 3.28. Hybrid hash join 中的多个 batch。

在 hybrid hash join 中，build 和 probe 阶段执行的次数与 batch 的数量相同，因为 inner 表和 outer 表被存储到了数量相同的 batch 中。在 build 和 probe 的第一轮中，不仅会创建每一个 batch，还会处理 inner 表和 outer 表各自的第一个 batch。另一方面，第二轮及后续各轮的处理需要向/从临时文件进行写入和重新加载，因此这些过程代价较高。为此，PostgreSQL 还额外准备了一个称为 skew 的特殊 batch，以便在第一轮中更高效地处理大量 tuple。

skew batch 存储的是这样一些 inner table tuple：它们将会和那些在连接条件所涉属性上具有较大 MCV 值的 outer table tuple 进行连接。不过，这种解释可能不太容易理解，因此下面用一个具体例子来说明。

假设有两张表：customers 和 purchase_history。

  • customers 表有两个属性：'name' 和 'address'。
  • purchase_history 表有两个属性：'customer_name' 和 'purchased_item'。
  • customers 表有 10,000 行，purchase_history 表有 1,000,000 行。
  • 前 10% 的客户购买了全部商品中的 70%。

在这些假设下，我们来看一下当执行下面所示的查询时，hybrid hash join with skew 在第一轮中的表现。

testdb=# SELECT * FROM customers AS c, purchase_history AS h WHERE c.name = h.customer_name;

如果 customers 表是 inner、purchase_history 表是 outer，那么根据 purchase_history 表的 MCV 值，前 10% 的 customer 会被存入 skew batch。注意，这里参考的是 outer table 的 MCV 值来向 skew batch 插入 inner table 的 tuple。在第一轮的 probe 阶段，outer table（purchase_history）中 70% 的 tuple 会与存储在 skew batch 里的 tuple 进行连接。由此可见，outer table 的分布越不均匀，在第一轮中能处理的 outer table tuple 就越多。

下面展示 hybrid hash join with skew 的工作过程。参见图 3.29 到图 3.32。

图 3.29. 第一轮中 hybrid hash join 的 build 阶段。

  • (1) 在 work_mem 上创建一个 batch 和一个 skew batch。
  • (2) 创建用于存储 inner table tuple 的临时 batch 文件。 在本例中创建了三个 batch 文件，因为 inner table 将被划分为四个 batch。
  • (3) 对 inner table 的第一个 tuple 执行 build 操作。 详细步骤如下：
    1. 如果第一个 tuple 应该插入到 skew batch，则执行插入。否则进入步骤 2。 在上面所述的示例中，如果第一个 tuple 属于前 10% 的 customer，就把它插入到 skew batch。
      1. 计算第一个 tuple 的 hash key，然后将其插入到对应的 batch 中。
  • (4) 对 inner table 剩余的 tuple 执行 build 操作。

图 3.30. 第一轮中 hybrid hash join 的 probe 阶段。

  • (5) 创建用于存储 outer table tuple 的临时 batch 文件。
  • (6) 如果第一个 tuple 的 MCV 值较大，则对其执行与 skew batch 的 probe 操作。否则进入步骤 (7)。 在上面所述的示例中，如果第一个 tuple 是前 10% 客户的购买数据，则将其与 skew batch 中的 tuple 进行比较。
  • (7) 对第一个 tuple 执行 probe 操作。 根据第一个 tuple 的 hash-key 值，执行以下过程：
    • 如果第一个 tuple 属于 Batch_0，则执行 probe 操作。
      • 否则，将其插入对应的 batch 中。
  • (8) 对 outer table 剩余的 tuple 执行 probe 操作。 注意，在本例中，outer table 有 70% 的 tuple 已经在第一轮中通过 skew 完成处理，而无需向/从临时文件进行写入与读取。

图 3.31. 第二轮的 build 和 probe 阶段。

  • (9) 移除 skew batch，清空 Batch_0，为第二轮做准备。
  • (10) 对 batch 文件 'batch_1_in' 执行 build 操作。
  • (11) 对存储在 batch 文件 'batch_1_out' 中的 tuple 执行 probe 操作。

图 3.32. 第三轮与最后一轮的 build 和 probe 阶段。

  • (12) 使用 batch 文件 'batch_2_in' 和 'batch_2_out' 执行 build 和 probe 操作。
  • (13) 使用 batch 文件 'batch_3_in' 和 'batch_3_out' 执行 build 和 probe 操作。

3.5.3.3. Index Scans in Hash Join

PostgreSQL 中的 Hash join 会在可能的情况下使用 index scan。下面给出一个具体示例。

testdb=# EXPLAIN SELECT * FROM pgbench_accounts AS a, pgbench_branches AS b
testdb-#                                              WHERE a.bid = b.bid AND a.aid BETWEEN 100 AND 1000;
                                                QUERY PLAN
----------------------------------------------------------------------------------------------------------
 Hash Join  (cost=1.88..51.93 rows=865 width=461)
   Hash Cond: (a.bid = b.bid)
   ->  Index Scan using pgbench_accounts_pkey on pgbench_accounts a  (cost=0.43..47.73 rows=865 width=97)
         Index Cond: ((aid >= 100) AND (aid <= 1000))
   ->  Hash  (cost=1.20..1.20 rows=20 width=364)
         ->  Seq Scan on pgbench_branches b  (cost=0.00..1.20 rows=20 width=364)
rows
  • 第 7 行：在 probe 阶段，PostgreSQL 在扫描 pgbench_accounts 表时使用了 index scan，因为 WHERE 子句中存在针对带有索引的列 'aid' 的条件。
