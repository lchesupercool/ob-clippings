3.2. 单表查询的代价估算

PostgreSQL 的查询优化基于 cost。Cost 是无量纲的数值，并不是绝对的性能指标，而是用来比较各种操作之间相对性能的指标。

Cost 由以下文件中定义的函数来估算 costsize.c。执行器所执行的每一种操作都有对应的 cost 函数。例如，sequential scan 和 index scan 的 cost 分别由 cost_seqscan() 和 cost_index() 估算。

在 PostgreSQL 中，cost 分为三种：start-up、run 和 total。Total cost 是 start-up cost 与 run cost 之和，因此只需独立估算 start-up cost 和 run cost。

  • start-up cost 是在获取第一条 tuple 之前所花费的代价。例如，index scan 节点的 start-up cost 就是为访问目标表中第一条 tuple 而读取 index page 的代价。
  • run cost 是获取所有 tuple 所花费的代价。
  • total cost 是 start-up cost 与 run cost 之和。

以下命令 EXPLAIN 会显示每个操作的 start-up cost 和 total cost。下面是一个最简单的示例：

testdb=# EXPLAIN SELECT * FROM tbl;
                       QUERY PLAN
---------------------------------------------------------
 Seq Scan on tbl  (cost=0.00..145.00 rows=10000 width=8)
row

在第 4 行，该命令显示了关于 sequential scan 的信息。在 cost 部分，有两个数值：0.00 和 145.00。在这个例子中，start-up cost 和 total cost 分别是 0.00 和 145.00。

在本节中，我们将详细探讨如何估算 sequential scan、index scan 以及 sort 操作的代价。

在下面的说明中，我们会使用如下所示的一张具体的表和一个索引：

testdb=# CREATE TABLE tbl (id int PRIMARY KEY, data int);
testdb=# CREATE INDEX tbl_data_idx ON tbl (data);
testdb=# INSERT INTO tbl SELECT generate_series(1,10000),generate_series(1,10000);
testdb=# ANALYZE;
testdb=# \d tbl

3.2.1. Sequential Scan

Sequential scan 的 cost 由 cost_seqscan() 函数估算。在本小节中，我们将探讨如何估算下面这个查询的 sequential scan cost：

testdb=# SELECT * FROM tbl WHERE id <= 8000;

在 sequential scan 中，start-up cost 等于 0，而 run cost 由下面的等式定义：

$$ '\text{run cost}' & = '\text{cpu run cost}' + '\text{disk run cost}' \ = \left(\right. \text{cpu}\text{tuple}\text{cost} + \text{cpu}\text{operator}\text{cost} \left.\right) \times N_{t u p l e} + \text{seq}\text{page}\text{cost} \times N_{p a g e} $$

其中 seq_page_cost、 cpu_tuple_cost 和 cpu_operator_cost 在 postgresql.conf 文件中设置，默认值分别为 1.0、0.01 和 0.0025。Ntuple $Ntuple$ $N_{tuple}$ 和 Npage $Npage$ $N_{page}$ 分别是这张表的所有 tuple 数和所有 page 数。这些数值可以通过下面的查询得到：

testdb=# SELECT relpages, reltuples FROM pg_class WHERE relname = 'tbl';
 relpages | reltuples
----------+-----------
       45 |     10000
row

$$ (\text{1}) N_{t u p l e} = 10000 \ (\text{2}) N_{p a g e} = 45 $$

因此，

$$ '\text{run cost}' & = \left(\right. 0.01 + 0.0025 \left.\right) \times 10000 + 1.0 \times 45 = 170.0 $$

最终，

$$ '\text{total cost}' = 0.0 + 170.0 = 170 $$

为了验证，上述查询的 EXPLAIN 命令结果如下所示：

testdb=# EXPLAIN SELECT * FROM tbl WHERE id <= 8000;
                       QUERY PLAN
--------------------------------------------------------
 Seq Scan on tbl  (cost=0.00..170.00 rows=8000 width=8)
   Filter: (id <= 8000)
rows

在第 4 行，我们可以看到 start-up cost 和 total cost 分别为 0.00 和 170.00。同时也估算出通过扫描所有行，会选出 8000 行（tuple）。

在第 5 行，显示了 sequential scan 的一个过滤条件 ‘ Filter:(id<=8000) $Filter:(id<=8000)$ $\text{Filter}:(\text{id} \lt= 8000)$ ’。更准确地说，它被称为 table level filter predicate（表级过滤谓词）。

需要注意的是，这类 filter 是在读取表中所有 tuple 时使用的，它并不会缩小所扫描的 table page 的范围。

Info

从上面 run cost 的估算可以看出，PostgreSQL 假定所有 page 都将从存储中读取。换句话说，PostgreSQL 并不考虑被扫描的 page 是否已经位于 shared buffers 中。

3.2.2.1. 启动代价（Start-Up Cost）

索引扫描的启动代价是指读取索引页以访问目标表中第一个元组所花费的代价。它由下面的公式定义：

$$ '\text{start}-\text{up cost}' = \left{\right. ceil \left(\right. log_{2} ⁡ \left(\right. N_{i n d e x , t u p l e} \left.\right) \left.\right) + \left(\right. H_{i n d e x} + 1 \left.\right) \times 50 \left.\right} \times \text{cpu}\text{operator}\text{cost} $$

其中 $H_{index}$ 是索引树的高度。这一计算的详细说明在 btcostestimate() 的注释中给出。

在本例中，根据 (3)，Nindex,tuple $Nindex,tuple$ $N_{index,tuple}$ 为 10000，Hindex $Hindex$ $H_{index}$ 为 1；cpu_operator_cost $cpu_operator_cost$ $\text{cpu_operator_cost}$ 为 0.0025 $0.0025$ $0.0025$（默认值）。因此，

$$ (\text{5}) '\text{start}-\text{up cost}' = \left{\right. ceil \left(\right. log_{2} ⁡ \left(\right. 10000 \left.\right) \left.\right) + \left(\right. 1 + 1 \left.\right) \times 50 \left.\right} \times 0.0025 = 0.285 $$

3.2.2.2. 运行代价（Run Cost）

索引扫描的运行代价是表和索引的 CPU 代价与 I/O（输入/输出）代价之和：

$$ '\text{run cost}' & = \left(\right. '\text{index cpu cost}' + '\text{table cpu cost}' \left.\right) + \left(\right. '\text{index IO cost}' + '\text{table IO cost}' \left.\right) . $$

Info

如果可以应用 Index-Only Scans （在 Section 7.2 中描述），那么 ’table cpu cost’ $’table cpu cost’$ $\text{’table cpu cost’}$ 和 ’table IO cost’ $’table IO cost’$ $\text{’table IO cost’}$ 不会被估算。

前三项代价（即 index CPU cost、table CPU cost 和 index I/O cost）如下所示：

$$ '\text{index cpu cost}' & = \text{Selectivity} \times N_{i n d e x , t u p l e} \times \left(\right. \text{cpu}\text{index}\text{tuple}\text{cost} + \text{qual}\text{op}\text{cost} \left.\right) \ '\text{table cpu cost}' & = \text{Selectivity} \times N{t u p l e} \times \text{cpu}\text{tuple}\text{cost} \ '\text{index IO cost}' & = ceil \left(\right. \text{Selectivity} \times N_{i n d e x , p a g e} \left.\right) \times \text{random}\text{page}\text{cost} $$

其中：

  • cpu_index_tuple_cost 和 random_page_cost 在 postgresql.conf 文件中设置。默认值分别为 0.005 和 4.0。
  • qual_op_cost $qual_op_cost$ $\text{qual_op_cost}$ 大致是指评估索引谓词（index predicate）的代价。默认值为 0.0025。
  • Selectivity $Selectivity$ $\text{Selectivity}$ 是索引搜索范围中满足 WHERE 子句的比例，它是介于 0 和 1 之间的浮点数。 (Selectivity×Ntuple) $(Selectivity×Ntuple)$ $(\text{Selectivity} \times N_{tuple})$ 表示需要读取的表 tuple 数量； (Selectivity×Nindex,page) $(Selectivity×Nindex,page)$ $(\text{Selectivity} \times N_{index,page})$ 表示需要读取的索引 page 数量。

selectivity 的具体内容在下面详细描述。

在第 4 行，我们可以看到 start-up cost 和 total cost 分别为 0.29 和 13.49，且估算将扫描 240 行（tuple）。

在第 5 行，展示了 index scan 的一个 index 条件 ' IndexCond:(data<=240) $IndexCond:(data<=240)$ $\text{Index} \text{Cond}:(\text{data} \lt= 240)$ '。更准确地说，这个条件称为 access predicate，它表达了 index scan 的起止条件。

根据这篇 post，PostgreSQL 中的 EXPLAIN 命令并不区分 access predicate 和 index filter predicate。因此，在分析 EXPLAIN 的输出时，同时考虑 index 条件和 rows 的估算值是很重要的。

seq_page_cost 和 random_page_cost 的默认值分别为 1.0 和 4.0。

这意味着 PostgreSQL 假定 random scan 比 sequential scan 慢四倍。换言之，PostgreSQL 的默认值是基于使用 HDD 设定的。

另一方面，近些年来，由于 SSD 被广泛使用，random_page_cost 的默认值就显得过大了。如果在使用 SSD 的情况下仍沿用 random_page_cost 的默认值，planner 可能会选择低效的执行计划。因此，在使用 SSD 时，最好将 random_page_cost 的值改为 1.0。

This blog 报告了使用 random_page_cost 默认值时出现的问题。

3.2.3. Sort

sort path 用于排序操作，例如 ORDER BY、merge join 操作的预处理以及其他功能。排序的成本通过 cost_sort() 函数来估算。

在排序操作中，如果所有待排序的 tuple 都能放入 work_mem，则使用 quicksort 算法。否则，会创建一个临时文件，并使用 file merge sort 算法。

sort path 的 start-up cost 是对目标 tuple 进行排序的成本。因此，该成本为 O(Nsort×log2(Nsort)) $O(Nsort×log2⁡(Nsort))$ $O(N_{sort} \times \log_2(N_{sort}))$，其中 Nsort $Nsort$ $N_{sort}$ 是待排序 tuple 的数量。sort path 的 run cost 是读取已排序 tuple 的成本。因此，该成本为 O(Nsort) $O(Nsort)$ $O(N_{sort})$。

在本小节中，我们将探讨如何估算以下查询的排序成本。假设该查询在 work_mem 中完成排序，不使用临时文件。

testdb=# SELECT id, data FROM tbl WHERE data <= 240 ORDER BY id;

在这种情况下，start-up cost 由以下方程定义：

$$ '\text{start}-\text{up cost}' = C + \text{comparison}\text{cost} \times N{s o r t} \times log_{2} ⁡ \left(\right. N_{s o r t} \left.\right) $$

其中：

  • C $C$ $C$ 是上一次扫描的 total cost，也就是 index scan 的 total cost；根据 (15)，其值为 13.485。
  • Nsort $Nsort$ $N_{sort}$ 是待排序 tuple 的数量。在本例中为 240。
  • comparison_cost $comparison_cost$ $\text{comparison_cost}$ 被定义为 2×cpu_operator_cost $2×cpu_operator_cost$ $2 \times \text{cpu_operator_cost}$。

因此，start-up cost $start-up cost$ $\text{start-up cost}$ 的计算如下：

$$ '\text{start}-\text{up cost}' = 13.485 + \left(\right. 2 \times 0.0025 \left.\right) \times 240.0 \times log_{2} ⁡ \left(\right. 240.0 \left.\right) = 22.973 $$

run cost $run cost$ $\text{run cost}$ 是在内存中读取已排序 tuple 的成本。因此：

$$ '\text{run cost}' = \text{cpu}\text{operator}\text{cost} \times N_{s o r t} = 0.0025 \times 240 = 0.6 $$

最后：

$$ '\text{total cost}' = 22.973 + 0.6 = 23.573 $$

为了验证，上述 SELECT 查询的 EXPLAIN 命令结果如下所示：

testdb=# EXPLAIN SELECT id, data FROM tbl WHERE data <= 240 ORDER BY id;
                                   QUERY PLAN
---------------------------------------------------------------------------------

   Sort Key: id
   ->  Index Scan using tbl_data_idx on tbl  (cost=0.29..13.49 rows=240 width=8)
         Index Cond: (data <= 240)
rows

在第 4 行，我们可以看到 start-up cost 和 total cost 分别为 22.97 和 23.57。

3.2.4. Cardinality 估算

前面的讨论假定 Selectivity 可以被准确地确定。然而在现实中，selectivity 估算从早期至今一直是数据库系统中最持久、最具挑战性的问题之一。

3.2.4.1. Selectivity 与 Cardinality

虽然 PostgreSQL 在内部使用 Selectivity，但数据库领域通常关注 Cardinality。Cardinality 是一个整数，selectivity 与 cardinality 之间的关系定义为：

Selectivity=CardinalityNtuple $$ Selectivity=CardinalityNtuple $$

$$ \text{Selectivity} = \frac{\text{Cardinality}}{N_{\text{tuple}}} $$

其中 Ntuple $Ntuple$ $N_{\text{tuple}}$ 是表中 tuple（行）的总数。后文将主要使用 Cardinality。

3.2.4.2. 展示 Cardinality 估算的困难之处

我们通过一个具体的例子来说明 Cardinality 估算的困难。考虑一个包含 100 位村民 的数据库。residents 表记录了他们的 age（年龄）类别（under18、young、middle、elder）以及驾驶 license（执照）状态（none、standard、gold）。（这里的 "gold license" 是日本对连续五年无事故、无违章驾驶员所颁发执照的称呼。）

3.2.4.3. 初次估算失败（未感知 correlation）

接下来执行一条 SELECT 语句，检索所有属于 under18 且 没有执照（none） 的居民。使用 EXPLAIN ANALYZE 来对比 planner 的估算值与实际值。

testdb=# EXPLAIN (ANALYZE TRUE, TIMING FALSE, BUFFERS FALSE)
testdb-#            SELECT * FROM residents WHERE age = 'under18' AND license = 'none';
                                      QUERY PLAN
--------------------------------------------------------------------------------------
 Seq Scan on residents  (cost=0.00..2.50 rows=8 width=18) (actual rows=20.00 loops=1)
   Filter: ((age = 'under18'::age) AND (license = 'none'::license))
   Rows Removed by Filter: 80
183
048
rows

估算值为 8，而实际值为 20。

实际值 20 是正确的，因为（至少在作者的祖国日本）未满 18 岁的人无法取得驾驶执照。因此，under18 年龄段的 20 位居民必然都 没有执照。

3.2.4.4. 根本原因：假设 independence

PostgreSQL planner 估算出 8，是简单地将 under18 的比例（0.2）与 none 的比例（0.4）相乘，假设这些列是 独立的：(0.2×0.4)×100=0.08×100=8 $(0.2×0.4)×100=0.08×100=8$ $(0.2 \times 0.4) \times 100 = 0.08 \times 100 = 8$。

不仅是 PostgreSQL，许多 RDBMS 的 planner 在计算 Cardinality（以及 Selectivity）时，如果没有特别指定，都会假设列之间相互 independent，而不会考虑列间的 correlation。因此，列之间的 correlation 越强，planner 的估算就会越差。

Cardinality 估算没有完整的解决方案，它至今仍是一个活跃的研究领域。

3.2.4.5. 一种部分解决方案：Extended Statistics

尽管如此，部分解决方案还是存在的。例如，PostgreSQL 在第 13 版中引入了对 extended statistics 的支持。

通过使用 CREATE STATISTICS 语句，我们可以将 age 与 license 列之间的 correlation 存储到一个新的统计信息 stat_residents 中。随后，planner 就可以使用 stat_residents 来进行 cardinality 估算，从而避免列间 independence 的假设。

testdb=# CREATE STATISTICS stat_residents (mcv) ON license, age FROM residents;
CREATE STATISTICS
testdb=# ANALYZE;
ANALYZE

在创建并分析 extended statistics 之后，我们来看一下针对 under18 年龄段居民的估算结果：

  3. age = 'under18' AND license = 'gold' sql testdb=# EXPLAIN (ANALYZE TRUE, TIMING FALSE, BUFFERS FALSE) testdb-# SELECT * FROM residents WHERE age = 'under18' AND license = 'gold'; QUERY PLAN ------------------------------------------------------------------------------------- Seq Scan on residents (cost=0.00..2.50 rows=1 width=18) (actual rows=0.00 loops=1) Filter: ((age = 'under18'::age) AND (license = 'gold'::license)) Rows Removed by Filter: 100 112 053 rows

对于 under18 年龄段，"无执照" 的估算值与实际值都是 20。

"standard" 与 "gold" 的估算值为 1，而 实际值 为 0。（估算值 1 很可能是由于四舍五入误差造成的。）

Extended Statistics 的局限性

PostgreSQL 通过 CREATE STATISTICS 创建的 Extended Statistics 只能针对属于 同一张表 的列进行配置。

遗憾的是，此特性无法应用于涉及多个表的 join。这一限制意味着在 JOIN 操作期间，Cardinality 估算 的准确性仍然相当差。

事实上，跨多表的 cardinality 估算是一个重大挑战。尽管已经开展了大量研究，但一个实用、普遍适用的解决方案尚未实现。这一领域至今仍是 RDBMS 研究的前沿。
