3.5.1. Nested Loop Join

Nested loop join 是最基础的 join 操作，可用于所有 join 条件。PostgreSQL 支持 nested loop join 以及它的五种变体。

3.5.1.1. Nested Loop Join

Nested loop join 不需要任何启动操作，因此 start-up cost 为 0：

$$ '\text{start}-\text{up cost}' = 0. $$

Nested loop join 的 run cost 与 outer 表和 inner 表的大小之积成正比。换句话说，'run cost' $‘run cost’$ $\text{‘run cost’}$ 为 O(Nouter×Ninner) $O(Nouter×Ninner)$ $O(N_{outer} \times N_{inner})$，其中 Nouter $Nouter$ $N_{outer}$ 和 Ninner $Ninner$ $N_{inner}$ 分别为 outer 表和 inner 表的 tuple 数量。更准确地说，run cost 由以下公式定义：

$$ '\text{run cost}' = \left(\right. \text{cpu}\text{operator}\text{cost} + \text{cpu}\text{tuple}\text{cost} \left.\right) \times N_{o u t e r} \times N_{i n n e r} + C_{i n n e r} \times N_{o u t e r} + C_{o u t e r} $$

其中 Couter $Couter$ $C_{outer}$ 和 Cinner $Cinner$ $C_{inner}$ 分别为 outer 表和 inner 表的扫描 cost。

图 3.19. Nested loop join。

Nested loop join 的 cost 总是会被估算，但这种 join 操作很少被实际采用，因为下文描述的更高效的变体通常会被使用。

3.5.1.2. Materialized Nested Loop Join

上面描述的 nested loop join 每读取一条 outer 表的 tuple，都必须扫描 inner 表的全部 tuple。由于为每条 outer 表 tuple 都扫描整个 inner 表是一个代价很高的过程，PostgreSQL 支持 materialized nested loop join，用以降低 inner 表的总扫描 cost。

在运行 nested loop join 之前，executor 会使用下文所述的 temporary tuple storage 模块对 inner 表进行一次扫描，将 inner 表的 tuple 写入 work_mem 或临时文件中。

这可能比使用 buffer manager 更高效地处理 inner 表的 tuple，尤其是当所有 tuple 至少都能被写入 work_mem 时。

图 3.20 说明了 materialized nested loop join 如何执行。对 materialized tuple 的扫描在内部被称为 rescan。

图 3.20. Materialized nested loop join。

PostgreSQL 内部提供了一个 temporary tuple storage 模块，用于 materialize 表、在 hybrid hash join 中创建 batch 等等。该模块由定义在 tuplestore.c 中的函数组成，它们在 work_mem 或临时文件中存取一段 tuple 序列。使用 work_mem 还是临时文件的决策取决于待存储 tuple 的总大小。

下面我们通过一个具体的示例来探索 executor 如何处理 materialized nested loop join 的 plan tree，以及 cost 是如何估算的。

testdb=# EXPLAIN SELECT * FROM tbl_a AS a, tbl_b AS b WHERE a.id = b.id;
                              QUERY PLAN
-----------------------------------------------------------------------
 Nested Loop  (cost=0.00..750230.50 rows=5000 width=16)
   Join Filter: (a.id = b.id)
   ->  Seq Scan on tbl_a a  (cost=0.00..145.00 rows=10000 width=8)
   ->  Materialize  (cost=0.00..98.00 rows=5000 width=8)
         ->  Seq Scan on tbl_b b  (cost=0.00..73.00 rows=5000 width=8)
rows

首先展示 executor 的操作。Executor 按如下方式处理所显示的 plan 节点：

  • 第 7 行：Executor 通过顺序扫描（第 8 行）materialize inner 表 tbl_b。
  • 第 4 行：Executor 执行 nested loop join 操作；outer 表为 tbl_a，inner 表为已 materialize 的 tbl_b。

接下来估算 'Materialize'（第 7 行）和 'Nested Loop'（第 4 行）操作的 cost。假设 materialize 后的 inner tuple 被存储在 work_mem 中。

Materialize:

启动没有 cost，因此 start-up cost 为 0。

$$ '\text{start}-\text{up cost}' = 0 $$

Run cost 由以下公式定义：

$$ '\text{run cost}' = 2 \times \text{cpu}\text{operator}\text{cost} \times N_{i n n e r} $$

因此，

$$ '\text{run cost}' = 2 \times 0.0025 \times 5000 = 25.0 . $$

另外，total cost 是 startup cost、顺序扫描的 total cost 以及 run cost 之和：

$$ '\text{total cost}' = \left(\right. '\text{start}-\text{up cost}' + '\text{total cost of seq scan}' \left.\right) + '\text{run cost}' $$

因此，

$$ '\text{total cost}' = \left(\right. 0.0 + 73.0 \left.\right) + 25.0 = 98.0 . $$

(Materialized) Nested Loop:

启动没有 cost，因此 start-up cost 为 0。

$$ '\text{start}-\text{up cost}' = 0 $$

在估算 run cost 之前，我们先考虑 rescan cost。该 cost 由以下公式定义：

$$ '\text{rescan cost}' = \text{cpu}\text{operator}\text{cost} \times N_{i n n e r} $$

在本例中，

$$ '\text{rescan cost}' = \left(\right. 0.0025 \left.\right) \times 5000 = 12.5 . $$

Run cost 由以下公式定义：

$$ '\text{run cost}' & = \left(\right. \text{cpu}\text{operator}\text{cost} + \text{cpu}\text{tuple}\text{cost} \left.\right) \times N_{i n n e r} \times N_{o u t e r} \ + '\text{rescan cost}' \times \left(\right. N_{o u t e r} - 1 \left.\right) + C_{o u t e r , s e q s c a n}^{t o t a l} + C_{m a t e r i a l i z e}^{t o t a l} $$

其中 Ctotalouter,seqscan $Couter,seqscantotal$ $C_{outer,seqscan}^{total}$ 是 outer 表的总扫描 cost，Ctotalmaterialize $Cmaterializetotal$ $C^{total}_{materialize}$ 是 materialize 操作的 total cost。因此，

$$ '\text{run cost}' = \left(\right. 0.0025 + 0.01 \left.\right) \times 5000 \times 10000 + 12.5 \times \left(\right. 10000 - 1 \left.\right) + 145.0 + 98.0 = 750230.5 . $$

3.5.1.3. Indexed Nested Loop Join

如果 inner 表上存在一个 index，可以用它查找满足 join 条件的 tuple，那么 planner 会考虑使用该 index 直接搜索 inner 表的 tuple，而不是进行顺序扫描。这种变体被称为 indexed nested loop join；参见图 3.21。尽管名字里带 loop，但该算法能够在单次 loop 中处理 outer 表的所有 tuple，因此可以高效地执行 join 操作。

图 3.21. Indexed nested loop join。

下面展示一个 indexed nested loop join 的具体示例。

testdb=# EXPLAIN SELECT * FROM tbl_c AS c, tbl_b AS b WHERE c.id = b.id;
                                   QUERY PLAN
--------------------------------------------------------------------------------
 Nested Loop  (cost=0.29..1935.50 rows=5000 width=16)
   ->  Seq Scan on tbl_b b (cost=0.00..73.00 rows=5000 width=8)
   ->  Index Scan using tbl_c_pkey on tbl_c c  (cost=0.29..0.36 rows=1 width=8)
         Index Cond: (id = b.id)
rows

在第 6 行，显示了访问 inner 表一条 tuple 的 cost。这是在 inner 表中查找满足 index 条件 '(id=b.id) $(id=b.id)$ $(\text{id} = \text{b.id})$'（见第 7 行）的 tuple 的 cost。

在第 7 行的 index 条件 '(id=b.id) $(id=b.id)$ $(\text{id} = \text{b.id})$' 中，'b.id $b.id$ $\text{b.id}$' 是 outer 表在 join 条件中使用的属性值。每当通过顺序扫描取到一条 outer 表的 tuple 时，第 6 行的 index scan path 就会查找待 join 的 inner tuple。换句话说，每次将 outer 表作为参数传入，该 index scan path 就会查找满足 join 条件的 inner tuple。这种 index path 被称为 parameterized (index) path。细节描述见 README。

该 nested loop join 的 start-up cost 等于第 6 行 index scan 的 cost；因此，

$$ '\text{start}-\text{up cost}' = 0.285 . $$

Indexed nested loop join 的 total cost 由以下公式定义：

$$ '\text{total cost}' = \left(\right. \text{cpu}\text{tuple}\text{cost} + C_{i n n e r , p a r a m e t e r i z e d}^{t o t a l} \left.\right) \times N_{o u t e r} + C_{o u t e r , s e q s c a n}^{r u n} $$

其中 Ctotalinner,parameterized $Cinner,parameterizedtotal$ $C^{total}_{inner,parameterized}$ 是 parameterized inner index scan 的 total cost。

在本例中，

$$ '\text{total cost}' = \left(\right. 0.01 + 0.3625 \left.\right) \times 5000 + 73.0 = 1935.5 $$

run cost 如下：

$$ '\text{run cost}' = 1935.5 - 0.285 = 1935.215 . $$

如上所示，indexed nested loop 的 total cost 为 O(Nouter) $O(Nouter)$ $O(N_{outer})$。

3.5.1.4. Other Variations

如果 outer 表上存在 index 且其属性参与 join 条件，则可以用它做 index scan 代替 outer 表的顺序扫描。特别是，如果存在一个 index，其属性可以作为 WHERE 子句中的 access predicate，则 outer 表的搜索范围会被缩小。这可以大幅降低 nested loop join 的 cost。

PostgreSQL 支持三种带 outer index scan 的 nested loop join 变体。参见图 3.22。
