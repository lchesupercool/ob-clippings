---

在我最近与 Claude Code 用户的交流中，有一个主题反复出现：1M token 的 context window 是一把双刃剑。

它让 Claude Code 可以更长时间地自主运行、更可靠地处理任务，但如果你不有意识地管理你的 session，也会让 context pollution 有机可乘。

session 管理比以往任何时候都更重要，而围绕它似乎也有不少问题。你是在一个 terminal 里保持一个 session 开着，还是两个？每次 prompt 都从头开始？什么时候该用 compact、rewind 或者 subagents？什么情况会导致一次糟糕的 compact？

这里面有着令人意外的诸多细节，它们真正塑造着你使用 Claude Code 的体验，而其中几乎所有内容都来自对 context window 的管理。

关于 Context、Compaction 与 Context Rot 的快速入门

context window 是模型在生成下一次回应时能够一次性"看到"的全部内容。它包括你的 system prompt、目前为止的对话、每一次 tool call 及其输出，以及每一个已经读过的文件。Claude Code 拥有一个一百万 token 的 context window。

不幸的是，使用 context 有一点轻微的代价，通常被称为 context rot。context rot 指的是这样一种观察：随着 context 增长，模型的表现会退化，因为 attention 被分散到更多 token 上，而更早的、无关的内容会开始干扰当前任务。对于我们的 1MM context 模型，我们看到某种程度的 context rot 大约在 ~300-400k token 处出现，但这高度取决于具体任务——并不是一条硬性规则。

context window 是一个硬性截断，因此当你接近 context window 末尾时，你需要把目前为止一直在做的任务总结成一段更小的描述，并在一个新的 context window 中继续工作，我们把这叫做 compaction。你也可以自己触发 compaction。

每一次 Turn 都是一个分岔点

比如说你刚刚让 Claude 做了某件事，它完成了，你现在的 context 里已经有一些信息（tool call、tool 输出、你的指令），而接下来该做什么，你有着出人意料之多的选项：

  • Continue — 在同一 session 中再发一条消息
  • /rewind (esc esc) — 跳回到某条之前的消息，并从那里重新尝试
  • /clear — 开启一个新的 session，通常会带上一份你从刚刚所学中提炼出的简报
  • Compact — 总结目前为止的 session，并在这份总结之上继续
  • Subagents — 把下一块工作委派给一个带有自己干净 context 的 agent，并只把它的结果拉回来

虽然最自然的做法就是继续，但另外四个选项的存在是为了帮你管理 context。

什么时候开启一个新的 Session

新的 1M context window 意味着你现在可以更可靠地完成更长的任务，比如让它从零构建一个全栈应用。但是仅仅因为你的模型还没有耗尽 context，并不意味着你就不该开启新 session。

我们的一般经验是：当你开始一个新任务时，你也应该开启一个新的 session。

一个灰色地带是，当你想要做一些相关的任务、其中部分 context 仍然必要、但并非全部都必要时。

比如说，为你刚刚实现的一个 feature 撰写文档。虽然你可以开启一个新 session，但 Claude 将不得不重新阅读你刚刚实现的那些文件，这会更慢也更昂贵。由于文档并不是一个对智能高度敏感的任务，这些额外的 context 所带来的效率收益——即不必再次重新读一遍相关文件——大概是值得的。

Rewind 而非修正

如果要我挑出一个能代表良好 context 管理的习惯，那就是 rewind。

在 Claude Code 中，双击 Esc（或者运行 /rewind）可以让你跳回任何一条之前的消息，并从那里重新 prompt。那个点之后的消息会从 context 中被丢弃。

rewind 往往是比修正更好的做法。比如说，Claude 读了五个文件，尝试了一种方法，结果不奏效。你的本能可能是输入"这不管用，试试 X 吧。"但更好的做法是 rewind 到文件读取刚刚完成之后的那一刻，并带着你所学到的东西重新 prompt："不要用 A 方案，foo 模块没有暴露那个——直接走 B 方案。"

你也可以使用"从这里开始总结"，让 Claude 把它所学到的东西总结出来并创建一条交接消息，有点像是一条由未来的 Claude 发给之前那个尝试了某件事却没成功的 Claude 的消息。

Compact 与开新 Session 的对比

一旦一个 session 变长，你有两种方式来减负：/compact 或 /clear（然后重新开始）。它们感觉很像，但行为非常不同。

Compact 会让模型总结目前为止的对话，然后用这份总结替换掉历史记录。它是有损的——你是在信任 Claude 来判断哪些内容重要，但你不必自己写任何东西，而且 Claude 在纳入重要的学习和文件方面可能更周全。你也可以通过传入指令来引导它（/compact 聚焦于 auth 重构，丢掉 test debugging 部分）。

使用 /clear 时，你会写下什么才是重要的（"我们在重构 auth middleware，约束是 X，重要的文件是 A 和 B，我们已经排除了 Y 方案"）然后干净地重新开始。这更费功夫，但由此得到的 context 正是你认定相关的那些。

什么会导致一次糟糕的 Compact？

如果你经常跑长时间运行的 session，你可能已经注意到有时候 compact 的效果会特别差。在这种情况下，我们经常发现：糟糕的 compact 往往发生在模型无法预测你的工作将往哪个方向走的时候。

比如说 autocompact 在一段长时间的 debug session 后触发，并总结了整个调查过程，而你的下一条消息是"现在修一下我们在 bar.ts 里看到的另一个 warning。"

但由于这个 session 聚焦于 debug，另一个 warning 可能在总结中被丢弃了。

这一点特别棘手，因为由于 context rot 的存在，模型在 compact 时正处于它最不聪明的状态。有了一百万 context，你就有更充裕的时间去主动 /compact，并带上一段关于你想做什么的描述。

Subagents 与全新的 Context Window

Subagents 是 context 管理的一种形式，当你事先就知道某一块工作会产生大量你之后不再需要的中间输出时，它很有用。

当 Claude 通过 Agent tool 派生一个 subagent 时，那个 subagent 会获得自己全新的 context window。它可以做所需要的任意多的工作，然后把结果综合起来，这样就只有最终的报告会回到 parent。

我们使用的心理测试是：这个 tool 的输出我之后还需要吗，还是只需要结论？

虽然 Claude Code 会自动调用 subagents，但你可能想要明确地告诉它去这样做。比如说，你可能会告诉它：

  • "派一个 subagent，根据以下 spec 文件去验证这项工作的结果"
  • "派一个 subagent 去通读另一个 codebase，并总结它是如何实现 auth flow 的，然后你自己以同样的方式去实现"
  • "派一个 subagent，根据我的 git 变更为这个 feature 撰写文档"

总结

总而言之，当 Claude 结束一个 turn、你即将发送一条新消息时，你面临一个决策点。

随着时间推移，我们预计 Claude 会帮你自己处理这件事，但就目前而言，这是你可以引导 Claude 输出的方式之一。
