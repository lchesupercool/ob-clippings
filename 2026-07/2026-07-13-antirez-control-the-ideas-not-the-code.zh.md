# 掌控想法，而非代码

> 作者：antirez · [原文](https://antirez.com/news/169)

看看这个博客的过往历史。有许多关于用 AI 编程的博文，其中有几篇可以追溯到 2024 年 1 月（比如这篇：https://antirez.com/news/140）。毕竟，我算是一名颇受认可的程序员。我并不需要像一个寻求相关性的老年人那样，仍然待在这个“圈子”里；我最近重新加入了 Redis，现在还在开发一款用于本地 LLM 推理的新开源软件，它在社区中获得了很好的反响。为什么我仍持续这样做，说出人们不想听的话？为什么我持续宣告未来的编程默认会是什么样子？因为我感到有必要降低这场变革对那些准备得不如我的人所造成的冲击——他们往往比我年轻，而且不像我一样，没能预见到许多事情即将发生（2022 年，在 ChatGPT 出现之前，我出版了一本书，预告了许多如今已经发生的事，以及其他一些我相信*将会*发生的事，所以我觉得这样说并不显得自大）。

所以，我有一个小把戏。人们越来越觉得编程已经被 AI 彻底改变，却不知道自己该做什么；他们是否真的可以以一种完全不同的方式开始编码，不再把代码当作自己的主要产出而反复审视。他们觉得自己正在背叛所属的领域。因此，我的意图是走过来对他们说：“看看我，我会写代码，你知道的，我不是躲在 AI 背后：然而，事情已经变了，这不是你的软弱，也不是你被 AI 洗脑了。只是我们的领域正在朝一个令人惊叹*且*痛苦（但也令人愉悦）的方向演化。”

这就是为什么昨天我在 X 上说，我相信此时许多程序员能发挥的影响力比现在更小，因为他们在看代码。我真心相信这一点。请注意，这并不意味着只要求最终产品、随意地 vibe code。关键是：如果你掌控了软件的想法，那么查看代码本身就是次优的，而且往往毫无意义。原因如下：

1. 现在你可以生成大量代码，甚至*还没有*把 LLM 的代码冗长性算进去（而这在很大程度上也是无法很好地指示它们的结果）。你每天怎么可能审查 5k 行代码？

2. LLM 非常擅长写出局部最优的代码，而对宏大的想法则较差（但正在进步）。逐个函数、逐行扫描有什么意义？相反，你应该提示自己心中的设计，有时问：“那一部分的设计具体是什么？它是如何运作的？”，并评估它是否是正确的模型。这快得多。

3. 一个工作日是 8 小时。如果你阅读代码，这就是一种权衡。你会更少去做如今自己工作中最重要的部分，即问自己：我在用这个软件做什么？我想走向哪些新方向？以及思考新想法、功能、优化技巧。还要做大量 QA。

掌控想法。你还记得《人月神话》中的这个表述吗？好吧，一本 70 年代的书告诉我们的关于当前软件时代的事，比 2000 年到 2020 年间人们所说的许多事情更多。那些如今抗议 AI 的人，为什么没有对过去十年间软件的状况感到恐惧？近些年来、在 AI 出现之前，我们触及的劣质内容程度令人难以置信。再告诉你一件事。什么是劣质内容？借助 DwarfStar，我以完全自动化的方式为两个 LLM（DeepSeek v4 和 GLM 5.2）实现了推理，但：你自己试试看，就会发现你不能只说一句“实现 XYZ”然后看着它运行。你必须理解事物如何运作，什么是最佳设计，如何达到某个性能水平。随后，我为验证正确性，将该实现与其他系统进行了对比，发现其他实现有时包含更多错误。我进一步研究后发现，本地推理世界充满了细微的错误，它们不断累积并损害模型输出；注意力实现中的问题会导致上下文超过某个限度后性能出现下滑，因为索引式注意力实现是有缺陷的（例如，它们做了超出应做范围的工作），诸如此类。这是一个极难处理、快速变化的领域所造成的结果；每天发布的模型在推理图上彼此都有细微差异。对开发者而言，这是一场不公平的游戏。好吧：AI 对此帮助很大。有许多领域，严谨的工程工作（在设计侧）和测试，比手写 GPU kernel（或阅读它）*要好得多*。那么，我们是否确信这种抵制大部分不是意识形态性的？

昨天，Matteo Collina 回复我的推文时问我：但你不是说你会检查 Redis 中所有 AI 生成的代码吗？这确实是个好问题。是的，我会检查，但在这一点上，这件事是我*需要*做、但我相信大多没有意义的事情；在 GPT 5.5 发布后部分如此，而如今有了 Fable 和 GPT 5.6 Sol 则更是如此。没错：我会识别出一些我不喜欢其编码方式的东西，但如果我打开 Redis 其他贡献者写的其他 Redis 文件，其中有*糟糕得多*的东西；这并不是因为他们不是优秀的编码者，而是因为这属于品味问题。我写非常干净的代码，因为我希望它可读，所以在实现 Redis Arrays 时我做了修改。对于 Redis 有序集合节省 50% 内存的优化，我又在这么做；我很快会提交一个 PR。但我不觉得这还有用了。任何人都不应该再看这些代码，而只应看代码所包含的想法。我出于对用户的尊重继续这么做。Redis 目前是一个被广泛使用的东西，许多程序员会打开文件并手动修改东西。但如果我能放开手脚，你知道我会怎么做吗？把审查所占用的所有时间拿来做更多 QA，思考并应用下一个优化想法，并使用 LLM 编写一份 DESIGN.md 文件，用人类语言描述每种数据结构，以及其中包含的想法、实现技巧和设计。这在未来会有用得多。你想修改有序集合吗？你打开文件，阅读设计，然后你就掌握了这些想法。你可以带着正确的心智模型打开自己的 agent，询问它该做什么。这比审查代码有用得多。

Fable 和 GPT 5.6 对有序集合内存节省方案的审查，将发现远比我的审查能够发现的更多错误和细微的竞态条件。但我仍会去做。然而，对大多数软件项目而言，这一切已不再有意义。相反，专注于掌控想法。专注于质量、测试，以及对你想要交付的软件有一个明确的构想。世界已经改变，这很痛苦，但也充满了改善一个原本已彻底腐烂的软件世界的机会。

我只对缺乏足够经验、无法建立心智模型的年轻程序员存有疑虑。我们尚不知道，他们是否需要非常好地理解一段给定代码如何工作；但我相信他们应该学习如何编写程序。不过，我不确定检查 LLM 输出是他们应该做的正确事情。如果他们学习某种编程语言，并实现一个小型解释器、小型数据库、一个哈希表等等，可能会有用得多。为某个客户审查某个网站的一些 Javascript 代码？见鬼，不，别把时间浪费在那种破事上。
