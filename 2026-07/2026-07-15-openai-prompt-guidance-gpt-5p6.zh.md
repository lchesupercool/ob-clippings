# GPT-5.6 Sol 提示词指南

在将提示词、工具描述、智能体指令或提示词栈适配到 GPT-5.6 Sol 或 GPT-5.6 系列时，请使用本指南。请结合当前的 [GPT-5.6 模型指南](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.6) 查看 API 细节、限制、定价和功能可用性。

当提示词定义了结果、重要约束、可用证据和完成标准，并为模型选择高效路径留出空间时，GPT-5.6 的效果最好。

删除重复的指令和示例，并简化工具描述，可以提升任务表现和 token 效率。在一组内部编码智能体评测运行样本中，使用更精简系统提示词的配置让评测分数大约提升了 10-15%，同时总 token 减少了 41-66%，成本降低了 33-67%。结果会因工作负载而异，因此请把这些范围视为方向性参考，并在你自己的应用中使用有代表性的任务验证变更。

## 先简化提示词

从已经能正常工作的提示词和工具集开始。一次删除一组指令、示例或工具，然后重新运行相同的评测。

删减：

- 对同一规则的重复陈述；
- 不会改变行为的重复风格或流程指令；
- 不会改变行为的示例；
- 针对模型已经能可靠执行的行为的流程指令；
- 与任务无关的工具和工具描述。

保留：

- 用户可见的结果；
- 成功标准和停止条件；
- 安全、业务、证据和权限约束；
- 当路由取决于上下文时的工具路由规则；
- 必需的输出形状和验证要求。

检查剩余指令中是否存在矛盾。GPT-5-class 模型会严格遵循提示词契约，因此相互冲突的规则可能比缺少细节造成更大的不稳定性。

## 以结果为先的提示词和停止条件

描述目的地，而不是规定每一步。只要提示词说明了什么才算好，GPT-5.6 通常可以选择高效的搜索、工具或推理路径。

优先使用：

    端到端解决客户的问题。

    成功意味着：
    - 根据可用的政策和账户证据作出资格决定
    - 在回复前完成任何允许的操作
    - 返回 completed_actions、customer_message 和 blockers
    - 如果缺少必需证据，询问最小的缺失字段

避免不必要的绝对规则。只将 ALWAYS、NEVER、must 和 only 用于真正的不变量，例如安全规则、必填字段，或绝不应发生的操作。对于需要判断的情况，例如何时搜索、提问、使用工具或继续迭代，优先使用决策规则。

保留显式的用户取值。当正确取值是隐含的，请提供决策标准，并让模型根据上下文或 schema 推理。避免通用默认值、关键词映射和宽泛的语义捷径。

添加停止条件：

    用尽可能少的有用工具循环来解决请求，但不要让循环
    最小化优先于正确性、必需证据、计算或
    必需引用。

    每次得到结果后，询问核心请求现在是否可以用
    有用证据回答。如果可以，就回答。如果仍缺少必需证据，
    指明缺失事实并使用最小的有用备用方案。

## 个性、协作和回复长度

默认情况下，GPT-5.6 往往比 GPT-5.5 更简洁。迁移时，请检查“保持简洁”或“简短回答”这类宽泛的简洁指令是否仍然有用。它们对某些任务可能没有必要，有时还会让回复过短。只有当它们能可靠地产生应用所需输出时，才保留它们。

为了在不同请求之间获得更一致的控制，请使用 `text.verbosity` 设置默认细节级别，然后用提示词说明任务特定要求。为请求选择 `low`、`medium` 或 `high` 作为默认细节级别。在提示词中，指定任何任务特定的长度、结构或必需内容。API 示例见[设置 `text.verbosity`](https://developers.openai.com/api/docs/guides/deployment-checklist#set-up-textverbosity)。

对于面向客户的助手和协作型产品，请同时定义个性和协作风格。

- 个性控制语气、温度、直接程度、正式程度、幽默感、同理心和润色程度。
- 协作风格控制模型何时提问、作出假设、主动推进、解释权衡、检查工作和处理不确定性。

两者都要保持简短。个性应塑造用户体验；协作指令应塑造任务行为。两者都不应取代明确的目标、成功标准、工具规则或停止条件。

当任务需要更短的回答时，指出模型必须保留的信息，以及可以省略的细节。例如：

    先给出结论。包含支持结论所需的证据、任何重要
    限定说明和下一步行动。省略次要细节和重复内容。

    保留所有必需事实、决策、限定说明和后续步骤。优先删减引言、
    重复内容、泛泛的安抚以及可选背景。

这会给模型明确的优先级顺序：先保留完成任务所需的内容，再删除价值较低的细节。

“友好”或“有同理心”这类宽泛标签可能含义不明。请描述定义产品语气的写作选择，例如回答应有多直接，何时承认问题，以及是否适合安抚或署名结束语。

    直接陈述答案。如果用户报告问题，先承认
    具体问题，再给出下一步。仅在相关时使用安抚。
    省略泛泛的称赞和不必要的署名结束语。

避免“始终用用户的语言回复”这类一刀切的语言规则，除非这确实是产品要求。指定预期输出语言，以及何时应改变语言。

对于编辑、改写、摘要和面向客户的草稿，请告诉模型要保留什么：

    优先保留请求的产物、长度、结构、体裁和事实主张。
    在不添加新主张、新章节或更具推广性的语气的前提下，
    改进清晰度、流畅度和正确性，除非用户要求这样做。

## 定义自主性和审批边界

执行多步骤任务时，GPT-5.6 可以主动且持续地推进。请定义每个请求授权的操作级别，让模型可以在没有不必要暂停的情况下继续安全、范围内的工作，同时在外部、破坏性、高成本或扩大范围的操作前停止。

一个紧凑的政策通常就足够：

    对于回答、解释、评审、诊断或规划类请求，检查
    相关材料并报告结果。除非请求也要求变更，
    否则不要实施修改。

    对于变更、构建或修复类请求，执行请求中范围内的本地
    修改，并在不先询问的情况下运行相关的非破坏性验证。

    对外部写入、破坏性操作、购买或实质性扩大范围的行为
    要求确认。

明确列出安全的本地操作，例如读取文件、检查日志、编辑范围内代码以及运行测试。将政策放在一个地方，每条规则只说一次。重复“先询问”“不要变更”或“等待批准”等指令，可能导致模型对安全且预期中的操作提出不必要的审批请求。

对于长时间运行的工作，请定义当前工作层级。区分研究、设计、实现、评审和外部协调，避免模型在不说明的情况下从一个层级移动到另一个层级。

## 工具路由

只暴露与任务相关的工具。工具描述应说明该工具做什么、何时使用、重要返回字段和错误行为。

当正确性依赖前置检索或查找时，请明确说明：

    在采取行动之前，完成必需的发现、检索和
    验证步骤。不要因为预期最终状态看起来显而易见
    就跳过前置条件。

当多个读取操作相互独立时，将它们并行化。当一个结果决定下一步操作时，保持顺序执行。并行检索后，先综合结果再行动。

如果工具返回空结果、部分结果或可疑地狭窄的结果，在断定不存在结果之前，先尝试一两个有意义的备用方案。

## Programmatic Tool Calling

Programmatic Tool Calling (PTC) 最适合有边界的工作流，其中代码可以处理多个工具结果或大型中间输出，并返回小得多的结构化结果。

仅仅存在多个、并行或依赖的调用，并不足以证明应该使用 Programmatic Tool Calling。

适用于：

- 筛选、连接、排序、排名、去重和聚合；
- 跨大量相似记录的批处理；
- 重复性的确定性验证；
- 可以归约为紧凑 schema 的大型结构化结果。

在以下情况下优先使用直接工具调用：

- 一次调用已经足够；
- 中间输出已经很小；
- 每个结果都可能改变下一步决策；
- 某个操作需要审批；
- 最终答案必须保留引用或原生产物；
- 工作流需要在调用之间进行语义判断。

不要依赖“高效使用 Programmatic Tool Calling”这类泛泛指令。说明有边界的阶段、可用工具、输出 schema、重试限制、停止条件，以及何时交回直接模型判断。

    仅将 Programmatic Tool Calling 用于有边界的记录归约阶段。
    只调用已记录的只读工具。筛选并去重
    中间结果，然后只输出包含证据字段的必需紧凑 schema。
    瞬时失败最多重试两次。对审批、语义判断、引用和
    最终验证使用直接工具调用。

如果两条路径都需要，请定义一个明确的交接点，并告诉模型不要切换路径或重复已完成的工作。

`program_output` 项和最终的 assistant `message` 是不同的输出；请务必同时测试两者。理论上，程序可能返回了正确记录，而 message 却遗漏了必填字段、引用或限定说明。

在相同的代表性任务上比较直接调用和 programmatic calling。检查最终回复是否正确、完整，并包含必需证据。然后比较总 token、延迟、成本、调用次数、轮数和重试次数。只有当回复仍然通过现有评测时，较低的资源使用才应算作改进。

## 扎根、引用和检索预算

对于有依据的回答，引用行为应是提示词的一部分。定义什么需要支持、什么算足够证据，以及缺少证据时如何处理。没有证据不应自动变成事实上的“否”。

    对于普通问答，从一次宽泛搜索开始，使用简短、有区分度的
    关键词。如果顶部结果对核心请求包含足够支持，
    就根据这些结果回答。

    只有在缺少必需事实、负责人、日期、ID 或
    来源；用户要求穷尽覆盖或比较；必须读取某个
    特定产物；或某个重要主张否则将缺乏支持时，
    才进行另一次检索调用。

    不要仅为了改进措辞、添加示例或支持
    非必要细节而再次搜索。

对于研究和综合：

- 只引用已检索到的来源；
- 将引用附到它们支持的主张上；
- 将推论与直接支持的事实分开标注；
- 说明来源之间的冲突；
- 缩小答案范围或报告缺失证据，而不是猜测。

对于创意草稿，请区分来源支持的事实和创意措辞。不要为了让草稿听起来更有力而编造名称、指标、日期、路线图状态、客户结果或产品能力。

## 长时间运行的工作流和状态

对于多步骤或工具密集型任务，提示模型在第一次工具调用前给出简短的可见开场说明，然后只在主要阶段变化时提供稀疏的、基于结果的更新。不要要求模型叙述例行工具调用。

    在多步骤任务的工具调用前，发送一到两句
    用户可见的更新，说明第一步。任务过程中，仅在
    主要阶段开始或某个发现改变计划时更新。每次更新都应
    陈述一个具体结果和下一步。

重放历史时保留 assistant phase 值，让模型可以区分 commentary 和最终答案。如果使用 previous_response_id，先前的 assistant state 会自动保留。如果手动重放历史，保持每个原始 phase 值不变。

在重大里程碑之后进行压缩，而不是每轮都压缩。压缩后保持提示词在功能上一致，并将已压缩项视为不透明状态。

当目标、假设和优先级在多轮之间保持稳定时，persisted reasoning 很有用。当早先推理不再相关时，使用当前轮行为。不要把 persisted reasoning 当作始终开启的优化：过时推理会增加 token、提高延迟，并把模型锚定在过时的方法上。

提示词缓存也会影响提示词构造。保持可复用前缀稳定，避免大型系统提示词中不必要的变动。只有当显式缓存断点能为工作负载改善经测量的缓存行为和成本时，才使用它们。

## 推理强度

在改变 reasoning effort 之前，先用当前 reasoning effort 建立基线。

- 将当前 GPT-5.5 或 GPT-5.4 reasoning effort 保留为基线。
- 在代表性任务上测试相同设置以及低一级的设置。
- 当 low 能保持质量时，将其用于对延迟敏感的工作。
- 将 medium 作为均衡的起点。
- 仅当评测显示有实质收益时，使用 high 或 xhigh。
- 将 max 留给最困难、质量优先的工作负载；不要全局推荐它。

在提高 reasoning effort 之前，请检查提示词是否缺少成功标准、依赖规则、工具路由规则或验证循环。

## 前端和视觉任务

GPT-5.6 具有更强的布局、视觉层级和设计判断能力。仍然要提供产品上下文，保留现有设计系统，并说明重要的状态和约束。

对于增量式前端变更：

- 检查并保留现有设计 token、组件和模式；
- 除非被要求，否则不要添加额外功能或装饰性 UI；
- 保留响应式行为和预期状态；
- 在最终确定前渲染并检查结果。

对于视觉、computer use、本地化或 OCR 任务，如果空间精度很重要，请有意选择 image detail。对于大型、密集或坐标敏感的图像，在额外输入成本和延迟有正当理由时，使用 original detail。

## 完成前检查工作

让 GPT-5.6 可以访问能够验证输出的工具，并说明哪些验证很重要。

对于编码：

    修改后，运行最相关的可用验证：
    - 针对已变更行为的定向测试
    - 适用时运行类型检查或 lint 检查
    - 针对受影响 package 的构建检查
    - 当完整验证成本过高时，运行最小 smoke test

    如果无法运行验证，解释原因并说明次优检查。

对于视觉产物：

    在最终确定前渲染产物。检查布局、裁切、间距、
    缺失内容和视觉一致性。持续修订，直到渲染输出
    符合要求。

对于实现计划，请包含需求、命名资源或文件、状态转换或数据流、验证检查、失败行为、隐私或安全考虑，以及会实质影响实现的开放问题。

## 建议的提示词结构

将此结构作为复杂提示词的起点。保持每个部分简短。只在细节会改变行为时添加细节。

    角色：[模型的职能和上下文]

    个性：[语气和协作风格]

    目标：[用户可见的结果]

    成功标准：[最终答案之前必须满足的条件]

    约束：[政策、安全、业务、证据和副作用限制]

    工具：[使用哪些工具、何时使用，以及不要使用什么]

    输出：[章节、长度、格式和语气]

    停止规则：[何时重试、使用备用方案、拒答、询问或停止]

## 提示词迁移工作流

将现有应用迁移到 GPT-5.6 时：

1. 切换模型，并保留当前 reasoning effort。
2. 在改变提示词之前运行代表性评测。
3. 删除过时的脚手架、重复指令和无关工具。
4. 只添加能够修复已测量回归的最小定向指令。
5. 每次改变提示词或 reasoning 后，重新运行评测。

不要一次性重写一个可用的提示词栈。否则你无法判断行为变化来自模型、reasoning 设置、提示词、工具集还是运行时。

当提示词出现回归时，用一小组真实追踪记录调试。识别故障模式，找到可能导致问题的指令或矛盾，做一次精确编辑，然后重新运行相同案例。
