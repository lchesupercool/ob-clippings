# 访谈 Mitchell Hashimoto

2026 年 7 月 - Alex Alejandre

---

[Mitchell Hashimoto](https://mitchellh.com/) 曾主导 [Vagrant](https://vagrantup.com)、[Packer](https://packer.io)、[Consul](https://consul.io)、[Terraform](https://terraform.io)、[Vault](https://vaultproject.io)、[Nomad](https://nomadproject.io)、[Waypoint](https://waypointproject.io)，现在在构建 [Ghostty](https://ghostty.org/) 和 [Vouch](https://github.com/mitchellh/vouch)。

在这次访谈中，我们聊了终端、Zig 和开源。

---

**你已经接受过非常多访谈了。为什么人们喜欢采访你？**

访谈里，每个人切入的角度都不同。很多人想知道从软件工程师到商业创始人的心态转变是怎么发生的。也有人对产品、我在 Hashicorp 做过的工作，或者现在的 Ghostty 感兴趣。这次不一样的是，一开始没有已知议程；我们两个人都没有东西要卖。

**你觉得终端有什么好玩的？比如，为什么是 Ghostty？**

我花了大约 15 年构建 CLI 应用（不是现在常见的 TUI）。在这个过程中，我偶然学会了怎么给东西上色、移动光标等等。离开 Hashicorp 之后，我想打磨自己的技术能力（这些能力因为疏于使用已经有点生锈），并且具体想做三件事：前 AI 时代的 GPU 编程、桌面/单节点系统编程（我之前在分布式一侧花了太多时间，在那里你不会太担心缓存局部性或向量运算，因为网络成本占主导）。我也很想玩 Zig。我想满足这 3 件事。

构建 CLI 15 年之后，我并不理解终端模拟器是如何工作的。我知道终端的组成部分，但真的想理解它是怎么运作的；这也能让我同时做 GPU、桌面和 Zig。我的目标是让 vim 和编译器能跑在里面，让它能构建自己，然后就把它扔掉。但随着我更了解终端生态，我发现没有任何东西符合我想要的那个小众定位：快速、功能丰富、原生跨平台。我把它分享给 Discord 里的几个朋友，他们问能不能分享给其他人，因为他们已经每天都在用了。Ghostty Discord 原本只是我朋友们的群聊，后来被复用了。我不想发布，因为我的公众身份会带来太多不必要的关注，所以我做了很长时间的私有 beta。

**我们怎样才能把终端推得更远？**

我不支持把终端推到极端。当然，它们是一个应用平台，有能力做其他建立在 OS 之上的应用平台能做的那些事，比如浏览器、旧的 Java 应用运行时环境。你可以把所有功能都构建进去：视频和麦克风访问、响应式布局……你可以这么做。

但浏览器擅长一些事情，桌面擅长另一些事情，而基于文本的（等宽网格）应用也擅长一种独特的事情。这些基于文本的应用应该实现快、交互容易、安全模型清晰。这个生态里有很多机会，我也很想构建更多协议来启用这些能力。

相比其他范式，终端应用更适合组合。TUI 稍弱一些，但大多数 CLI 工具都有机制（不止 stdin 和 stdout）让你像使用函数一样使用它们（UNIX“只做一件事”的哲学是极端形式）。Neovim 和 AI 工具提供了越来越多命令行 flag。一个拥有更好终端应用的世界，就是一个拥有更好自动化和脚本能力的世界。

我想让终端成为应用的特殊场所。PTY 的带内信令（由转义序列组成的非结构化字节流）是个大问题。Nushell 生态试图用另一层来修复它，但我们需要一种根本改进。很多人不喜欢 Microsoft 生态，但 PowerShell 在结构化数据方面做对了很多事情。

**你怎么看非 legacy 的终端 API？**

我的北极星是：我们现在已经有多个主要的大型应用平台：浏览器、emacs、整个 Apple 生态、Microsoft 生态、Android、游戏主机平台。这些生态各有优缺点，但它们的框架是怎么工作的？在 Web 上，是 DOM 和 JS API。在 Apple 上，是 AppKit、[Cocoa](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/CocoaFundamentals/WhatIsCocoa/WhatIsCocoa.html) 和 SwiftUI。在 Windows 上，是 Win32、WinUI 等等。在 Linux 上，是 GTK 和 Qt 等等。当有人说我们需要一种更好的方式访问剪贴板数据（历史协议只有文本，那图片、多 MIME 类型等等怎么办？桌面系统几十年前就处理过这些问题），我会去看每个平台上剪贴板管理器的文档，看看大家最后落在了什么地方。我们没有理由只基于自己的理解去构建某个东西，而不研究几十年的先例。这就是我在这里尝试采用的方法。我还没有引入任何自定义协议。

有两个协议一直在对我喊叫。当前，终端有一个 main screen 和一个 alt screen（有时叫 primary 和 secondary），它们有不同属性。main screen 就像你的 shell，有 scrollback 等等；alternate screen 就像 Neovim、大多数 TUI 等等。只有 2 个，你要么开启某个模式，要么关闭它，从而进入 primary 或 secondary（占满整个屏幕、失去 scrollback 等等）。

我想引入一个 n-screen API，可以在后台创建和填充无限数量的 screen，让你用不同的网格尺寸叠加 screen 等等。终端模拟器可以处理换行、选择、鼠标事件路由等等。你可以把某个 screen 指定为一个独立窗口，由终端模拟器在网格之外渲染——想象一下你的 Neovim tab 同时作为原生窗口 tab 打开！这个基础层会解决很多事情。

我还设计了一个 button protocol。目前，有一些 mouse protocol 可以在有人点击网格单元格时得到通知。但你只能收到当前屏幕上的内容事件，历史里的、滚回去的内容就不行了。我们目前支持超链接（[OSC 8](https://gist.github.com/egmontkob/eb114294efbcd5adb1944c9f3cb5feda)），我想要类似 OSC 8 的东西：点击后向程序发送一条消息（由你指定）。你可以创建一个带有 `open_profile` ID 的按钮，即使用户滚回历史记录里，它仍然会注册。这会影响 main screen 应用（唯一有 scrollback 的应用），比如 Claude Code。我没兴趣在这里讨论 AI，它只是一个非常流行的 main screen 应用。一旦东西进入历史记录，你就失去了打开文件、应用内链接等能力。

**这在多大程度上只是在重做整个 user space？这里有很多范围蔓延的空间。**

我实验过用 Wayland 替换整个 pty 协议。如果眯着眼看，终端只是一个 windowing server，管理窗口和窗口上的 widget。我研究 Wayland 是为了让 Ghostty 在它上面跑得更好，我觉得对于它试图解决的问题（本地桌面、渲染窗口），它是一个相当好的协议。但我把那个方向扔掉了。

终端的问题之一是已经不再有标准化组织了。有一些旧规范，是 de jure 标准化的，但过去 20 年里，标准化主要基于最流行的终端做了什么。我们有一堆拼凑起来的功能，但没有一个实体在推动有品味的愿景。

我不知道正确的前进路径是什么。你可以为基于文本的应用创建一个替代性的家，不再叫终端，构建某种新东西（上面再放一个终端翻译层来带上 legacy 应用），尝试做不同的事情。

**你如何在这些想法和用户日常需求之间取得平衡？**

我非常公开地说过，开源维护者对用户没有 0 以外的任何义务。OS 许可证第一行就是“as is, no warranty”。这就是协议：你拿到免费软件，不能对它提出要求。但我喜欢努力构建好软件（有些人可能不同意，说我的软件很烂），所以我确实感觉有义务去修问题、让软件变得更好。

有些日子我醒来，预期就是翻 issue，修别人的问题。但有时我醒来会专注于我想要的东西，一个 issue、discussion 或 PR 都不看。有时你需要推动更大的愿景；有时你需要处理地面上的现实。

你可以在天空中建造一座完美城市，然后回来发现现实世界里充满恐惧和痛苦。所以有时候你需要清理那些东西。

如果我每天做的全部事情都是处理用户 issue，你会得到稳定但停滞的软件。如果你接受所有 PR，你会改变，但没有愿景。我不是想侮辱贡献者，但每隔几年只有一个人能从根本上理解它。大多数贡献只是挠某个人自己的痒，全部接受会导致一座代码大山。真正理解之后，你有时能发现优雅的系统，用简洁方式解决所有问题。

我曾经做过一个[功能设计视频](https://x.com/mitchellh/status/2001810354096214059?lang=en)，在里面我关闭了 3-4 个不同的功能请求，那些请求都在解决人们各自的问题，因为一个单一功能（不同于它们每一个）可以同时解决它们。很少有人能做到这一点，不是因为它困难，而是因为它需要一种很少有人会投入到别人项目里的关心程度。

> 我对这件事断断续续想了大概一年（和几百件其他事情一起，不是专门想；我不在电脑前时总是在想这些东西）。当我终于坐下来想“我要解决这个”时，可能……1 小时？<https://x.com/mitchellh/status/2003957851514126510>

**更少但组合得更好的功能会吸引人们走向异域的编程范式。这需要很多视角。**

我最近在网上和某个人因为我的哲学吵了一架。Ghostty 最高请求量的功能之一是 search，现在已经完成并发布了。但有人抱怨 search 让 Ghostty 臃肿，破坏了它的极简主义。我宣传 Ghostty 是 feature rich！但我确实把它和 bloat 区分开来。我认为你不应该为你不用的东西付出代价（除了磁盘空间或常驻代码内存）。我解释说，我架构 search 的方式意味着它会占用磁盘空间并被加载进 RAM，但什么都不会执行；如果你不用它，这就是一个免费的功能。我希望 Ghostty 是一个可 rice、可定制、适配人们需求的终端，但也能开箱即用，并把这些能力隐藏起来，直到你需要或搜索它们，同时不付出任何成本。

但如果你真的想要这样，就 fork 并自己维护。这并不比你要求我做的更多。如果你想让我维护一个 flag 来移除它，我也可以要求你维护一个移除它的 fork。告诉别人“fork it”经常会让他们不高兴。

**很少有人维护自己的 patch 等等，却要求整个项目移动来迁就他们。这是一种非常削弱自主性的心态：乞求别人去做他们自己很容易能做的事，放弃自己的能动性。**

我一直相信应该有更多 fork，无论是个人 fork 还是有人维护的 fork。

我确实会责怪我自己，以及整个风投支持的开源。这里有整整一代人，期待高度打磨、有资金、观点鲜明、有网站和付费支持人员（在 Discord、Slack 等）的项目，认为一个 open sourced 项目就是一个产品——在这些风投支持的案例里，它确实曾经是产品。但那只是生态里极其微小的一部分。

开源包括分享，但它的核心是自由和权利。这才是开源的核心部分，定义 OSI 批准的开源许可证。按你想要的方式使用软件，修改它，fork 它。这些权利里没有任何一项是关于稳定性或维护义务的。人们责怪维护者发布安全漏洞，但你为什么没有 review 那个 commit？你和维护者一样有义务 review 那个 commit。但人们把维护者放在更高责任上，而他们本来可以 fork，然后立刻成为维护者。

如果你想要更好的保证，如果你想拥有责怪某人的资格，那就为软件付费。当你拥有 vendor-customer 关系时，你现在就有权要求东西。但开源里没有 entitlement。按你喜欢的方式使用它，那才是得到你想要东西的路径。如果更多人 fork，他们也会对构建者更有同理心。

有时人们以为我的某个项目是一家公司，或者发一个 PR 修复一个我个人没有遇到的 bug，而我不合并，因为合并意味着承诺永远维护它。在个人项目里，我不会合并，因为我没有遇到那个 bug。

**消费别人那个“非产品”时，你怎么看 Zig 的开发？显然你可以接受没有 1.0。**

我知道自己报名参加的是什么。我是通过做编译器 patch 进入 Zig 的，也很了解这个社区。我很好地理解它的文化、哲学等等，所以我不会因为这些事情不高兴。

我预计 I/O 变更会是我们做过的最困难的事情之一，但我们还没开始。

Zig 越来越流行，而 BDFL Andrew 并没有从他认为必要的变更上退让；作为下游消费者，我喜欢这一点。0.15 相当重大，改变了 writer interface，因此影响任何打印任何东西的代码。但这个 API 确实好太多了。

Zig 正变得越来越好。他们非常关注编译工具，甚至移除了语言特性来提升编译速度，令人惊讶。你可以瞬间构建 lib-ghostty（整个终端），而 Andrew 仍然觉得这些毫秒太慢。

我确实认为 Zig 最终会到达 1.0，虽然我认为还要几年。当 AI 参与进来时，这件事重要性小得多。我希望读到这里的人知道，我不是 AI hype-master。

在非常基础的层面上，我们知道这些神经网络非常擅长模式匹配和模式填补。对于这类语言变更，我展示了如何在多种上下文中完成它，然后让它 draw the rest of the owl。虽然 diff 很大，但 90% 是我在厨房时自动完成的。这暗示了一个未来：如果你能解释如何从状态 A 迁移到状态 B，那么向后兼容性的重要性会降低很多。

考虑到 Zig 严格的反 AI 政策，这有点讽刺，但 AI 确实减轻了变更给下游用户带来的痛苦。

**你如何处理 library 和 API 设计？Ghostty 使用 lib-ghostty。一个朋友对你的库有多好用赞不绝口。除了单纯在乎之外，你有没有具体方法来改进它们？**

最具体的方法是在很多社区里使用很多库。就像学习一种你实际上不会（专业地）使用的编程语言一样，跨生态使用库会扩展你的视角，并让你受益。在大学里，我花了很多时间涉猎 esoteric languages。我用 Prolog、Haskell、Clojure，甚至 Java 做了很多玩具产品（我从来不是专业 Java 程序员，所以它对我来说很新。我用它写了一个完整的 web side project。我不喜欢它，但学到了很多关于 build system、ergonomics、libraries、web frameworks、web servers、app servers 以及所有那些东西）。每个生态都有不同文化。那种文化当然是人的文化，但它会渗透到他们在库和框架层面如何分离关注点、如何让 API 看起来。很长一段时间里，Java 到处使用 builder pattern，这在其他语言里我没怎么见过，但我在 Ruby 里试了一下，感觉挺好。这就是移植概念的例子。这就是我处理 library design 的方式：尝试使用那些我觉得最愉快的概念，并希望有类似品味的人也会喜欢它。

> 我坚信“名词”很重要，而 Docker 对我来说的问题是，有太多东西聚焦在 deployment/runtime 方面，并且干扰了人的工作流。Vagrant 直接、专门聚焦于 development 是有意设计的：配置、CLI 等等都围绕 development-focused nouns 展开，我认为这是一件好事。- <https://lobste.rs/c/ddl137>

**你自己会做终端应用来 dogfood 和测试这些 API 与想法吗？**

坦白说，不够。我整个职业生涯都是工具制造者，并且坚信 tool maker’s dilemma：你迫切需要某个东西，也很理解问题空间，于是构建了一个理想工具，但其他人喜欢它，你就变成了脱离地面的工具制造者，而不是工具使用者。这件事咬过我很多次。从终端角度看，我生活在终端里；但从 TUI 开发角度看，我做得不够，不过我们有几位维护者是高产 TUI 创作者，比如 [rockorager](https://github.com/rockorager)，他维护多个 email 和 IRC client，也撰写了一些规范。我一直在依靠他。

**你对今天的技术栈满意吗？过去你提到过精致打磨的 OS 作为产品，大型科技公司也曾经用技术区分自己。但现在看起来它们似乎完全放弃了，既不 dogfood，也不关心。它们的开源感觉停滞了（偶尔的例外，比如 Jujutsu 除外）。**

我对今天的技术栈……还……算……*okay*。它们是 *okay*。显然我希望很多事情不一样，但我不能太陷入对自己无法改变的事情、不是我该打的仗的压力里。比如，前端、TypeScript、React 类型社区里有很多好东西。但也有太多 churn、太多复杂性，抽象层次完全不清晰。我花时间研究过它们，但完全不同意这个社区在文化上处理这些问题的方式。但我不会去斗争、去替换它。所以我随波逐流，坚持主流，以便帮助社区、招聘等等。

我对今天的技术栈是 **fine**。我认为一些较新的发展整体上过于复杂。HTTP/1 vs. HTTP/2 和 HTTP/3，复杂性不是线性变化，而是非线性的；它以各种方式被合理化，但仍然难以下咽。你在前端技术、终端技术等领域都能看到这一点。我怀疑我们是不是移动得太快，以至于构建了一些本可以更简单的复杂东西。“我没时间写一封短信，所以写了一封长信。”这似乎正在整个行业里发生，并被 AI 和这类工具加速。

**谈到 Zig，你说你理解它的价值观等等。在 Hashicorp，你写过一份原则文档。你如何决定、创建、获得认同，并在日常中使用原则？为什么 Ghostty 比如说是 feature-rich？原则如何具体影响开发？**

即使当我和联合创始人写 Hashicorp 原则，或者当我决定 Ghostty 如何发展时，那都只是个人的，是我的反映，所以对我来说每天践行这些原则非常容易。我只需要做我自己。人们在制定不像自己的原则时会遇到问题。这就是新年愿望问题：你为生活做出这些宏大的、指向剧烈改变的意图，但它很难，因为真正做出剧烈改变本来就很难。

对于 Ghostty，我关心一些不那么人性、更技术、feature-rich 的选择，比如拥有跨平台核心，以及非常不跨平台但毫不抱歉的原生 GUI。重视这些东西的人会加入并协作；不同意的人就不会来。这很好。我非常喜欢开源项目和互联网是一组 tribes 的集合。

在这里，最让我恼火的是编程语言，很多语言正在变成 least common denominator 的 **things**，人们批评某某语言，因为它缺少其他所有语言都有的某个特性，所以它没用。类似这种夸张说法。其实我很喜欢某些语言缺少其他语言享有的某些特性，因为这些约束会孕育创造力和文化。我想要不同地方感觉不同。我不需要每个地方都让每个人感到欢迎。

人们会因为这段话生我的气，但你可以保留。比如，对我来说，我不喜欢 Rust 文化。没有更好的说法了。每次我和他们互动，或者听他们谈论 Rust 的方式，我就是不喜欢。这并不意味着他们是坏人；我认为他们是非常好的人。语言背后的哲学和语言本身都非常好。我只是不想使用它，这没有问题。仅仅因为我不想待在某个社区周围，并不意味着它不好。我也不喜欢足球。

但互联网上的人会陷入这种关于好与坏的二元视角，这会渗透到技术如何变成一池 conformist 的无聊东西。

回到 Zig，Zig 对它从技术到社区管理、资金、PR、博客文章以及话语方式所做的事情都有非常极化、非常具体的立场。我不完全同意所有立场，但我 *非常尊重* 它们毫不抱歉地怪异。所以我继续在财务上支持它们，并使用它们的技术，因为我支持人们努力成为他们自己。

**大公司存在巨大的质量保证问题，而像 Ghostty 或 Zig 这样的小项目可以用 taste 替代 4 个 PR，做出单一、整体性的解决方案（human scale）。你如何调和高质量交付和快速交付，是的还有 AI 生成代码等等？**

要交付正确的东西，就必须对你正在做的产品有更大的理解。这个角色在不同公司里由不同的人解决，但总体上 corporate America 在规模化时做得不好。你不能只是听一组客户或用户遇到的具体问题，然后解决那个具体问题。你需要理解他们一开始为什么会遇到这个问题，在你的软件之外是什么激发了这个问题？他们本来是否应该走到这里，或者上游某个东西是否本可以顺带解决另外 3 个问题？你需要一种更大、更整体的理解。我不知道如何在企业规模上解决这个问题。但我的处理方式是成为自己软件的重度用户。

我知道不是每个人都能做到这一点，但我只在那些我自己是其产品用户的岗位上工作过，所以我可以成为一个好的人类判断者，判断自己的工作是否好。如果你离客户太远，你就会转向“我完成了 spec”或“我勾选了 checkbox”，缺少足够深的理解去判断它是好还是坏。

我知道这个社区在 AI 方面有相当极化的分裂，但我一直是理性使用 AI 的强烈支持者。我完全会 sloppify demo 等等，因为我不会把它 ship 出去。代码是彻底的垃圾，但我可以玩一玩，检查某个方向是否有用。如果它好，我可以带着它应得的关心重新开始。现在我有一个 6 周大的宝宝，每天只有大约 3 小时在电脑前，所以任何节省时间的东西都很有帮助。现在，我可以做多得多，因为我可以在不在电脑前的时候把想法 ship 给自己。

你只需要交付质量，阅读并理解你 ship 的代码，并且对将要使用它的用户有同理心。你想创造一些他们会很愉快使用的东西。这就是全部。

**你会建议今天的人如何学习 C？直接从 Zig 开始有意义吗？**

更重要的是学习计算机如何工作，而让语言只是理解计算机工作方式的手段。我最重度使用 C 是在大学里，围绕文件系统和操作系统的 3 门课。C 只是我们贴近低层系统接口的机制。我的建议是，即使在这个更高层抽象和 web development 的时代，理解 CPU scheduling、memory、cache hierarchies、file systems、disk and file access 这些基础仍然很重要。当你直接在 syscall 层之上工作时，无论是用 C、Zig 还是 Rust，它真的会帮助你理解正在发生什么。如果你走得太高层，Python、JavaScript 或 Ruby 的 file open API 会为你抽象掉很多东西。

我学到很多的另一种方式，是阅读更高层语言是如何实现的。不要把标准库函数视为理所当然；某个人类写了它，而你也可以。它是怎么工作的？阅读 stdlib，并深入挖掘事情如何运作。语言很容易；语言不重要。底层理解才重要。
