# 通过 Harness 工程实现 AI 自我提升 — 中文摘要

## 一句话结论

这篇文章认为，AI 的递归式自我提升（RSI）短期内更可能先发生在模型外层的 Harness / Agent Runtime 上，而不是模型直接改写自身权重；真正决定强模型能走多远的，可能是围绕模型构建的工作流、上下文管理、工具调用、记忆、评估和权限控制系统。

## 文章主旨

机器之心编译了 Lilian Weng 的新博客《Harness Engineering for Self-Improvement》。文章讨论的核心问题是：当基础模型能力已经足够强时，系统性能的瓶颈会逐渐转移到“模型外面的那层工程系统”。

这里的 Harness 可以理解为包裹在模型外层的运行时与脚手架：它决定模型如何规划、如何调用工具、如何管理上下文、如何把中间产物写入文件系统、如何派生子智能体、如何评估结果，以及如何基于失败案例改进自身。Claude Code、Codex、Cursor 类编程智能体的成功，正是 Harness 工程价值的现实例子。

文章把近期围绕自我改进智能体的研究串起来，包括 ACE、Meta Context Engineering、Meta-Harness、AI Scientist、ADAS、AFlow、STOP、Self-Harness、AlphaEvolve、Darwin Gödel Machine 等，并讨论这些工作离真正的 RSI 还有多远。

## 核心概念：Harness 不只是提示词，而是运行时系统

早期 Agent 常被概括为“LLM + 记忆 + 工具 + 规划 + 行动”。但 Harness Engineering 更进一步，包含：

- 工作流设计：规划、执行、观察、测试、修复的循环。
- 上下文工程：决定哪些信息进入上下文，哪些进入长期记忆。
- 文件系统记忆：把日志、实验结果、代码 diff、失败记录写入可追溯文件，而不是全部塞进上下文窗口。
- 子智能体与后台任务：并发探索不同假设，避免污染主上下文。
- 评估与回归测试：让系统知道哪些修改真的改善了结果。
- 权限与安全边界：限制智能体可编辑的范围，避免奖励作弊或越权修改。

作者强调，Harness 更像操作系统或运行时，而不是简单 prompt 模板。它应该把复杂逻辑封装起来，同时暴露简洁、标准化的接口。

## 三个重要设计模式

### 1. 工作流自动化

智能体需要能在一个循环里运行、测试、观察、修复，再继续执行。Karpathy 的 autoresearch、OpenAI Codex Agent、Claude Code 都体现了这种“目标导向循环”。模型不是一次性回答问题，而是在运行时中分析工具结果、失败轨迹和测试反馈，再决定下一步。

这正是 Agent loop 的价值：智能体通过工具和环境反馈形成闭环，而不是静态生成一段答案。

### 2. 文件系统作为持久化记忆

长时程任务会产生大量中间状态：实验日志、错误记录、论文摘要、代码 diff、评估结果等。把这些全部放进上下文会很快失控。更稳健的方式是把状态落在文件系统里，让模型按需读取、搜索和编辑。

这个设计很重要，因为 LLM 本来就擅长理解文件、命令行、代码仓库和日志。随着基础模型能力增强，基于文件系统的记忆机制也会自然受益。

### 3. 子智能体与后台任务

主智能体可以派生多个子智能体并行执行搜索、实验或孤立子任务。关键是这些子任务的输出必须可检查、可追溯、可合并。如果结果只停留在临时对话上下文中，很快就会过期；如果被保存为文件、日志和状态，系统就能恢复、审计并继续推理。

## Harness 优化的演进路线

文章总结了 Harness 优化对象的演进：

指令提示词 → 结构化上下文 → 工作流 → Harness 代码 → 优化器代码。

也就是说，优化不再只是在 prompt 上做手工调参，而是逐渐转向自动优化“产生好答案的机制”。

## 上下文工程：从 prompt 到可演化 playbook

文章重点介绍了 ACE 和 MCE。

ACE（Agentic Context Engineering）把上下文当作持续演化的 playbook，而不是越堆越长的 prompt。它包含三个角色：

- Generator：基于现有上下文执行任务。
- Reflector：从成功和失败轨迹中提炼经验。
- Curator：把经验增量合并成结构化条目。

关键设计是：Curator 不重写整段 prompt，而是维护条目化、可去重、可精炼的上下文日志，避免上下文坍缩和“越改越短”的偏差。

MCE（Meta Context Engineering）进一步区分“上下文内容”和“管理上下文的机制”。它把技能表示为一组静态组件和动态算子，让元层智能体搜索更好的上下文管理方法，基础层智能体则在具体任务上优化上下文。

这和 Hermes / Obsidian / skills 的理念很接近：不是把所有东西塞进一次对话，而是把可复用的经验沉淀为结构化技能、文件和工作流。

## 工作流设计：自动化研究的 Harness

文章讨论了多种自动化研究系统。

AI Scientist 试图从研究想法、代码实现、实验运行、结果分析、论文写作到同行评审实现端到端自动化。ScientistOne 强调每个论断都要有证据链。Autodata 则用出题者、弱解题者、强解题者、验证者协作生成难度合适的训练/评估数据。

但这些系统也暴露出问题：能写论文不等于能做科学发现。自动化研究真正困难的部分不是“生成一篇看似完整的文章”，而是判断问题是否有价值、实验是否真实有效、失败是否应该被承认，以及结果是否能经得起证据链审查。

## 自动搜索工作流：ADAS 与 AFlow

ADAS 把 Agent 工作流设计本身变成优化问题：由元智能体提出新的工作流方案、写成代码、评估，再把成功方案加入档案库。

AFlow 则把工作流表示为图：节点是 LLM 调用，边是代码逻辑，并用蒙特卡洛树搜索寻找更好的流程。在问答、代码、数学任务上，AFlow 相比人工工作流和 ADAS 都有提升。

这说明：如果工作流可以被代码表示、可以被自动评估，那么 Harness 设计就能进入搜索空间，而不是完全依赖人类手工设计。

## 自我提升型 Harness：从 STOP 到 Self-Harness

STOP（Self-Taught Optimizer）是早期递归式脚手架改进案例。它不是直接优化某个答案，而是优化“改进器”本身。实验中，GPT-4 能发现遗传算法、任务分解、树搜索、模拟退火等策略；但较弱模型反而会越改越差。这说明自我改进依赖足够强的基础模型，递归结构本身不够。

Self-Harness 则让智能体通过“弱点挖掘 → Harness 提议 → 验证合并”的循环改进自身：

1. 从失败轨迹中聚类出真实失败模式。
2. 在有限、受控的可编辑区域内提出 Harness 修改。
3. 用 held-in 与 held-out 数据做回归测试，只有不引入退化的修改才会被接受。

这类方法的关键价值是：Harness 的改进不再是拍脑袋，而是基于失败证据和回归验证。但风险也很明确：如果允许系统编辑过多底层能力或评估逻辑，就容易破坏边界，引发 reward hacking。

## 进化搜索：让 Harness 像程序一样演化

文章把进化搜索视为 Harness 优化的重要路线，因为 Harness 搜索空间巨大、形状复杂，很难直接用梯度优化，但可以通过执行结果评估好坏。

AlphaEvolve 维护候选程序池，让 LLM 生成 diff 并保留更好的程序。ShinkaEvolve 引入父代采样、代码新颖性拒绝采样和元便签本，提高采样效率。Darwin Gödel Machine 则更直接：让编程智能体修改自己的 Harness 代码仓库，并通过评估决定哪些新版本能进入种群。

DGM 在固定模型条件下，将 SWE-bench Verified 表现从 20% 提升到 50%，说明即使模型权重不变，Harness 演化也能显著提升系统表现。

## 权重更新与 Harness 联合优化

文章最后讨论了更完整的自我提升：不仅改 Harness，也更新模型权重。SIA 尝试让反馈智能体决定下一步应该修改 Harness 还是更新模型参数。但作者认为该方向目前证据仍初步，实验设置也有难以横向比较的问题。

短期看，更可信的路径仍是先优化 Harness：因为它更容易验证、回滚、审计，也更接近现有软件工程实践。

## 未来挑战

文章最有价值的部分，是坦率列出当前自我提升系统的瓶颈。

### 1. 评估者弱且模糊

许多研究任务没有快速、客观、精确的验证器。自我提升循环最适合单元测试、基准分数、可量化指标明确的任务；但研究品味、新颖性、长期价值很难评分。

### 2. 上下文与记忆生命周期

智能体越自主，记忆越膨胀。真正有用的 Harness 必须决定什么该记、什么该忘、什么该总结、什么该归档。上下文工程会越来越像智能本身的一部分，而不只是外围软件。

### 3. 负面结果被忽视

科研文献天然偏向成功案例，LLM 也更容易学到“成功叙事”。但好的研究系统必须保存失败、承认失败，并从失败中缩小搜索空间。

### 4. 多样性坍缩

进化和强化学习循环容易过度利用已知高回报模式，导致所有候选方案变成同一种解法的变体。开放式研究尤其需要保护多样性。

### 5. 奖励作弊

系统会优化任何给它的奖励。如果奖励是单元测试，它可能过拟合测试；如果奖励是评判模型，它可能学会迎合评判模型；如果奖励是 benchmark，它可能钻基准漏洞。因此评估者和权限控制最好放在演化循环之外，并配合 held-out 测试、执行轨迹审计和关键节点人工审查。

### 6. 长期成功很难衡量

编程智能体能完成眼前任务，但未必能维护大型代码库的长期健康。可维护性、职责边界、迁移成本、向后兼容、未来调试负担，都很难被短期沙盒训练捕捉。

### 7. 人类角色上移

作者不是主张把人彻底移出循环，而是认为人类应该移动到更高抽象层：在关键时刻、关键层级提供监督、判断和价值约束。

## 对我们的启发

这篇文章和当前 Hermes / Claude Code / Codex 的实践非常贴近。真正可复利的不是某一次 prompt，而是：

- 把任务拆成可运行、可验证的 loop。
- 把经验沉淀成 skill / playbook。
- 把上下文落到文件系统和 Obsidian。
- 用测试、日志、索引、同步状态做闭环验证。
- 让子智能体并行探索，但把结果写成可追溯产物。
- 把“失败原因”也存下来，而不是只记录成功结果。

换句话说，Harness Engineering 本质上就是把 AI 使用从“聊天技巧”升级成“软件工程”。

## 我的理解

这篇文章最重要的判断是：模型智能和 Harness 工程不是二选一。更强的模型让更复杂的 Harness 成为可能；更好的 Harness 又能把模型能力释放到长时程、可验证、可恢复的任务中。短期内，RSI 不太可能表现为模型自己偷偷改权重，而更可能表现为：智能体逐渐学会改自己的工作流、上下文结构、工具使用方式和评估流程。

对个人工作流来说，这意味着最值得投入的不是追逐每一个新模型，而是建设一套可持续的 Harness：任务记录、知识库、技能、验证脚本、自动化 cron、审计日志、回滚机制。这些才是能跨模型复用的资产。
