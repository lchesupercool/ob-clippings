# ChatGPT Prompting 指南：从描述结果到可验证交付

## 一句话结论

好的 Prompt 不是把模型的每一步都规定死，而是清楚说明**要什么结果、基于什么上下文、以何种形式交付、哪些边界不能碰**；重要任务再加上可检查的验收条件。

## 文章主旨

官方把 Prompt 定义为“告诉 ChatGPT 你想知道、制作或修改什么”。它反对僵硬的模板：先用自然语言提出目标，查看结果，再用后续消息逐步校正。简单任务通常一句话足够；任务的风险、规模或影响增大时，才补充必要的信息。

一个完整 Prompt 可由四部分组成：

- **Goal**：要完成什么。
- **Context**：哪些材料、来源或背景会改变结论。
- **Output**：面向谁、什么格式、篇幅和详略。
- **Boundaries**：哪些事实不得改动、哪些来源必须使用、哪些动作必须先征求批准。

重点不是填满四格，而是只提供会显著改变产出的信息。

## 关键方法

### 1. 从结果而非操作步骤开始

先说“把会议纪要变成给项目组的短更新，决策和下一步放前面”，通常优于指定一长串模型该如何思考或检索的步骤。只有当过程本身是约束、可审计性要求或专业流程的一部分时，才明确过程。

### 2. 上下文必须有选择地提供

提供会改变答案的文件、表格、截图、网页或项目资料，并说明每份材料的用途；不要把所有东西都扔进去。涉及视觉内容时，应指出图中要关注的区域。需要最新事实时，明确要求 Web 搜索并要求给出来源。

连接的 Drive、Slack、GitHub 等来源也同样如此：说明去哪里找、寻找什么结论即可，不必微观指定每次搜索。

### 3. 边界是防止返工和误操作的最小控制面

高价值边界示例包括：

- 已批准的日期和预算不得改动。
- 只能使用提供的材料；信息缺失时标注而非猜测。
- 推荐必须在预算内。
- 先产出草稿，不得发送或发布。

文章的取向很明确：只写最关键的一两条边界，而非控制模型的每一步。

### 4. 让交付物“可用”，并要求最终检查

要说明结果的使用场景：给高管会前扫描的一页纸、带负责人和日期的跟进邮件、标出偏差超过 10% 的预算表等。重要交付要求模型最后检查，例如每个行动项是否都有 owner 与 due date、哪些内容尚未验证；但人工仍应在使用或分享前复核。

### 5. 把对话当作迭代，而非一次性考试

首个 Prompt 不必完美。根据结果提出具体修改即可：开头更直接、保留证据、建议放到背景之前；也可以补充来源、修正方向、要求替代方案或改变细节层次。

对于 Codex 运行中的任务，文档区分：

- **Steer**：把新消息加入当前运行，适合改方向、补遗漏。
- **Queue**：把消息留给下一轮，适合必须等当前工作完成后再做的跟进。

## Chat、Work 与 Codex 的分工

| 场景 | 更合适的能力 | Prompt 应突出什么 |
|---|---|---|
| 问答、改写、头脑风暴、轻量草稿 | Chat | 目标与目标受众 |
| 多来源、多步骤、改文件或大交付物 | Work | 来源、成果、审阅方式、验收 |
| 代码、代码库、开发工具 | Codex | 目标行为、相关代码/复现、约束、验证 |

Work 的建议是先要求一个可审查结果：缩小来源和日期范围、定义受众/格式/长度、把必需工作和可选润色分开；当方法重要时先要计划，并让模型在发送、发布或影响他人前请求批准。

Codex Prompt 则必须更像工程任务单：说明预期行为、可复现步骤、不可破坏的 API 或约束，以及要运行什么检查。多步骤改动可先用 `/plan` 让其调查并提出方案；计划确认后再实施。典型验收包括重新跑复现步骤、最小相关测试、lint，或在浏览器中查看渲染结果。

## 对实际使用的启发

这份指南的核心并非“提示词技巧”，而是**把责任边界和验证嵌入交付定义**：

1. 先把结果定义成能被人审阅的产物，而不是模糊的“帮我处理”。
2. 把不可逆或影响他人的动作显式改为“先草稿/先计划/先批准”。
3. 对研究、代码和文件任务，把来源、约束和验收条件与目标一起给出。
4. 用小步反馈代替一次性超长指令；保留模型在检索、比较和调整路径上的自由度。

对 AI Coding 而言，可将它压缩为一个实用模板：**要改成什么行为 + 相关文件或复现 + 不可破坏的约束 + 完成后如何验证**。这比要求模型照固定思维链执行更稳定，也更便于 review。
