# 人在回路中，已经累了｜内容总结

## 一句话结论

LLM 让写代码的产出变快了，却把人的角色改造成高强度的意图持有者、审查者和纠偏者；真正稀缺的资源不再是代码，而是人的注意力、判断力、品味和维持系统整体意图的能力。这个转变有真实价值，也有真实的疲惫与孤独，不该被当作个人适应不良。

## 文章主旨

作者不是在争论 AI 会不会取代程序员，而是在描述当下开发者的主观处境：LLM 编程既有效又让人失去稳定感。模型能高速制造看似合理的代码，但人仍必须持续确认方向、检查细节、修正偏差。若只谈生产力而忽略这种心理与认知成本，团队会更容易耗竭。

## 关键论点

### 1. “代码自己写”没有消除工作，而是把工作变成监督

Pydantic AI 维护者 Douwe 每天醒来要面对大量由 AI 在夜间生成的 PR；每个 PR 都需要人快速判断。他可以把审查也交给 AI，但随即会产生一个问题：那人还在系统中做什么？

作者自己的经验是：可能花近两天为 LLM 写计划、反复澄清和细化，模型仍会做出荒谬但貌似合理的事，例如把 React hook 放进不该放的 Storybook 文件、读错计划、编造不存在的组件。问题未必是模型不会写代码，而是它无法在复杂变更中持续保持连贯意图。

这带来“监督疲劳”：机器生成的结果大部分正确，但仍需要人的眼睛、判断和品味。过去和真人协作时，帮助对方成长本身是一种奖励；如今许多工作流把输出投进“AI 黑洞”，另一端没有真实的人学习或交流。

### 2. AI 提高了工作的强度，而非自动降低压力

LLM 的即时可用性诱发“再来一个 prompt、再加一个功能”的循环。作者因觉得计划“马上就对了”而工作到凌晨两点。另一个同事开玩笑说 Claude Code 卡住就多开五个 session，反正你忙着给其他 session 反馈。

这揭示了并行陷阱：可以启动的任务数量暴涨，但能深思熟虑完成的任务没有增加，因为最后仍受同一个无法并行化的瓶颈约束——人的大脑。

### 3. 人类的奖励函数被破坏了

手写代码虽难，却有密集的小奖励：在脑中解题、理解复杂逻辑、看到代码编译、获得控制感。LLM 自动化了大量产生这些多巴胺反馈的环节，却把它们替换为审查和监督的认知负荷。

结果是：令人满足的部分变少，令人耗竭的部分变多，新的反馈奖励却没有补上。因此，开发者同时觉得更高产、更不快乐，不是个人出了问题，而是工作反馈回路出了问题；作者主张应把它视为一个工程与组织设计问题。

### 4. LLM 编程会加剧孤立与成瘾式循环

原本开发者会向同事提问、橡皮鸭调试、分享一个小突破；现在这些互动常被又一个 prompt 替代。对于没有强协作文化的团队，AI 可能进一步降低沟通温度，偏偏人在最需要确认“其他人也觉得很难”的时候更孤立。

模型有时给出精彩结果、有时给出垃圾，且难以预测，这种间歇性奖励像斯金纳箱一样让人很难停下。切回手写代码也不轻松，因为 LLM 协作与手工编程是两种不同的思维模式，需要有意识地给自己切换的许可。

### 5. 这更像一次技能重构，而非技能死亡

作者把今天与响应式设计早期类比：固定像素布局被流动布局取代时，设计师也曾因失去控制感而焦虑。最终保留下来的并不是像素级控制，而是比例感、层级理解、系统思维、适应性，以及为不确定性设计的能力。

LLM 对编程也是类似的拐点，只是速度快得多、风险也更高。工程师不因没有亲手写每一行而失去价值；相反，面对更大规模的模型输出，知道“好是什么样”的能力变得更重要。

### 6. 留下并升值的能力：品味、架构判断与领域深度

当人人都能生成能编译的代码和看起来合理的 UI，真正的差异来自品味、细腻判断、成熟的架构观点，以及基于经验而非模式匹配的逆向判断。

人在自己理解最深的领域最能有效引导模型；一旦进入技能较浅的领域，输出会更“印象派”——看起来可信，离生产可用却更远。模型不知道自己不知道什么，只会自信地填补空白，这也是人类常见的失败模式。

与此同时，新技能正在形成：

- 对复杂计划做 `pre-mortem`：让全新的 LLM session 假设方案已经灾难性失败，并反推失败原因，以发现规格缺口。
- 从数千条历史 code review 评论里提炼规则，写入 `AGENTS.md`，把长期隐性的工程判断编码为模型可遵循的指令。

这不是专业知识消失，而是专业知识被蒸馏、外显和系统化。

## 对个人与团队的启发

1. 不要把“更高产却更痛苦”简单归因于自己不够适应；需要重新设计反馈、边界与协作机制。
2. 限制并行 agent/session 数量。并行生成不等于并行完成，人的审查带宽才是硬约束。
3. 对关键变更保留明确的意图、验收标准和人工质量闸门；不要让“看着对”取代“确实对”。
4. 有意识保留真人协作：设计讨论、结对审查、技术分享和共同学习，避免把所有沟通都压缩成 prompt。
5. 把个人与团队的工程判断沉淀成规则、测试、`AGENTS.md`、评审准则和可验证的工作流，而非只依赖临场提示词。
6. 主动在 LLM 辅助与手写/深度思考之间切换，为不使用 AI 留出正当位置。

## 我的理解

这篇文章最有价值的地方，是把 AI coding 的问题从“模型能否写代码”移到了“人如何在高产出系统中维持意图、获得反馈并保持协作”上。未来的工程效率不只取决于给模型更强的 prompt，也取决于是否为人的注意力设计了合适的节奏、质量门和社会性反馈。
