# 重新思考 GPT-6 Astra 的 Skills 与提示词

Eric Provencher

![重新思考 GPT-6 Astra 的 Skills 与提示词](../../assets/rethinking-skills-and-prompts-for-gpt-6-astra/cover.webp)

编码智能体已经取得了长足进步，最佳实践也在迅速变化。随着模型能力增强，以前需要大量手把手引导和脚手架的工作，如今已不再需要。

如果你在过去一年中一直使用 Codex 之类的智能体来开展项目，那么在努力引导模型取得良好结果的过程中，你很可能已经积累了大量指令。每次发布新版本时，都值得重新审视这些假设；但对于 GPT-6 Astra，这一点比以往任何时候都更加重要。

这些指令可以采用多种形式：Skills、`AGENTS.md` 和任务提示词都在影响模型完成工作的方式。

## 更好的 Skills

这些指令可以采用 Skills 的形式；Skills 本质上是存储为 Markdown 文件的提示词，也可以与资源及打包的脚本一起封装。一般来说，它们最适合用于指导特定工作流，或用于使用某些应用时的操作指引。

如今，人们往往默认在项目中封装大量 Skills；每个 Skill 都有名称和描述，它们会被载入模型的上下文，让模型知道何时使用它们。但许多描述实在太长，而当你添加过多 Skills 时，Codex 会开始缩短这些描述以便容纳。模型最终看到的每项描述都更少，因此更难判断该选择哪个 Skill。

更糟的是，这些描述往往会彼此矛盾，或过分强调何时应该使用 Skills，导致模型载入实际上对任务没有帮助的指令。

创建 Skills 的一种常见工作流是使用 `$skill-creator` Skill。我们最近更新了它的指导说明，以帮助缓解许多我们在实践中见过的失败模式。

首先，Skill 描述应该尽可能简短，同时明确说明模型应在何时使用它们：

> **明确说明适用情形**
>
> **反例**：创建并验证 Postgres schema 迁移。处理数据库、查询、模型或持久化时使用。
>
> **正例**：创建并验证 Postgres schema 迁移。添加或更改迁移，或审查其上线过程时使用。

*这里，反例中的 Skill 描述可能会促使模型在接触任何数据库相关内容时都使用它，而不是仅在必须处理迁移时才使用。*

其次，有用 Skill 的关键标志之一是渐进式披露。读取 Skill 会占用上下文，使你更接近上下文压缩，并引入可能不适用于当前任务的指导。对于包含多个工作流的 Skills，应将根文档做成一个最精简的路由器，由它指向配套文档和脚本。给模型足够的指导，让它知道去哪里查找，而不要迫使它读取当前无关的内容。

第三，许多 Skills 被写成了详尽的行程表或操作配方。模型理解细微差别和模糊性的能力已经大幅提升，因此，过去曾经有帮助的过度具体指导，如今反而可能妨碍结果。

仓库中的 Skills 也会指导其他贡献者的智能体，而它们可能使用不同的模型。对 Sol 或 Luna 有帮助的指导可能会对 GPT-6 Astra 造成过度约束，因此需要考虑你留下的指令将由哪些模型使用。

## 保持 AGENTS.md 最新

由于 [`AGENTS.md`](https://agents.md) 会在模型于你的仓库中工作时始终生效，因此你应该经常重新审视每条指令，并问问自己它是否仍然有必要。

仅仅为了修正一个拼写错误，就要求模型在每次编辑前阅读一整套文档或完整的仓库地图，这显然过度了。GPT-6 Astra 能自行判断需要阅读哪些内容，无需被要求在每次更改前审查整个项目。

> **阅读任务所需的内容**
>
> **反例**：每次编辑前，阅读 architecture.md、database.md 和 deployment.md。
>
> **正例**：需要了解服务边界时使用 architecture.md，涉及 schema 更改时使用 database.md，准备部署时使用 deployment.md。

*提示模型在每次编辑前读取文件，是消耗上下文并拖慢工作的绝佳方式。不过，指向某些文档仍可能有所帮助，只要这种指引贴合具体情境即可。也一定要让你的文档保持最新！*

以往的模型需要得到鼓励才会运行测试并检查自己的工作。GPT-6 Astra 会自行完成这些事，因此相同的指令可能导致不必要的测试。

GPT-6 Astra 做事很彻底，但对于一项任务究竟该推进到什么程度，它可能更加谨慎。有时需要稍微推动一下，让它继续进行。对于你确认安全的特定工作流（例如本地测试套件），可以使用 `AGENTS.md` 授予它相应权限：

> 本地测试使用可丢弃的 fixtures，且无法访问生产环境。运行测试，修复由所请求更改引起的失败，并重新运行受影响的测试；无需在每一步都请求批准。

## 决策边界

要格外留意你如何描述边界。如果先前的模型曾未经许可就代你行事，你可能添加过措辞强硬的指令，要求它先征求同意。这样做可能有用，但 GPT-6 Astra 是我们对齐程度最高的模型，判断力要好得多；除非确认安全，否则它不会执行任务——因此，你也应该据此对待它。

如果你之前设定边界，是因为想防止其他模型走得太远，而现在要切换到 GPT-6 Astra，请考虑更新相关措辞：Astra 可能会过于认真地遵守它，并在你其实乐于让它继续的地方停下工作。

## 持续推进

如果你习惯了 GPT-5.6 Sol 接到请求后持续工作很长一段时间，那么 GPT-6 Astra 在判断何时停止方面可能会显得更加谨慎。它可能完成第一版实现后就回来请你审查，尽管仍有工作尚未完成。

这正是预先定义完成标准能够发挥作用的地方。你可能需要推动 Astra 继续，直到彻底完成。如果任务包括让实现运行起来、检查结果并修复失败之处，就把这些内容写入请求。要求在第一版实现后停下来接受审查，会把模型拉向更早的停止点，所以请确认这是否真的是一个需要由你作出的决定。

如果你希望它在完成第一轮工作后继续探索，就说明你希望探索什么，以及应该在哪里停止。

新模型是清理门户的好机会，但你无需手动审查所有内容：请 GPT-6 Astra 根据本文讨论的内容进行一次审计，然后去构建一些你以前不会尝试的东西吧！
